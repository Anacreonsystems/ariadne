# Полное исследование исходников Flink

Использовать при продолжении архитектурного исследования Flink для собственного движка Ariadne. Это исследование архитектуры, а не встраивание Flink runtime и не продолжение прежней интеграции Prefect. Результаты лежат в `architecture/streaming-etl/research/flink-source-study/`.

## Поднять сохранённый контекст

1. Прочитать применимые `AGENTS.md`, затем README исследования, `corpus.json`, `coverage.json`, `verification.md` и свою часть confirmed ledger. Сверить Git branch/status, не терять несохранённую работу других участников.
2. Работать в существующей ветке `native-stream-storage`. Последние опубликованные срезы исследуются через Git history; не считать их завершением всего корпуса. Не менять исторические принятые ADR или implementation readiness из-за появления исследовательской главы.
3. Исходники в `/workspace/flink` должны соответствовать commit из `corpus.json`. На начало кампании это `068f428b29f4d9ee587fa1006d2f1a69b43c0000`. Исходное дерево используется только для чтения. Не менять ревизию и не редактировать source/tests/resources ради совпадения с теорией.
4. Проверить hash исходного inventory. Он является неизменным обязательством, а не реестром уже прочитанного. Новые внешние корпуса учитывать отдельно с собственным commit/inventory; не менять знаменатель задним числом.

## Читать, а не подменять чтение поиском

- Читать все строки назначенных файлов: объявления, generated boilerplate, комментарии, ошибки/cleanup, тесты и ресурсы. `rg`, AST, grep, заголовки методов, hash и подсчёт строк помогают навигации, но не закрывают чтение.
- Предъявлять небольшие полные диапазоны через `tools/read_source.py PATH --reader NAME --start N --lines K` из корня Ariadne. Для длинных строк уменьшать K. Учитывать суммарный output budget при пакетных вызовах.
- Exposure helper означает только вывод. После реального потребления неусечённого текста вручную добавить запись в `readers/NAME.confirmed.jsonl`: `path`, `start`, `end`, `file_sha256`, содержательная `note`.
- После truncated output перечитать пропавшие строки. До этого подтверждать только достоверно прочитанные диапазоны. Разрешены partial receipts: файл не становится fully_read до покрытия всех строк.
- При прямом нумерованном чтении без helper явно указать этот способ в note. Hash не заменяет чтение, а связывает подтверждение с конкретными байтами.
- Дубли разных readers допустимы и объединяются без увеличения уникального покрытия. Зависимости других областей можно читать, сохраняя исходного inventory owner.
- Бинарные ресурсы и gitlinks учитывать явно; не называть их прочитанным текстом. В исходном inventory есть `docs/themes/book` — gitlink `a486adf8462c0abfc9034436ddd72927d6656809`, вложенный theme repository пока не включён в текстовый корпус.

## Сохранять архитектуру по мере чтения

Главы 01–07 соответствуют control plane, execution/network, state/checkpoint/time, API/Python, Table/SQL, connectors/storage/metrics и build/web. Глава 00 связывает установленные цепочки. README служит входом; ссылки между главами формируют граф.

Для каждой подсистемы описывать конкретно:

- Входные вызовы/сообщения, владельца mutable state, thread/executor и lifetime.
- Последовательность успешного исполнения и различия между RPC ACK, обработкой сообщения, синхронным срезом и durable завершением.
- Backpressure/admission, ownership буферов/handles, release/close/cancel и неопределённость при ошибке ответа.
- Snapshot/restore/retry/rescale, идентичности attempts/epochs, fencing и ограничения serializers/time/state.
- Какие assertions прочитаны, что они фактически покрывают, что не запускалось. Название теста и комментарий не заменяют тело кода.

Ссылаться на `https://github.com/apache/flink/blob/<pinned-commit>/<path>#L<line>`. Свод чужого domain review явно атрибутировать соответствующей главе/reader; не заявлять собственное полное повторное чтение этих исходников. Расхождение комментария с реализацией описывать точно. Подозрение без воспроизведения помечать как source observation, не как подтверждённый production incident.

Исследовательская полнота, корректность описания и готовность будущего продукта — разные величины. Не объявлять чтение теста успешным тестовым прогоном. Не переносить найденный протокол в Ariadne без отдельного согласованного этапа ADR. В текущем этапе не запускать runtime implementation, прототипы, builds или нагрузочные тесты.

## Проверять и публиковать промежуточные срезы

1. `python3 architecture/streaming-etl/research/flink-source-study/tools/coverage.py` проверяет hashes/ranges и объединяет интервалы, создаёт `coverage.json` и `reading-status.jsonl`.
2. Проверить pinned source links и локальные ссылки, актуальность открытых вопросов и `git diff --check`. Helper scripts проверять репозиторным Ruff. Не расширять проверки до несвязанных runtime suites.
3. Перед commit в общей рабочей директории согласовать короткую паузу **записей** всех readers. Они могут читать напрямую без helper exposure writes и сохранить точные pending receipts после RESUME. Не запускать hooks, которые stash-ят одновременно изменяемые файлы.
4. Обновить verification с точным срезом, обычным commit/push сохранить документы в той же ветке в рамках действующего разрешения пользователя. Не обходить hooks, не amend/force и не менять identity пользователя.
5. Сразу после завершения hooks дать RESUME. Сначала сохранить pending direct-read receipts, затем продолжать. Не оставлять новое чтение только в памяти через compaction.

Полное исследование не закрывать, пока остаются непрочитанные файлы/диапазоны. В сообщениях указывать фактический объём и незавершённость; не обещать фоновую работу без действующего исполнения.
