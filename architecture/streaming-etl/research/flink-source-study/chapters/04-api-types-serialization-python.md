## От пользовательского вызова к двум графам

В этом checkout нельзя определять архитектурные границы по старым названиям Maven-модулей. `Transformation` и `TypeInformation` находятся в `flink-core`; `DataStream`, `StreamExecutionEnvironment`, `StreamGraph`, генераторы графов и классы операторов находятся в `flink-runtime`. Публичный Java package `streaming.api` не означает расположение в модуле `flink-streaming-java`. Переход API→implementation приходится проверять по вызовам, а не по имени каталога.

`DataStream<T>` хранит две ссылки: environment и transformation. Конструктор не выполняет поток; `getType()` обращается к выходному типу transformation. Вызов `map(mapper)` очищает closure, выводит тип через `TypeExtractor`, затем перегрузка с явным типом создаёт `StreamMap`. `flatMap` аналогично создаёт `StreamFlatMap`, `process` — `ProcessOperator`. Общий путь `transform` оборачивает оператор в `SimpleOperatorFactory`; `doTransform` сначала запрашивает тип входной transformation, затем создаёт `OneInputTransformation`, возвращает оболочку `SingleOutputStreamOperator` и регистрирует transformation в environment. Следовательно, здесь создаются описание и фабрика будущего вычисления, а пользовательский callback по элементам ещё не вызывается. [DataStream: поля и тип](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/datastream/DataStream.java#L113-L187), [map/flatMap](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/datastream/DataStream.java#L412-L481), [создание и регистрация](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/datastream/DataStream.java#L781-L846).

Логическая transformation не равна физическому оператору. `union` создаёт `UnionTransformation`, а изменение partitioner — `PartitionTransformation`, без отдельной регистрации физического рабочего оператора. Базовый `Transformation` прямо описывает, что union и partitioning превращаются в свойства рёбер. `StreamGraphGenerator` использует виртуальные узлы; при добавлении downstream-ребра `StreamGraph.addEdgeInternal` рекурсивно разрешает исходный физический узел, переносит output tag/partitioner/exchange mode и создаёт настоящее ребро. Это существенно для собственной IR: число пользовательских шагов, число узлов графа и число исполняемых task не обязаны совпадать. [Transformation: логические операции](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/dag/Transformation.java#L49-L108), [виртуальные рёбра](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamGraph.java#L754-L972).

Причинная последовательность запуска такова:

1. `environment.addOperator` пополняет список transformations. `execute(String)` сохраняет его копию и вызывает `getStreamGraph()`; имя задания накладывается на уже построенный граф.
2. `getStreamGraph(boolean)` строит граф и только после успешного построения при `true` очищает список. Генератор получает отдельную копию списка, чтобы новые регистрации не вмешались в построение. Пустая topology отвергается до генерации.
3. `StreamGraphGenerator.generate` создаёт `StreamGraph`, определяет режим, затем переводит transformations. `alreadyTransformed` — `IdentityHashMap`: общий upstream-объект не переводится заново из-за повторного ребра. `translate` сначала рекурсивно переводит inputs, получает их node IDs, определяет slot-sharing group и вызывает конкретный `translateForBatch` либо `translateForStreaming`.
4. Выбор translator идёт по точному `transform.getClass()` в registry. Перед ним `transform.getOutputType()` принудительно обнаруживает `MissingTypeInfo`. Неподдержанная transformation без специального wrapper-пути заканчивается `IllegalStateException`.
5. При добавлении физического узла `StreamGraph` выбирает класс task invokable, создаёт входные/выходные `TypeSerializer` из `TypeInformation` и `SerializerConfig`, настраивает type-configurable factory. Обычный one-input путь использует `OneInputStreamTask`, новый source — `SourceOperatorStreamTask`, two-input и multi-input имеют свои task-классы.
6. `StreamGraph.getJobGraph(...)` передаёт граф в `StreamingJobGraphGenerator.createJobGraph(...)`. Тот вычисляет стабильные hashes, строит chains и `JobVertex`, соединяет их datasets/`JobEdge`, устанавливает ресурсы и доли памяти и дожидается сериализации operator coordinators и stream configs.
7. `executeAsync(StreamGraph)` выбирает `PipelineExecutor` по deployment target и передаёт ему **StreamGraph**; локальная конверсия в JobGraph не является обязательным непосредственным вызовом из environment. Метод ждёт future успешной подачи, сообщает listeners и присоединяет `JobClient` к collect-итераторам. `execute(StreamGraph)` дополнительно ждёт результат только в attached-режиме; detached-режим возвращает отдельный результат с job ID.

Источники последовательности: [environment: запуск](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/environment/StreamExecutionEnvironment.java#L1838-L1901), [submission и graph lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/environment/StreamExecutionEnvironment.java#L1988-L2093), [registry/генерация](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamGraphGenerator.java#L162-L302), [перевод](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamGraphGenerator.java#L463-L640), [serializers/task classes](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamGraph.java#L540-L725), [JobGraph conversion](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamingJobGraphGenerator.java#L187-L275).

Название `executeAsync` здесь не означает, что метод немедленно возвращает future: он блокируется на `CompletableFuture<JobClient>.get()` до завершения submission. Это отдельная граница от ожидания полного результата задания. Ошибка submission снимает оболочку `ExecutionException`, уведомляет `onJobSubmitted(null,error)` и превращается во `FlinkException`; ошибка ожидания результата уведомляет `onJobExecuted` и перебрасывается. Отдельный повторный запуск в `execute(String)` предусмотрен для повреждённого cluster dataset: кэш инвалидируется, исходные transformations переводятся повторно, затем задание запускается ещё раз. Это конкретный retry-путь, а не универсальное подавление ошибок. [Submission](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/environment/StreamExecutionEnvironment.java#L1988-L2010), [повтор без кэша](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/environment/StreamExecutionEnvironment.java#L1838-L1858).

## Что именно меняет физический план

Режим вычисления — проверяемое свойство графа. `BATCH` вместе с unbounded source отвергается. `AUTOMATIC` выбирает batch только при отсутствии unbounded source среди transformations и их транзитивных предков. Batch-путь отключает checkpointing в копии checkpoint config, выбирает batch state backend/timer service при соответствующей настройке и проверяет необходимость sorted inputs. Для fine-grained batch resources генератор принудительно выбирает blocking exchanges из-за известной опасности resource deadlock с pipelined edges. [Выбор режима и ограничения](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamGraphGenerator.java#L336-L455).

Chaining не следует автоматически из соседства двух transformations. Нужны совместимость slot-sharing group, chaining strategies, parallelism/max parallelism и partitioner/exchange mode. В обычном пути downstream должен иметь одно входное ребро. Дополнительная проверка не позволяет chained input объединять через union в одной input position. Forward edge при совместимых условиях может войти в chain; batch exchange препятствует этому. Новый source может стать chained input при `HEAD_WITH_SOURCES`; legacy source не может быть head для yielding operator factory. Это независимые от Python generator `yield` внутренние правила Java scheduler/mailbox. [Условия chaining](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamingJobGraphGenerator.java#L1730-L1895).

`createChain` разделяет chainable/non-chainable outputs и рекурсивно группирует операторные configs. Для head создаётся `JobVertex`; прочие configs входят в transitive chained task configs, каждый оператор сохраняет собственный OperatorID. `createJobVertex` получает JobVertexID из hash head-узла, сохраняет пары сгенерированного/пользовательского OperatorID для членов chain, назначает task invokable, parallelism и max parallelism. Физические non-chained соединения превращаются в POINTWISE либо ALL_TO_ALL datasets в зависимости от partitioner. Поэтому один JobVertex может содержать несколько пользовательских функций, но их state identity не исчезает внутри общей task. [Построение chain](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamingJobGraphGenerator.java#L629-L807), [JobVertex и configs](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamingJobGraphGenerator.java#L1074-L1289), [datasets](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamingJobGraphGenerator.java#L1585-L1648).

До построения проверяются несовместимые комбинации checkpointing: некоторые iterative/custom-partitioner случаи с unaligned checkpoints, InputSelectable operators и конфликт pause-until-first-checkpoint с отключением checkpoints во время backlog. Это проверки конкретного плана. Они не позволяют считать флаг exactly-once самостоятельной гарантией для произвольного источника/выхода. [Pre-validation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamingJobGraphGenerator.java#L502-L551).

## Типовая информация, identity и формат состояния

`TypeInformation` описывает тип на уровне планирования: arity, число рекурсивно развёрнутых логических полей, key/sort-key пригодность и фабрику serializer. Коллекция или массив считаются одним полем, поскольку единая схема должна подходить экземплярам разной длины. Это не сохранённый checkpoint schema fingerprint. `TypeInformation.of(Class)` не восстанавливает потерянные generic parameters: при невозможности extraction пользователю нужен `TypeHint`. [TypeInformation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeinfo/TypeInformation.java#L34-L177), [generic hint](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeinfo/TypeInformation.java#L198-L234).

Тип transformation можно уточнить, пока он ещё не использован. Успешный `getOutputType()` устанавливает `typeUsed=true`; после этого `setOutputType` выбрасывает `IllegalStateException`. Для `MissingTypeInfo` getter сначала бросает `InvalidTypesException`, объясняя `returns(...)`/`ResultTypeQueryable`, и до установки `typeUsed` не доходит. Поэтому корректнее говорить о фиксации после успешного чтения типа, а не после любого вызова getter. [Type freeze](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/dag/Transformation.java#L551-L593).

Есть разные идентификаторы: `Transformation.id` выдаёт статический process-local counter; `uid` задаётся пользователем для сохранения operator identity между submissions; пользовательский 32-символьный hex hash — отдельный механизм. Ресурсы, managed-memory weights и max parallelism тоже хранятся в logical transformation, но не становятся семантикой самой пользовательской функции. Для Ariadne отсюда следует необходимость явно различать identity логического шага, физической группы исполнения и попытки запуска; это вывод для проектирования, а не уже принятое изменение ADR. [Identity](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/dag/Transformation.java#L115-L193), [UID/hash](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/dag/Transformation.java#L394-L458).

`TypeSerializer` задаёт не только `serialize/deserialize`. Контракт включает глубокое копирование объекта, вариант с reuse, копирование записи между binary views, immutable flag, создание экземпляра, фиксированную/переменную длину и `duplicate`. Stateful serializer может быть небезопасен между потоками; `duplicate` нужен для разделения экземпляров, stateless serializer может вернуть себя. Reuse не гарантирован. Snapshot обязан содержать всё, что влияет на формат, чтобы восстановить старый reader и проверить новый. [Serializer contract](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/TypeSerializer.java#L28-L196).

Направление schema compatibility в этом pin: **new snapshot.resolveSchemaCompatibility(old snapshot)**. Возвращаются четыре различных результата:

| Результат | Требуемое действие по контракту |
| --- | --- |
| compatible as is | Новый serializer читает существующие bytes без изменения |
| compatible after migration | Старый serializer читает старые bytes, значение переводится и записывается новым serializer |
| compatible with reconfigured serializer | Следует использовать возвращённый сконфигурированный serializer вместо исходного нового |
| incompatible | Продолжение восстановления этим serializer невозможно |

`getReconfiguredSerializer` защищён проверкой результата; это не nullable-поле для произвольного использования. Snapshot имеет собственную версию формата и nullary constructor. Общая запись snapshot сохраняет имя его класса, version, затем payload; чтение сначала создаёт snapshot-класс с classloader, читает version и передаёт его в `readSnapshot`. Совместимость формата snapshot и совместимость bytes пользовательского состояния — связанные, но разные задачи. [Snapshot factory/wire format](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/TypeSerializerSnapshot.java#L66-L135), [версионированная запись](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/TypeSerializerSnapshot.java#L176-L203), [четыре результата](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/TypeSerializerSchemaCompatibility.java#L43-L183).

В этом pin есть дополнительный метод `newSnapshot.migrate(oldSnapshot,value)`. Значение уже десериализовано старым serializer. По умолчанию метод возвращает его без изменения. Композитная миграция не применяется рекурсивно автоматически: реализация должна сама разобрать составное значение и вызвать nested snapshots. Исходный persisted snapshot предпочтительнее повторно полученного из восстановленного serializer: такой round trip не всегда воспроизводит записанную схему. Это важное ограничение для переноса идей в Ariadne: наличие версии на контейнере или callback migration не доказывает корректность вложенного изменения layout. [Миграция значения](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/TypeSerializerSnapshot.java#L137-L170).

## Пользовательские callbacks и Python output iterable

Java `MapFunction.map(value)` возвращает ровно одно значение; `FlatMapFunction.flatMap(value,Collector)` выдаёт от нуля до многих через collector. Оба callback могут бросить exception: контракт говорит о failure операции и возможном recovery. `RichFunction` добавляет `open`, `close` и runtime context; исключение в lifecycle не превращается в обычную запись потока. Runtime выбирает failover. Описанный интерфейс не доказывает, что `close` гарантирован при каждом варианте failed initialization: это требуется проверять по реализации task/operator lifecycle. [Map](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/functions/MapFunction.java#L25-L56), [FlatMap](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/functions/FlatMapFunction.java#L26-L56), [Rich lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/functions/RichFunction.java#L26-L116).

В Python process execution payload функции распаковывается `pickle.loads`. Stateless wrapper устанавливает timestamp и watermark в context перед `process_element`/одним из co-process callbacks, затем передаёт возвращённый iterable в `_emit_results`. Stateful wrapper дополнительно устанавливает текущий user key и backend key до callback; `on_timer` получает timestamp, key и time domain. Для обычного CoProcessFunction предусмотрено отсутствие `on_timer`: тогда возвращается пустой tuple. WINDOW branch создаёт `WindowOperator` из assigner, trigger, lateness, state descriptor и internal window function; устанавливает namespace coder и делегирует record/timer callbacks. [Stateless extraction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/process/operations.py#L142-L260), [stateful и window extraction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/process/operations.py#L263-L473).

`RunnerInputHandler` разбирает envelope `[timestamp, watermark, data]`, обновляет watermark, вызывает callback и перечисляет его outputs. `TimerHandler` разбирает `[timerType,watermark,timestamp,key,serializedNamespace]`, восстанавливает namespace и выбирает event-time или processing-time callback; неизвестный timer type бросает exception. `_emit_results` не интерпретирует generator как командный протокол: для каждого элемента iterable создаётся `Row(timestamp,watermark,result)`. При side outputs tuple с `OutputTag` превращается в tag ID и соответствующую Row, прочие значения идут в default tag. `yield from` здесь перечисляет результаты одного callback. Это не основание отождествлять PyFlink с протоколом Ariadne, где пользовательский generator может иметь иные управляющие значения. [Envelope/outputs](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/process/input_handler.py#L33-L132).

## Beam process boundary и её lifecycle

Python Beam transform factory регистрирует DataStream `PAR_DO`, читает `do_fn.urn` и protobuf `UserDefinedDataStreamFunction`, выбирает stateless/stateful operation. Фабрика создаёт `RemoteOperatorStateBackend`, при keyed функции — `RemoteKeyedStateBackend` с coder и cache-настройками, полученными из protobuf; `factory.state_handler` является transport-facing зависимостью. `PYFLINK_CYTHON_ENABLED` выбирает fast либо slow Beam implementation. Следующие наблюдения относятся к полностью прочитанному slow-пути; fast-путь ещё требует собственного чтения. [URN factory и backends](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_operations.py#L18-L39), [DataStream factory](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_operations.py#L131-L236).

В slow `FunctionOperation` создаёт output processors, создаёт internal operation и вызывает `operation.open()` уже в конструкторе. `process` обходит входные values, передаёт callback iterable в network encoder либо промежуточному consumer; для side outputs выбирает processors по tag. Есть отдельные branch для bundle operations и async operation, поэтому синхронное перечисление не следует распространять на все PyFlink-функции. Network output кодирует iterable в output stream и может flush; intermediate output передаёт iterable через `WindowedValue.with_value` следующему consumer. `finish` вызывает `operation.finish`, где DataStream operation обновляет gauges и коммитит operator backend; stateful operation дополнительно коммитит keyed backend. Это commit state-кэшей на данной границе, а не доказательство завершённого глобального checkpoint. [Slow lifecycle/output](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_operations_slow.py#L47-L170), [state finish](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/process/operations.py#L53-L139).

`teardown` последовательно вызывает internal `close`, затем `close` всех output processors. В этом методе нет `try/finally` вокруг пользовательского close: если он бросает, последующие processor closes здесь не выполняются. Это наблюдение о локальном control flow, не проверенное запуском и не утверждение об отсутствии внешней очистки Beam. В Java graph conversion собственный serialization executor, напротив, закрывается через `finally` и при исключении. [Python teardown](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_operations_slow.py#L114-L132), [Java executor cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/graph/StreamingJobGraphGenerator.java#L144-L169).

Таймер Python process backend не является локальным sleeping coroutine. `InternalTimerServiceImpl._set_timer` сериализует namespace, формирует Row с operation type, timestamp и current backend key, помещает её в `Beam userstate.Timer.user_key` и отправляет coder-ом в output stream. Public `TimerServiceImpl` использует namespace `None`. Non-keyed timer service разрешает чтение текущего времени/watermark, но registration и deletion бросают exception. Legacy implementation рядом копит timer operations в OrderedDict и прямо помечена TODO перехода к новой реализации; смешивать эти два пути нельзя. [Timer transport](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/process/timerservice_impl.py#L78-L173), [non-keyed failure](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/process/timerservice_impl.py#L176-L203).

## Fast/Cython transport и boot Python worker

Теперь полностью прочитаны все15 файлов `fn_execution/beam`, включая `.pyx`/`.pxd`, а также365 строк `operation_utils.py`. Fast `FunctionOperation` выбирает network input wrapper либо intermediate iterator и сохраняет отдельные branch для side outputs, bundle operation, async operation и обычного callback. Stateful timer path передаёт `timer_data.user_key` внутренней operation, затем направляет main/side results теми же output processors. Internal operation открывается в конструкторе; teardown последовательно вызывает user/internal close и closes output processors без локального finally, как slow path. Cython ускорение меняет способ доступа к данным, но не превращает callback iterable в scheduler-control protocol. [Fast branches](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_operations_fast.pyx#L112-L215), [timer output](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_operations_fast.pyx#L268-L297).

Coder bridge регистрирует `flink:coder:v1`, строит coder из `CoderInfoDescriptor` и выбирает field либо length-prefix wrapper. Beam LENGTH_PREFIX регистрация заменена pass-through wrapper: длину уже обрабатывает вложенный Flink coder, второй префикс добавлять нельзя. Fast field bridge переносит bytes в Beam output buffer; top-level stream читает/пишет variable-length framing. Закрытие отменяет PeriodicThread через Event; `cancel` этого thread не делает join. Эти transport mechanisms не запускают пользовательский callback по таймеру. [Coder registration](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_coders.py#L27-L80), [framing/flush](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_stream_fast.pyx#L28-L124), [PeriodicThread lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/utils/operation_utils.py#L335-L365).

Loopback отправляет StartWorker в локальный worker-pool service. Сам service запускает SdkHarness в RPC thread, использует ref-count для shared process environment: первый worker добавляет PYTHONPATH/меняет cwd, последний возвращает sys.path/cwd в finally вокруг harness. `StopWorker` в этом файле пустой. Provision RPC и parsing options находятся раньше данного finally, поэтому нельзя описывать этот локальный блок как безусловную очистку всех ошибок старта; recovery внешнего сервиса этим чтением не доказан. [Boot branch](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_boot.py#L76-L123), [loopback lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_worker_pool_service.py#L89-L189).

Далее stdout/stderr направляются в logging, print буферизуется до newline; `custom_print.close` стоит после обычного возврата Beam main без finally. Для собственного engine существенна явная фиксация единиц cache budget и областей process-global изменения среды, а не копирование этих monkeypatch. [Cache adaptation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_sdk_worker_main.py#L21-L62), [stdio lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/beam/beam_sdk_worker_main.py#L65-L105).

## Java↔Python: буферизация, watermark и владение завершением

Java-сторона process boundary строит runner input Row `[timestamp,watermark,element]`, сериализует её специальным Python type-info converter и отправляет bytes в runner. Затем увеличивает счётчик bundle, при необходимости завершает bundle по размеру и выгружает накопленные результаты. Output — tuple `(tag,bytes,length)`; Java выбирает main/side serializer, десериализует Row и передаёт в timestamped collector. `endInput` вызывает finish bundle. [Java envelope](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/operators/python/process/AbstractExternalOneInputPythonFunctionOperator.java#L98-L163).

`BeamDataStreamPythonFunctionRunner` строит внутреннюю последовательность Beam `PAR_DO` transforms для объединённых Python functions. Только head получает исходный function URN и timer family; следующие функции идут stateless-путём. Последние main/side outputs проходят отдельные `REVISE_OUTPUT` transforms. Поле Beam timer family time domain всегда задаётся EVENT_TIME с прямым комментарием, что оно не используется: реальная категория Flink timer передаётся внутри пользовательского payload. Поэтому чтение одного protobuf поля не позволяет заключить, что processing-time timers потеряны. [Beam UDF graph](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/BeamDataStreamPythonFunctionRunner.java#L113-L218).

`AbstractPythonFunctionOperator` завершает bundle по count, processing-time timeout, `finish`, pre-checkpoint barrier и end-of-input пути подкласса. Watermark не должен обгонять уже переданные Python записи. При незавершённом bundle обычный watermark удерживается в `bundleFinishedCallback`; после финализации вызываются timer advancement и downstream watermark. `Long.MAX_VALUE` watermark сначала принудительно завершает bundle. Advancement дренирует полученные от Python timer registrations, продвигает Java timer manager и снова завершает bundle, пока timer callbacks создают работу. В batch смена current key аналогично дренирует регистрацию до перехода, чтобы callback старого ключа не вернул backend на уже завершённый key. [Bundle/watermark](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/operators/python/AbstractPythonFunctionOperator.java#L124-L245), [timer advancement](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/operators/python/AbstractPythonFunctionOperator.java#L282-L317).

При финализации Java operator запускает `runner.flush` на отдельном executor, одновременно продолжает забирать результаты, затем проверяет сохранённое исключение flush. `finally` flush-потока отправляет нулевой marker через `notifyNoMoreResults`, чтобы `takeResult` не завис после последнего output. Счётчик записей и callback обновляются только после успешного завершения/drain. Эта пара producer/consumer объясняет, почему простой синхронный вызов Python-функции не описывает реализацию. [Flush и drain](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/operators/python/process/AbstractExternalPythonFunctionOperator.java#L95-L137).

В `BeamPythonFunctionRunner.open` создаются result queue и state request handler, открывается process environment manager, строятся portable pipeline options и executable stage. При managed memory с долей `(0,1]` несколько операторов в slot используют `PythonSharedResources` через собственные resource leases; иначе runner владеет собственным JobBundleFactory. Shared process — это не отсутствие отдельного operator lifecycle. `process` и `processTimer` выбирают input receiver под monitor runner и вызывают receiver снаружи monitor. Timer registrations из callback добавляются в synchronized список и планируются в main mailbox; явный `drainUnregisteredTimers` закрывает ordering gap перед key/watermark advancement. [Open/resources](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/BeamPythonFunctionRunner.java#L274-L372), [record/timer dispatch](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/BeamPythonFunctionRunner.java#L429-L499), [mailbox registration](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/BeamPythonFunctionRunner.java#L1133-L1147).

Завершение имеет явное владение, а не только boolean «closed»:

1. `flush` под monitor либо забирает активный RemoteBundle в `BundleCloseOperation`, либо получает уже существующую operation. Активные receiver-ссылки очищаются. Только владелец вызывает `RemoteBundle.close`, остальные ждут того же completion future. Новый bundle запрещён, пока предыдущий ещё закрывается.
2. Нормальный `close` единожды начинает close, завершает bundle, затем через вложенные `finally` закрывает resources, state handler и shutdown hook; конкурирующий close ждёт close completion.
3. `cancel` отмечает cancelRequested и, если flush ещё не забрал bundle, передаёт его закрытие отдельному executor. Если close bundle уже принадлежит flush-потоку, cancel не пытается закрыть его второй раз и не ждёт этот callback. Runner освобождает свой lease, затем закрывает/gates state handler до удаления backend. Другие leases продолжают владеть общим worker.
4. Resource disposal сам имеет одно completion future. Если final lease уже удаляется другим потоком, cancel всё же ждёт завершения **disposal** через join: slot SharedResources lock должен быть освобождён до завершения task cleanup. Поэтому «cancel не ждёт bundle flush» не означает «cancel никогда не ждёт». Ошибка disposal передаётся ожидающему.
5. Первый data RPC failure сохраняется, кладёт marker в result queue, прерывает поток закрытия bundle и вызывает `environment.failExternally`. `takeResult` проверяет failure до и после blocking take; `pollResult`, начало bundle и finish bundle также проверяют её. Поздние callbacks после cancellation/resource close игнорируются.

Источники: [close/cancel](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/BeamPythonFunctionRunner.java#L374-L427), [flush/failure](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/BeamPythonFunctionRunner.java#L501-L614), [ownership/resource disposal](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/BeamPythonFunctionRunner.java#L616-L800).

Для Ariadne это полезный пример собственной протокольной обязанности при process isolation: отдельно определить владельца активного callback, owner отменённой фоновой работы, границу блокирования новых state requests и срок жизни shared worker. Конкретные Java классы не задают обязательную реализацию Python engine; переносить следует доказанные инварианты владения и ordering. Утверждение о «быстрой отмене» без разделения bundle completion и final shared-resource disposal было бы слабее фактического контракта этого pin.

## Python state: key/namespace, cache и Java RPC

Полностью прочитаны `internal_state.py`133 строки, `state_impl.py`1391 строк, все9 Java классов Beam state package1290 строк и их Python/Java tests1272 строки. Python internal hierarchy добавляет namespace selection и merge к пользовательским state interfaces. `RemoteKeyedStateBackend` держит wrapper на state name, а внутренний cache индексируется `(state name,encoded key,encoded namespace)`. При изменении key старые internal states либо переходят в LRU с commit при eviction, либо немедленно commit-ятся при cache size0, затем wrapper сбрасывает namespace/internal reference. Это сохраняет pending clear до ухода со старого key; commit также обходит текущие и cached states. `update(None)` для value state очищает bag и не добавляет None; у map запись с None отличается от отсутствующего key через отдельный exists flag. [Namespace hierarchy](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/internal_state.py#L32-L85), [value update](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L157-L178), [map contains](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L777-L834), [key/cache lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L1092-L1205).

TTL меняет допустимость **кэширования конкретного state**. NeverReturnExpired отключает read/write cache, OnReadAndWrite при разрешённом expired visibility оставляет write cache, но отключает read cache. Backend создаёт отдельный `GlobalCachingStateHandler(StateCache(0),same underlying)` и map handler для таких reads, сохраняя cache других states. Иначе повторное чтение в том же bundle могло бы вернуть устаревший cached value либо пропустить продление TTL на Java-стороне. `merge_namespaces` сначала commit-ит sources/target, удаляет их cache entries и отправляет специальный bag append с marker `merge_namespaces`; Java handler десериализует namespaces и вызывает InternalListState.mergeNamespaces. [TTL cache policy](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L118-L154), [per-state uncached handlers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L985-L999), [namespace merge](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L1213-L1248), [Java merge](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/state/BeamBagStateHandler.java#L68-L96).

Map RPC использует Beam MultimapSideInput как envelope, потому что используемый Beam proto не даёт нужный MapState contract. Python state descriptor вместе с TTL кодируется в base64 side-input-id, namespace — в window, current key — в key. Broadcast использует другой envelope MultimapKeysSideInput без keyed key. Java stores восстанавливают descriptor с префиксом `python-state-`; значения Flink backend остаются byte arrays, Python field coders работают внутри этих bytes. Один state name не разрешено использовать одновременно для list и map, Python дополнительно проверяет coder equality при повторной регистрации. Это внутренний transport protocol, а не утверждение, что broadcast state является обычным side input пользовательского графа. [Python envelopes](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L1136-L1165), [bag envelope](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L1250-L1261), [Java key/descriptor](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/src/main/java/org/apache/flink/streaming/api/runners/python/beam/state/BeamKeyedStateStore.java#L89-L140), [operator envelope](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/state_impl.py#L1343-L1378).

`is_empty` не сводится к `next(items())`: Python сначала учитывает buffered inserts/deletions/clear, затем при необходимости отправляет CHECK_EMPTY_EXCLUDING_KEYS со списком локально удалённых keys. ## Composition serializer snapshots и версии формата

Полностью прочитанные CompositeTypeSerializerSnapshot, NestedSerializersSnapshotDelegate и CompositeTypeSerializerUtil показывают, что версия transport envelope, версия composite base, версия outer snapshot и версия nested delegate — разные слои. Base version3 пишет outer magic/version/payload и затем nested delegate magic/version/count/snapshots; legacy read versions≤2 обрабатываются без outer magic. Делегат проверяет собственный magic/version и восстанавливает nested serializers в сохранённом порядке. Serializer snapshot не является одним Java-serialized объектом со случайно доступным serialVersionUID. [Composite format/read](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/CompositeTypeSerializerSnapshot.java#L55-L172), [nested format](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/NestedSerializersSnapshotDelegate.java#L104-L139).

Composite compatibility сначала отвергает изменение числа nested snapshots. Затем учитываются outer и каждый nested result: incompatibility доминирует, далее migration, затем reconfiguration, иначе as-is. Reconfiguration требует собрать новый outer serializer с массивом восстановленных/reconfigured nested serializers; intermediate result не разрешает получить final result до этой сборки. Default outer check оставляет deprecated fallback, который восстанавливает new serializer и вызывает старый outer hook; subclass с дополнительным outer configuration обязан переопределить write/read/compatibility. Эти проверки выбирают стратегию чтения, но сами не выполняют рекурсивную миграцию каждого значения. [Arity/outer check](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/CompositeTypeSerializerSnapshot.java#L178-L209), [precedence](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/CompositeTypeSerializerSnapshot.java#L409-L437), [nested aggregation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/CompositeTypeSerializerUtil.java#L88-L135), [intermediate constraint](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-core/src/main/java/org/apache/flink/api/common/typeutils/CompositeTypeSerializerUtil.java#L191-L217).

## Полный Python callback surface и cleanup окна

`pyflink/datastream/functions.py` прочитан целиком. Его `SourceFunction`/`SinkFunction` наследуют `JavaFunctionWrapper`: принимают JavaObject или имя Java-класса, которое создаётся через gateway. В этом файле нет Python `SourceFunction.run`-generator callback. В отличие от него Python `flat_map(value)` прямо документирован как generator; `MapFunction.map` возвращает одиночное значение. `WindowFunction.apply(key,window,inputs)` и `ProcessWindowFunction.process(key,context,elements)` принимают iterable содержимого окна и возвращают iterable outputs. Это разные пользовательские contracts, объединённые внутренним output enumeration, но не единая «yield-based source model». [Java source/sink adapters](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/datastream/functions.py#L579-L619), [flat-map callback](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/datastream/functions.py#L275-L304), [window callbacks](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/datastream/functions.py#L1025-L1132).

Process/keyed/broadcast contexts имеют срок жизни одного callback, сохранять их нельзя. Python interfaces иногда содержат широкие формулировки о timer registration, поэтому ограничения проверены по реализации: non-keyed timer service бросает exception, keyed wrappers устанавливают backend key до callback. Broadcast side получает read/write view broadcast state; regular side — read-only view, а keyed regular side дополнительно получает keyed state/timer service. `applyToKeyedState` в Python keyed broadcast context явно не поддержан. [Context lifetime](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/datastream/functions.py#L654-L740), [broadcast distinction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/datastream/functions.py#L1599-L1721).

Полностью прочитанный Python `WindowOperator` разделяет window contents, trigger state и пользовательский per-window state. Record присваивается окнам, поздние окна пропускаются, содержимое добавляется в state namespace окна, trigger решает FIRE/PURGE, регистрируется cleanup timer. FIRE вызывает internal window function; PURGE очищает contents, но не является полным lifecycle cleanup. Event/processing timer callbacks восстанавливают namespace, вызывают trigger, могут выдать результаты и при cleanup timestamp вызывают `clear_all_state`. Эта функция последовательно очищает contents, вызывает trigger.clear, затем пользовательский window clear и удаляет окно из merging set. У `ProcessWindowFunction.window_state` документация прямо требует реализовать `clear`; default пустой. При merging windows доступ к per-window user state запрещён исключениями. [Record/trigger path](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/window/window_operator.py#L345-L425), [timer/cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/window/window_operator.py#L427-L564), [user cleanup obligation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/datastream/functions.py#L1090-L1132), [merging restriction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-python/pyflink/fn_execution/datastream/window/window_operator.py#L58-L104).

## Примитивные и временные serializers: null — часть framing

Полностью прочитаны TypeSerializerSingleton, все восемь boxed primitive serializers, StringSerializer, Date/SqlDate/SqlTime/SqlTimestamp, Instant/LocalDate/LocalTime/LocalDateTime serializers, включая вложенные snapshots. Singleton относится к stateless serializer instance; Date values при этом mutable и копируются, а immutable boxed primitives/String/java.time types могут возвращаться из copy без новой оболочки. Primitive serializers используют fixed-width DataView operations; String делегирует StringValue format. Date/SQL date/time записывают Long.MIN_VALUE вместо null, то есть это значение зарезервировано и не roundtrip-ится как обычное время.
