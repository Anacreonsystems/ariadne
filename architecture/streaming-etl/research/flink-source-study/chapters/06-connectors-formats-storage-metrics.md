## Источник: разделение I/O и выдачи записей

`SourceReaderBase` соединяет `SplitFetcherManager`, `RecordEmitter` и `FutureCompletingBlockingQueue<RecordsWithSplitIds<E>>`. Карта `splitStates` хранит изменяемое состояние каждого назначенного split, а `snapshotState` переводит именно эту карту в список неизменяемых `SplitT`. Прочитанный из внешней системы batch сам по себе не обновляет эту карту: `pollNext` достаёт запись batch и вызывает `recordEmitter.emitRecord(record, currentSplitOutput, currentSplitContext.state)`. Таким образом, наблюдаемая здесь граница checkpoint progress проходит через выдачу записи в mailbox-пути, а не через завершение фонового чтения. Конкретное обновление offset определяется реализацией emitter и пока не обобщается на все коннекторы. [Поля и конструктор](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L78-L170), [выдача](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L173-L260), [snapshot и назначение](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L347-L374).

Без rate limiter один вызов `pollNext` выдаёт одну богатую входную запись и возвращает `MORE_AVAILABLE`, даже когда следующей записи может не быть. Это намеренная ложноположительная доступность ради отсутствия дополнительной проверки на каждой записи. Один emitter может выдать несколько конечных записей. В режиме rate limiting обёртка считает именно вызовы `SourceOutput.collect`, передаёт их число в `rateLimiter.acquire` и сбрасывает счётчик окна. Если permit future ещё не завершён, этот метод также возвращает `MORE_AVAILABLE`; `isAvailable` данного класса выбирает только текущий fetch либо queue future. Поэтому по этому файлу нельзя утверждать, что rate limiter сам переводит runtime в ожидание своего future. [Rate limiting](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L219-L259), [availability](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L340-L345), [счётчик конечных записей](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L551-L608).

Batch последовательно переключает split через `nextSplit`. Для неизвестного split срабатывает `checkState`; для известного создаётся или переиспользуется отдельный output. При исчерпании batch reader удаляет только объявленные `finishedSplits` из карты, освобождает их outputs, вызывает `onSplitFinished` и затем `fetch.recycle`. EOF evaluator подавляет сам EOF-record и последующие записи этого split и асинхронно запрашивает удаление split у fetcher manager. Это отличается от немедленного удаления checkpoint state: его удаляет обработка finished-split batch. [Переходы и recycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L282-L337), [EOF output](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L483-L539).

## Fetcher: управление, сообщения и срок жизни ресурсов

`SplitFetcher` — `Runnable` с одним `SplitReader`, fallback `FetchTask`, очередью управляющих задач и картой назначенных split. Под lock он выбирает управляющую FIFO-задачу, иначе fetch при наличии split, иначе ждёт condition; саму задачу выполняет вне lock, позволяя другому потоку вызвать её `wakeUp`. Невыполненная управляющая задача ставится обратно в голову очереди. Add/remove/pause-resume ставят задачи, а не вызывают внешний reader непосредственно из mailbox. `SingleThreadMultiplexSourceReaderBase` выбирает `SingleThreadFetcherManager`; его реализация лениво создаёт fetcher, ставит add до запуска, затем переиспользует первый активный fetcher. После удаления idle fetcher следующее назначение создаёт новый reader, а старый ещё может ожидать recycle. Контракт допускает последовательное чтение файлов либо multiplex нескольких подписок одним reader. [Реализация manager](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SingleThreadFetcherManager.java#L104-L128). [Цикл fetcher](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L166-L255), [асинхронные задачи](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L258-L327), [база multiplex reader](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SingleThreadMultiplexSourceReaderBase.java#L35-L104).

`FetchTask` сохраняет `lastRecords`, если wakeup помешал handover. Callback finished splits вызывается только после успешной постановки batch в queue; затем ссылка обнуляется. Wakeup сначала устанавливает флаг, затем будит либо `SplitReader`, либо producer, ожидающий свободного места queue. Поэтому callback не сообщает об окончании split раньше передачи последних записей consumer. [Полный алгоритм](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/FetchTask.java#L54-L107).

Штатное выключение idle fetcher учитывает срок жизни памяти batch: fetcher кладёт пустой синхронизационный batch и ждёт `recordsProcessedLatch`; только `recycle` этого batch снимает latch, после чего закрывается `SplitReader`. Обычный `shutdown(false)` снимает latch сразу. Manager удаляет idle fetcher из активной карты ещё до завершения закрытия ресурса, поэтому отдельно считает `fetchersToShutDown`. Его `close(timeout)` запрещает создание новых fetcher, вызывает shutdown активных, запускает drain/recycle очереди и ждёт завершения executor в пределах общего deadline. При истечении времени этот код пишет warning; он не доказывает принудительную остановку внешнего I/O. [Shutdown fetcher](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L126-L164), [варианты shutdown](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L337-L368), [manager lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L246-L347).

Ошибки I/O сохраняются в `AtomicReference`: первая становится основной, последующие добавляются как suppressed. Manager завершает availability future, чтобы разбудить consumer; `checkErrors` повторно выбрасывает сохранённую причину на reader-пути. `END_OF_INPUT` выдаётся после `notifyNoMoreSplits`, отсутствия активных fetcher и пустой queue, с заключительной проверкой ошибки. Это несколько условий жизненного цикла, а не вывод из одного `fetch()==EOF`. Executor фактически создаётся через `newCachedThreadPool`; комментарий про два потока не описывает вызов конструктора в этой ревизии. [Ошибка и executor](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L151-L191), [повторное выбрасывание](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L349-L355), [условия конца](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L433-L448).

## Handover queue: backpressure и учёт producer

`FutureCompletingBlockingQueue` ограничивает количество элементов queue. Для reader это количество batch, а не байтов или конечных записей; отдельный batch и `lastRecords` могут удерживать память сверх числа слотов queue. Producer блокируется в `put` при заполнении; consumer использует неблокирующий `poll` и future доступности. `notifyAvailable` может завершить future без данных. После пустого `poll` или удаления последнего элемента future заменяется новым незавершённым. Consumer обязан повторно проверить данные/условия и получить актуальный future; completed future не является обещанием ненулевой записи. [Контракт](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L43-L77), [put/poll](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L198-L274).

Graceful wakeup сохраняется как sticky flag по producer id, включая wakeup до первого блокирования. Состояние создаётся только при wakeup или ожидании и удаляется через `releaseProducer` после окончательного выхода producer. Сам номер fetcher монотонно увеличивается; cleanup препятствует накоплению condition для всех исторических fetcher. Удалять состояние во время `put` нельзя: producer мог уже получить signal и исчезнуть из FIFO ожидающих, но ещё не захватить lock. Отдельный `waitingPutters` покрывает весь `await`, а `releaseProducer` отказывается удалять такую запись. Shutdown hook manager вызывает release после выхода run loop. [Wakeup и release](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L355-L420), [ожидание](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L449-L530), [hook](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L253-L275).

Полностью прочитан `FutureCompletingBlockingQueueTest` (492 строки), тесты не запускались. Они задают следующие проверяемые инварианты: wakeup первого producer не оставляет следующего без signal; release идемпотентен и адресен; release во время parked put и в окне signal→reacquire сохраняет sticky wakeup; interrupt снимает отметку waiting; опустошение queue сбрасывает availability; default capacity равна двум; `AVAILABLE` совпадает с runtime singleton. Последний тест проверяет reflection fast path, а не семантику всех вариантов classloader. [Wakeup и cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/test/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueueTest.java#L110-L340), [capacity и availability](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/test/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueueTest.java#L409-L491).

## Асинхронный sink: mailbox, повторные записи и checkpoint

`AsyncSinkBase` поддерживает destination с асинхронным клиентом и writer state. Его собственный контракт — at-least-once; retry может менять порядок. `AsyncSinkWriter` хранит преобразованные `RequestEntryT`, а не исходные `InputT`: частичный ответ destination часто позволяет восстановить failed request, но не исходное событие. `ElementConverter.open` выполняется до восстановления буфера. Generic `close` пуст; закрытие клиентского pool/socket остаётся ответственностью конкретного sink. [Base contract](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/AsyncSinkBase.java#L32-L52), [request buffer и конструктор](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L99-L151), [open/restore/close](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L287-L297).

Mailbox-поток инициирует `submitRequestEntries`. Destination-клиент завершает запрос своим потоком, но `ResultHandler` переносит изменение writer state обратно в mailbox. `AtomicBoolean.compareAndSet` допускает ровно один исход для handler: complete, partial retry, fatal error либо timeout. При complete/partial retry отменяется timer; mailbox уменьшает in-flight, сообщает результат rate limiter, возвращает failed entries в голову buffer в сохранённом внутри списка порядке и пробует следующий flush. Повторные callback после выигрыша CAS ничего не меняют в writer state. [Submit thread contract](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L153-L208), [completeRequest](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L382-L404), [все исходы handler](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L479-L550).

Ровно один callback не означает ровно одну внешнюю запись. Timeout по умолчанию через 10 минут возвращает весь batch в retry; внешний запрос этим кодом не отменяется. Поздний успех может уже записать данные, хотя его callback проиграет CAS. Полностью прочитанный `AsyncSinkWriterTimeoutTest` прямо ожидает `[1, 1]` для такого сценария. При `failOnTimeout=true` timeout передаётся как fatal exception в mailbox. Тесты не запускались. [Defaults](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/config/AsyncSinkWriterConfiguration.java#L33-L35), [late success duplicate](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/test/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriterTimeoutTest.java#L48-L123).

`flush(false)` ждёт завершения in-flight через `mailboxExecutor.yield`, оставляя право сохранить оставшийся unsent buffer в snapshot. `flush(true)` дополнительно опустошает buffer. `snapshotState` сам не ждёт I/O: он копирует buffered wrappers в `BufferedRequestState`, полагаясь на предшествующий lifecycle runtime. Параметр `version` в абстрактной реализации deserialize не ветвит алгоритм; реализация кодека/version конкретного sink ещё не прочитана. ## FileSink: recoverable files и отдельный commit

Полностью прочитаны `FileSink`, `FileWriter`, `FileWriterBucket`, `FileCommitter`, обе структуры состояния и их serializers/factories. Шесть связанных тестовых файлов теперь прочитаны полностью; их инварианты приведены ниже, запуск не выполнялся. Обещание exactly-once в JavaDoc `FileSink` здесь рассматривается как контракт модуля, требующий проверки recovery и runtime commit chain, а не автоматически доказанный факт для каждой файловой системы.

`FileSink` создаёт writer и committer раздельно. Row-путь строит `RowWiseBucketWriter` из `FileSystem.createRecoverableWriter()` и encoder; bulk-путь — `BulkBucketWriter` из recoverable writer и `BulkWriter.Factory`. По умолчанию row применяет `DefaultRollingPolicy`, bulk — `OnCheckpointRollingPolicy`, а bulk builder принимает только `CheckpointRollingPolicy`. Writer-state serializer берётся из serializers underlying recoverable writer. Так формат определяет запись/финализацию данных, а filesystem — восстановление и публикацию файла; реализация конкретных recoverable writers ещё не прочитана. [Factory boundaries](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L148-L190), [row wiring](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L422-L492), [bulk wiring](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L537-L580).

`FileWriter` владеет map активных bucket; пользовательский `BucketAssigner` получает timestamp записи, watermark и processing time. Write получает/создаёт bucket, пишет элемент и увеличивает record counter. `flush(endOfInput)` только сохраняет флаг; реальное закрытие и подготовка файлов идут через `prepareCommit`. Перед ним удаляются уже неактивные bucket; остальные возвращают committables. Periodic timer проверяет rolling policy всех активных bucket и регистрирует следующую проверку. `close` вызывает dispose текущих part files, не commit. [Write/prepare/snapshot](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriter.java#L188-L238), [dispose и timer](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriter.java#L252-L279).

Bucket хранит один `inProgressPart`, список pending recoverables и последний persisted recoverable для cleanup. Event/time/checkpoint policy либо end-of-input закрывает part через `closeForCommit` и переводит handle в pending. `prepareCommit` выдаёт pending handles как committables и очищает локальный список; отдельно выдаётся cleanup предыдущего persisted handle. `snapshotState` вызывает `persist()` текущего part, запоминает handle для последующего cleanup и сохраняет bucket metadata/creation time/handle. Pending commit state современной версии поэтому отделено от writer-state и переносится через committable topology. Порядок runtime prepare→snapshot→commit ещё должен быть сверён с sink operator. [Bucket transition](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L180-L229), [closeForCommit](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L249-L289).

Restore выбирает `resumeInProgressFileFrom`, если underlying bucket writer поддерживает resume; иначе восстановленный in-progress handle добавляется в pending. Старые pending-per-checkpoint handles из миграционного состояния кешируются до первого prepareCommit. При нескольких состояниях одного bucket writer сохраняет первый bucket, закрывает in-progress part присоединяемого и объединяет pending handles. Имена новых файлов используют новый UUID и счётчик с нуля: общий конструктор вызывается и при restore. Это фактическая защита имён в прочитанном пути; JavaDoc `FileWriter.initializeState` про восстановление максимального part counter не соответствует этому bucket-коду и структуре writer-state, где counter отсутствует. [Restore и merge](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L84-L178), [генерация имени](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L264-L275), [комментарий initializeState](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriter.java#L140-L175).

`FileCommitter` всегда выполняет `recoverPendingFile(...).commitAfterRecovery()`, в том числе без отдельной ветки normal/recovery; дополнительные checks делегируются underlying writer. Затем выполняется cleanup persisted in-progress handle. Удаление исходного compacted файла best effort: исключение подавляется с debug log. Ошибки публикации pending и cleanup recoverable здесь не подавляются. Серилизация writer-state v3 пишет magic, bucket id/path, creation time и optional in-progress; v1/v2 readers дополнительно читают legacy pending maps и адаптируют старые recoverable types. Committable serializer v2 содержит bucket id и три optional payload: pending, in-progress cleanup, compacted-file cleanup; v1 восстанавливает пустой bucket id. [Commit и cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/committer/FileCommitter.java#L55-L89), [writer-state versions](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucketStateSerializer.java#L72-L208), [committable versions](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSinkCommittableSerializer.java#L57-L155).

Compaction меняет precommit topology: committables rebalanced в coordinator parallelism 1, затем compactor с parallelism committer. Равенство нужно для совместного попадания summary и соответствующих committables. Writer скрывает временные файлы префиксом `.`. Если compaction не использовался, topology пропускается; explicit disable добавляет state-handler placeholder operators с прежними UID, чтобы обработать оставшееся состояние. Поэтому простое удаление topology при выключении не эквивалентно вызову `disableCompact`. Внутренние coordinator/compactor state machines пока не прочитаны. [Topology и disable handlers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L214-L288), [hidden writer files](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L422-L446).

## FileSource: discovery, assignment и прогресс выдачи

`AbstractFileSource` создаёт `FileEnumerator` и получает начальные splits при создании coordinator enumerator. Затем `FileSplitAssigner` управляет ещё не назначенными splits. В bounded-режиме создаётся `StaticFileSplitEnumerator`; в continuous — `ContinuousFileSplitEnumerator`, исторический set путей и период discovery. При restore координатор берёт pending splits и пути из checkpoint вместо повторного формирования начального набора. Reader-state восстанавливается отдельно на reader-стороне. `FileSource` выбирает block/nonblock enumerator по `BulkFormat.isSplittable`, а StreamFormat оборачивает в `StreamFormatAdapter`, его реализация полностью прочитана и описана ниже. [Создание/restore](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/AbstractFileSource.java#L120-L218), [format wiring](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/FileSource.java#L169-L235).

Reader инициирует pull только если после restore у него нет splits; после finished split снова посылает request. Static enumerator игнорирует запрос уже deregistered reader, назначает один split с учётом hostname, либо сообщает no-more-splits. Его start/close не владеют отдельным ресурсом. Continuous enumerator сохраняет запросы в `LinkedHashMap`, проверяет регистрацию перед назначением, оставляет запрос ожидающим при отсутствии split и не отправляет no-more-splits. [Reader pull](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/impl/FileSourceReader.java#L39-L70), [static assignment](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/impl/StaticFileSplitEnumerator.java#L72-L125), [continuous wait-map](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/impl/ContinuousFileSplitEnumerator.java#L106-L179).

Continuous listing выполняется через `context.callAsync` с `enumerateSplits(paths, 1)`. Ошибка listing логируется, callback возвращается; здесь она не превращается в fail job. Set `pathsAlreadyProcessed` пополняется при discovery, до выдачи и обработки данных: это set уже обнаруженных путей, а не подтверждённых downstream файлов. По этому коду append/overwrite того же Path не образует новый входной файл, modificationTime и fileSize не участвуют в dedup. Set не очищается и попадает в каждый enumerator snapshot, поэтому память и checkpoint metadata растут с историческим числом путей. [Discovery/dedup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/impl/ContinuousFileSplitEnumerator.java#L92-L154), [checkpoint copy](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/PendingSplitsCheckpoint.java#L88-L110).

Есть конкретное несоответствие composition двух прочитанных компонентов: discovery фильтрует каждый split через `pathsAlreadyProcessed.add(split.path())`. ## Assignment и отдельный batch-only dynamic filter

`FileEnumerator.minDesiredSplits` — optional hint; по интерфейсу он не является максимальным количеством splits. Default locality assigner нормализует hostname до нижнего регистра short name, лениво создаёт локальные choosers и предпочитает splits с меньшим числом уже наблюдавшихся локальных hosts; затем использует remote fallback. Это heuristic placement, не гарантия locality. Новые splits добавляются в remote chooser/unassigned, а уже построенные per-host choosers этим методом не пополняются. `SimpleSplitAssigner` фактически снимает последний элемент ArrayList: его порядок нельзя описывать как FIFO, хотя JavaDoc называет выдачу random. [Locality implementation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/assigners/LocalityAwareSplitAssigner.java#L86-L151), [Simple order](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/assigners/SimpleSplitAssigner.java#L43-L56).

`DynamicFileSplitEnumerator` — отдельный batch-only путь. Первый request без filter создаёт полный assigner; dynamic filter event пересоздаёт assigner, сохраняя set уже назначенных split ids для предотвращения повторной выдачи. Add-back возвращает только splits, которые ещё входят в актуальный enumerated set, и снимает их assigned marker. Snapshot явно бросает `UnsupportedOperationException`; execution-attempt overload обработчика намеренно игнорирует attemptNumber. Поэтому этот механизм не следует описывать как checkpointed streaming discovery с возможностью произвольного изменения filter. Его тесты и concrete dynamic enumerator providers пока не прочитаны. [Dynamic lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/src/impl/DynamicFileSplitEnumerator.java#L113-L205).

## Metrics core: именование, измерение и export — разные обязанности

`MetricGroup` регистрирует четыре вида metric, создаёт subgroup hierarchy и строит scoped identifier/variables. `addGroup(key,value)` добавляет variable `<key>=value`; это не просто два обычных group names. Experimental addSpan/addEvent в базовом интерфейсе default no-op, поэтому их вызов на произвольной реализации MetricGroup не доказывает export. `MetricReporter` получает add/remove callbacks, `Reporter` задаёт open-first/close-resources lifecycle. `Scheduled.report` — отдельный интерфейс periodic push, который не должен надолго блокировать вызывающий registry thread. Сам registry и его executor полностью прочитаны reader=execution; их cross-domain контракт приведён ниже с указанным владельцем evidence. Прочитанные ниже concrete exporters — Prometheus и OpenTelemetry; остальные exporters пока не прочитаны. [MetricGroup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/main/java/org/apache/flink/metrics/MetricGroup.java#L28-L51), [variables](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/main/java/org/apache/flink/metrics/MetricGroup.java#L185-L238), [scheduled contract](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/main/java/org/apache/flink/metrics/reporter/Scheduled.java#L23-L32).

`AbstractReporter` держит map metric-instance→scoped-name отдельно для gauge/counter/histogram/meter; add/remove защищены synchronized(this). Это не делает все зарегистрированные metrics thread-safe: `SimpleCounter` — обычный long, `ThreadSafeSimpleCounter` использует LongAdder. Counter API поддерживает и decrement, поэтому само слово counter не гарантирует монотонность. Gauge вычисляет значение при чтении; reporter обязан учитывать стоимость и concurrency конкретного gauge. [Reporter maps](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/main/java/org/apache/flink/metrics/reporter/AbstractReporter.java#L41-L95), [plain counter](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/main/java/org/apache/flink/metrics/SimpleCounter.java#L23-L69), [concurrent counter](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/main/java/org/apache/flink/metrics/ThreadSafeSimpleCounter.java#L24-L70).

`MeterView` считает rate из кольцевой истории counter. Background `update` раз в ожидаемые 5 секунд сдвигает ring и вычисляет разность отсчётов / настроенный span; span округляется вниз к кратному 5, минимум 5, default60. `getRate` возвращает уже вычисленный rate, а не измеряет elapsed wall time при каждом вызове. Поэтому задержка вызовов update не корректируется этим алгоритмом по реальному elapsed time. Gauge-wrapper используется как read-only counter: markEvent для него бросает UnsupportedOperationException. [Rate algorithm](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/main/java/org/apache/flink/metrics/MeterView.java#L66-L107), [test](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-metrics/flink-metrics-core/src/test/java/org/apache/flink/metrics/MeterViewTest.java#L50-L105).

`SlidingWindowHistogram` хранит последние N значений по количеству обновлений; это не временное окно. `getCount` считает все updates, `statistics.size` ограничена ring capacity. Возвращаемые statistics независимы от следующих updates. Runtime metrics dependency изучена отдельно reader=execution: `MetricRegistryImpl` и `ViewUpdater` прочитаны им полностью, автор этой главы не присваивает себе их чтение. Создаются два single-thread scheduled executor: общий для Scheduled reporters и отдельный для View updates. Reporter scheduling использует fixed delay; report Throwable ловится. По видимому коду этой ревизии тот же shutdown не доказывает закрытие trace/event reporter lists. Typed metric groups дополнительно разделяют события send и commit. `SinkWriterMetricGroup.getNumRecordsSendCounter` прямо допускает downstream persistence failure после send; committer group отдельно считает successful/already-committed/retried committables. ## Span/event: снимок наблюдения и изменяемые attributes

Полностью прочитан весь tracked subtree `flink-metrics/flink-metrics-core`: production, tests, test utilities, POM и текстовый service resource. Это узкая завершённая область чтения; остальные metrics modules и весь назначенный корпус остаются открытыми. Тесты не запускались.

## OpenTelemetry: collection cut, delta и export completion

## Native S3 recoverable writer: multipart state и публикация

Полностью прочитаны все шесть production classes пакета `s3native.writer`, пять test/helper classes и recovery integration scenario; остальные native filesystem classes и provider/retry/container зависимости ещё открыты. Write path держит buffered local temp file и синхронно upload-ит part после достижения minPartSize. Вызов write(byte[]) не делит большой вход на равные parts: весь вызов сначала попадает в текущий файл, threshold проверяется после. Поэтому minPartSize — порог, не максимальная память/размер part. Поле maxConcurrentUploadsPerStream хранится в writer, но не передаётся в stream и в прочитанном writer path не используется для parallel upload. [Writer construction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/writer/NativeS3RecoverableWriter.java#L43-L75), [write/upload](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/writer/NativeS3RecoverableFsDataOutputStream.java#L146-L218).

Flush сбрасывает локальный BufferedOutputStream; sync вызывает persist. Persist сохраняет список уже uploaded parts и при наличии малого tail пишет отдельный объект `parent/.incomplete/uploadId/UUID`. Он не завершает multipart target. Recovery скачивает tail по сохранённому opaque key, проверяет длину, продолжает локальный файл append-mode; удалённый tail оставляет для повторного recovery до cleanupRecoverableState. Close/ошибка closeForCommit удаляют только local resources и не abort-ят multipart upload: stream не знает, удерживает ли upload сохранённый checkpoint/savepoint. Abandoned uploads требуют внешнего lifecycle. Таким образом terminal cleanup task и безопасное удаление storage state не совпадают. [Persist](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/writer/NativeS3RecoverableFsDataOutputStream.java#L269-L333), [tail recovery/cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/writer/NativeS3RecoverableWriter.java#L86-L198).

CloseForCommit upload-ит последний part и возвращает committer; только commit завершает multipart upload. CommitAfterRecovery просто повторяет commit. ObjectOperations при NoSuchUpload делает HEAD конечного key и считает найденный объект результатом успешного прошлого commit; не сверяет переданный length, сохранённый upload id или version/content. Поэтому эта ветка восстанавливает неоднозначный response-loss при предположении исключительного владения конечным key; существование произвольного объекта по тому же key не доказывает его идентичность ожидаемой записи. Empty multipart commit явно отклонён. Это важная конкретизация JavaDoc «exactly-once», не универсальная гарантия произвольного S3-compatible backend или конкурентных writers. [Commit](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/writer/NativeS3Committer.java#L63-L92), [completion fallback](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/writer/NativeS3ObjectOperations.java#L297-L334).

## Native S3 filesystem: streams, clients и отмена downloads

Дополнительно полностью прочитаны NativeS3FileSystem/Factory, S3ClientProvider, обычные input/output streams, recursive-delete/bulk-copy helpers, URI/status/block metadata, retry factory и SDK metrics bridge/recorder. Их tests, кроме InputStreamTest, ещё не покрыты полностью; module в целом открыт.

Обычный NativeS3OutputStream хранит целый объект в local temp file. И sync, и close выставляют fileUploaded до upload, закрывают local stream и выполняют PUT; после sync дальнейший write отклоняется. При failure temp удаляется в finally, повторный close upload не повторяет. Это отдельный terminal write protocol, его нельзя объяснять через persist/committable recoverable stream. Rename filesystem — CopyObject, затем DeleteObject; directory rename unsupported, rollback между этими операциями отсутствует. Create NO_OVERWRITE использует exists-before-PUT, а не atomic conditional PUT. [Terminal sync/close](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3OutputStream.java#L146-L211), [create/rename](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3FileSystem.java#L438-L499).

Input stream открывает GET лениво после seek; forward seek до readBufferSize пытается skip в BufferedInputStream, иногда читая live HTTP stream, более дальний/backward seek открывает новый Range GET. Available показывает оставшиеся bytes по исходному contentLength, не готовые без блокировки bytes. GET не привязывается к ETag/version; стабильность содержимого при повторных ranges предполагается снаружи. Read держит lock во время I/O; close получает тот же lock и лишь затем abort-ит response, поэтому сам close не может немедленно прервать read, уже удерживающий lock. Полностью прочитанный InputStreamTest671 проверяет byte contents, lazy coalescing/ranges/abort order и skip fallback на stub; теста реального blocked-read cancellation там нет. Названные EOF-release tests не проверяют early release, а production read при EOF возвращает до lazySeek, оставляя release до close. [Lazy seek](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3InputStream.java#L111-L195), [read/close](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3InputStream.java#L283-L389), [EOF test body](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/test/java/org/apache/flink/fs/s3native/NativeS3InputStreamTest.java#L417-L431).

Factory создаёт sync client, async client и TransferManager независимо от использования async object puts. Non-CRT sync использует Apache transport, async — Netty; CRT меняет оба. Общий standard/adaptive RetryStrategy ставится на обычные clients; CRT async получает отдельный numRetries и не использует этот strategy/metric publisher override. Socket timeout не задаётся CRT sync, chunked setting не передаётся CRT async. Следовательно один config key не гарантирует одинаковую retry/timeout/observability семантику всех transports. Default credential chain по коду: custom providers, configured static credentials, dynamic token provider, SDK default; описание factory перечисляет token перед static, поэтому приоритет берётся из builder implementation. [Client construction/transport](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/S3ClientProvider.java#L700-L903), [credential order](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/S3ClientProvider.java#L922-L953).

CloseAsync filesystem закрывает admission AtomicBoolean и запускает provider close; текущие операции не подсчитываются и не drain-ятся. Provider последовательно закрывает TransferManager→async→sync→credentials→STS в common pool, ловит ошибки каждого close, а общий timeout превращает в нормальное завершение через exceptionally. Повторный вызов обоих closeAsync возвращает completedFuture вместо исходного ещё выполняющегося close. Поэтому normal returned future и отсутствие active readers/resources не эквивалентны. Timeout CompletableFuture также сам не останавливает произвольный underlying close call. [Filesystem close](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3FileSystem.java#L549-L589), [provider cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/S3ClientProvider.java#L361-L406).

Bulk copy создаёт fixed download pool на один вызов; batch size clamped к maxConnections и новый batch ждёт весь предыдущий. SDK async response преобразуется в blocking InputStream; worker копирует его через bounded byte[] в temp file рядом с destination, затем move. Успешно опубликованные local destinations при общей ошибке сохраняются. Registry cancellation отменяет futures, abort/close active streams, shutdownNow и ждёт workers до5s; late registrations перепроверяют closed. Нормальная copyFuture завершается до finally release stream/temp, так что её completion не доказывает завершение всех cleanup callbacks. Recursive delete ограничивает heap одной listing page1000 и проверяет per-key errors batched delete, но не делает удаление subtree атомарным. [Bulk scheduling](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3BulkCopyHelper.java#L149-L215), [worker handoff](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3BulkCopyHelper.java#L299-L344), [cancellation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3BulkCopyHelper.java#L409-L470), [paged deletion](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3RecursiveDelete.java#L64-L147).

SDK metric bridge существует до attachment MetricGroup и отбрасывает ранние observations. Atomic recorder replacement перенаправляет последующие publish в новую group; metrics — concurrent counters и sample histograms по operation/status/reason. API call count — один логический SDK call, throttle count — количество429/503 attempt responses, retry reason выбирается по наличию throttling/5xx в children. Allowlist iops лишь включает api_call_count: recorder не регистрирует отдельный iops meter/gauge. Это различие metric observation и сетевой попытки важно при оценке retry нагрузки. [Bridge](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/metrics/AwsSdkMetricBridge.java#L72-L122), [recorder](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/metrics/S3MetricRecorder.java#L80-L158).

Полностью дочитан весь native S3 production Java subtree, включая bucket configuration, encryption и delegation-token provider/receiver. Local move helper сначала пробует ATOMIC_MOVE, но при unsupported filesystem делает обычный replacement move; atomic local publication поэтому условна. Bucket overrides распознаются по longest known property suffix, допускают dotted bucket names и требуют парные credentials; не вся global configuration допускает bucket override. Token receiver хранит credentials и region в отдельных static volatile fields; обновление credentials не проверяет expiry или порядок поступления token refresh. Фактическое управление renewal и доставка tokens принадлежат ещё не прочитанным здесь runtime dependencies. [Local fallback](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/NativeS3FileIoUtils.java#L45-L68), [bucket parsing](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/BucketConfigProvider.java#L137-L212), [token state](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-filesystems/flink-s3-fs-native/src/main/java/org/apache/flink/fs/s3native/token/NativeS3DelegationTokenReceiver.java#L56-L105).
