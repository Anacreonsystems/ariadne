## Источник: разделение I/O и выдачи записей

`SourceReaderBase` соединяет `SplitFetcherManager`, `RecordEmitter` и `FutureCompletingBlockingQueue<RecordsWithSplitIds<E>>`. Карта `splitStates` хранит изменяемое состояние каждого назначенного split, а `snapshotState` переводит именно эту карту в список неизменяемых `SplitT`. Прочитанный из внешней системы batch сам по себе не обновляет эту карту: `pollNext` достаёт запись batch и вызывает `recordEmitter.emitRecord(record, currentSplitOutput, currentSplitContext.state)`. Таким образом, наблюдаемая здесь граница checkpoint progress проходит через выдачу записи в mailbox-пути, а не через завершение фонового чтения. Конкретное обновление offset определяется реализацией emitter и пока не обобщается на все коннекторы. [Поля и конструктор](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L78-L170), [выдача](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L173-L260), [snapshot и назначение](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L347-L374).

Без rate limiter один вызов `pollNext` выдаёт одну богатую входную запись и возвращает `MORE_AVAILABLE`, даже когда следующей записи может не быть. Это намеренная ложноположительная доступность ради отсутствия дополнительной проверки на каждой записи. Один emitter может выдать несколько конечных записей. В режиме rate limiting обёртка считает именно вызовы `SourceOutput.collect`, передаёт их число в `rateLimiter.acquire` и сбрасывает счётчик окна. Если permit future ещё не завершён, этот метод также возвращает `MORE_AVAILABLE`; `isAvailable` данного класса выбирает только текущий fetch либо queue future. Поэтому по этому файлу нельзя утверждать, что rate limiter сам переводит runtime в ожидание своего future. [Rate limiting](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L219-L259), [availability](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L340-L345), [счётчик конечных записей](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L551-L608).

Batch последовательно переключает split через `nextSplit`. Для неизвестного split срабатывает `checkState`; для известного создаётся или переиспользуется отдельный output. При исчерпании batch reader удаляет только объявленные `finishedSplits` из карты, освобождает их outputs, вызывает `onSplitFinished` и затем `fetch.recycle`. EOF evaluator подавляет сам EOF-record и последующие записи этого split и асинхронно запрашивает удаление split у fetcher manager. Это отличается от немедленного удаления checkpoint state: его удаляет обработка finished-split batch. [Переходы и recycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L282-L337), [EOF output](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L483-L539).

## Fetcher: управление, сообщения и срок жизни ресурсов

`SplitFetcher` — `Runnable` с одним `SplitReader`, fallback `FetchTask`, очередью управляющих задач и картой назначенных split. Под lock он выбирает управляющую FIFO-задачу, иначе fetch при наличии split, иначе ждёт condition; саму задачу выполняет вне lock, позволяя другому потоку вызвать её `wakeUp`. Невыполненная управляющая задача ставится обратно в голову очереди. Add/remove/pause-resume ставят задачи, а не вызывают внешний reader непосредственно из mailbox. `SingleThreadMultiplexSourceReaderBase` выбирает `SingleThreadFetcherManager`; его реализация лениво создаёт fetcher, ставит add до запуска, затем переиспользует первый активный fetcher. После удаления idle fetcher следующее назначение создаёт новый reader, а старый ещё может ожидать recycle. Контракт допускает последовательное чтение файлов либо multiplex нескольких подписок одним reader. [Реализация manager](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SingleThreadFetcherManager.java#L104-L128). [Цикл fetcher](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L166-L255), [асинхронные задачи](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L258-L327), [база multiplex reader](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SingleThreadMultiplexSourceReaderBase.java#L35-L104).

`FetchTask` сохраняет `lastRecords`, если wakeup помешал handover. Callback finished splits вызывается только после успешной постановки batch в queue; затем ссылка обнуляется. Wakeup сначала устанавливает флаг, затем будит либо `SplitReader`, либо producer, ожидающий свободного места queue. Поэтому callback не сообщает об окончании split раньше передачи последних записей consumer. [Полный алгоритм](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/FetchTask.java#L54-L107).

Штатное выключение idle fetcher учитывает срок жизни памяти batch: fetcher кладёт пустой синхронизационный batch и ждёт `recordsProcessedLatch`; только `recycle` этого batch снимает latch, после чего закрывается `SplitReader`. Обычный `shutdown(false)` снимает latch сразу. Manager удаляет idle fetcher из активной карты ещё до завершения закрытия ресурса, поэтому отдельно считает `fetchersToShutDown`. Его `close(timeout)` запрещает создание новых fetcher, вызывает shutdown активных, запускает drain/recycle очереди и ждёт завершения executor в пределах общего deadline. При истечении времени этот код пишет warning; он не доказывает принудительную остановку внешнего I/O. [Shutdown fetcher](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L126-L164), [варианты shutdown](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcher.java#L337-L368), [manager lifecycle](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L246-L347).

Ошибки I/O сохраняются в `AtomicReference`: первая становится основной, последующие добавляются как suppressed. Manager завершает availability future, чтобы разбудить consumer; `checkErrors` повторно выбрасывает сохранённую причину на reader-пути. `END_OF_INPUT` выдаётся после `notifyNoMoreSplits`, отсутствия активных fetcher и пустой queue, с заключительной проверкой ошибки. Это несколько условий жизненного цикла, а не вывод из одного `fetch()==EOF`. Executor фактически создаётся через `newCachedThreadPool`; комментарий про два потока не описывает вызов конструктора в этой ревизии. [Ошибка и executor](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L151-L191), [повторное выбрасывание](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L349-L355), [условия конца](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/SourceReaderBase.java#L433-L448).

## Handover queue: backpressure и учёт producer

`FutureCompletingBlockingQueue` ограничивает количество элементов queue. Для reader это количество batch, а не байтов или конечных записей; отдельный batch и `lastRecords` могут удерживать память сверх числа слотов queue. Producer блокируется в `put` при заполнении; consumer использует неблокирующий `poll` и future доступности. `notifyAvailable` может завершить future без данных. После пустого `poll` или удаления последнего элемента future заменяется новым незавершённым. Consumer обязан повторно проверить данные/условия и получить актуальный future; completed future не является обещанием ненулевой записи. [Контракт](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L43-L77), [put/poll](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L198-L274).

Graceful wakeup сохраняется как sticky flag по producer id, включая wakeup до первого блокирования. Состояние создаётся только при wakeup или ожидании и удаляется через `releaseProducer` после окончательного выхода producer. Сам номер fetcher монотонно увеличивается; cleanup препятствует накоплению condition для всех исторических fetcher. Удалять состояние во время `put` нельзя: producer мог уже получить signal и исчезнуть из FIFO ожидающих, но ещё не захватить lock. Отдельный `waitingPutters` покрывает весь `await`, а `releaseProducer` отказывается удалять такую запись. Shutdown hook manager вызывает release после выхода run loop. [Wakeup и release](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L355-L420), [ожидание](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueue.java#L449-L530), [hook](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/source/reader/fetcher/SplitFetcherManager.java#L253-L275).

Полностью прочитан `FutureCompletingBlockingQueueTest` (492 строки), тесты не запускались. Они задают следующие проверяемые инварианты: wakeup первого producer не оставляет следующего без signal; release идемпотентен и адресен; release во время parked put и в окне signal→reacquire сохраняет sticky wakeup; interrupt снимает отметку waiting; опустошение queue сбрасывает availability; default capacity равна двум; `AVAILABLE` совпадает с runtime singleton. Последний тест проверяет reflection fast path, а не семантику всех вариантов classloader. [Wakeup и cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/test/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueueTest.java#L110-L340), [capacity и availability](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/test/java/org/apache/flink/connector/base/source/reader/synchronization/FutureCompletingBlockingQueueTest.java#L409-L491).

## Асинхронный sink: mailbox, повторные записи и checkpoint

`AsyncSinkBase` поддерживает destination с асинхронным клиентом и writer state. Его собственный контракт — at-least-once; retry может менять порядок. `AsyncSinkWriter` хранит преобразованные `RequestEntryT`, а не исходные `InputT`: частичный ответ destination часто позволяет восстановить failed request, но не исходное событие. `ElementConverter.open` выполняется до восстановления буфера. Generic `close` пуст; закрытие клиентского pool/socket остаётся ответственностью конкретного sink. [Base contract](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/AsyncSinkBase.java#L32-L52), [request buffer и конструктор](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L99-L151), [open/restore/close](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L287-L297).

Mailbox-поток инициирует `submitRequestEntries`. Destination-клиент завершает запрос своим потоком, но `ResultHandler` переносит изменение writer state обратно в mailbox. `AtomicBoolean.compareAndSet` допускает ровно один исход для handler: complete, partial retry, fatal error либо timeout. При complete/partial retry отменяется timer; mailbox уменьшает in-flight, сообщает результат rate limiter, возвращает failed entries в голову buffer в сохранённом внутри списка порядке и пробует следующий flush. Повторные callback после выигрыша CAS ничего не меняют в writer state. [Submit thread contract](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L153-L208), [completeRequest](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L382-L404), [все исходы handler](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L479-L550).

Ровно один callback не означает ровно одну внешнюю запись. Timeout по умолчанию через 10 минут возвращает весь batch в retry; внешний запрос этим кодом не отменяется. Поздний успех может уже записать данные, хотя его callback проиграет CAS. Полностью прочитанный `AsyncSinkWriterTimeoutTest` прямо ожидает `[1, 1]` для такого сценария. При `failOnTimeout=true` timeout передаётся как fatal exception в mailbox. Тесты не запускались. [Defaults](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/config/AsyncSinkWriterConfiguration.java#L33-L35), [late success duplicate](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/test/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriterTimeoutTest.java#L48-L123).

`flush(false)` ждёт завершения in-flight через `mailboxExecutor.yield`, оставляя право сохранить оставшийся unsent buffer в snapshot. `flush(true)` дополнительно опустошает buffer. `snapshotState` сам не ждёт I/O: он копирует buffered wrappers в `BufferedRequestState`, полагаясь на предшествующий lifecycle runtime. Restore повторно добавляет эти wrappers; если после checkpoint они уже были отправлены до сбоя, повторение допустимо. Связь runtime вызовов `flush`→snapshot подлежит отдельной сверке с sink operator. Сериализатор записывает long marker `-1`, int count и для каждой записи long destination-size плюс конкретный payload codec. Параметр `version` в абстрактной реализации deserialize не ветвит алгоритм; реализация кодека/version конкретного sink ещё не прочитана. [Flush/snapshot/restore](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L425-L469), [state copy](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/BufferedRequestState.java#L29-L76), [serialization](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriterStateSerializer.java#L40-L99).

|---|---|
| `maxBufferedRequests` | Проверяется перед добавлением новой входной записи; завершение I/O возвращает retry entries без этой проверки. Это не предел всех одновременно живых request objects. |

Стандартная strategy начинает с message budget `maxBatchSize` и AIMD ceiling `maxBatchSize * maxInFlightRequests`. Полностью успешный request увеличивает message budget на 10 до ceiling; хотя бы одна failed message уменьшает бюджет с округлением до половины и минимумом 1. Это реакция на результаты запросов, а не лимит запросов в секунду и не time-based backoff. `DequeRequestBuffer` отправляет новые entries FIFO, помещает retry в голову и хранит отдельную сумму bytes; snapshot возвращает копию списка wrappers. I/O-метрики writer увеличиваются при попытке отправки batch, поэтому retries учитываются повторно и эти counters нельзя читать как число уникальных подтверждённых записей. [Default strategy](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/config/AsyncSinkWriterConfiguration.java#L181-L204), [AIMD](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/strategy/AIMDScalingStrategy.java#L33-L65), [buffer](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/DequeRequestBuffer.java#L44-L98), [attempt metrics](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-base/src/main/java/org/apache/flink/connector/base/sink/writer/AsyncSinkWriter.java#L360-L375).

## FileSink: recoverable files и отдельный commit

Полностью прочитаны `FileSink`, `FileWriter`, `FileWriterBucket`, `FileCommitter`, обе структуры состояния и их serializers/factories. Тесты файлового sink пока не прочитаны. Обещание exactly-once в JavaDoc `FileSink` здесь рассматривается как контракт модуля, требующий проверки recovery и runtime commit chain, а не автоматически доказанный факт для каждой файловой системы.

`FileSink` создаёт writer и committer раздельно. Row-путь строит `RowWiseBucketWriter` из `FileSystem.createRecoverableWriter()` и encoder; bulk-путь — `BulkBucketWriter` из recoverable writer и `BulkWriter.Factory`. По умолчанию row применяет `DefaultRollingPolicy`, bulk — `OnCheckpointRollingPolicy`, а bulk builder принимает только `CheckpointRollingPolicy`. Writer-state serializer берётся из serializers underlying recoverable writer. Так формат определяет запись/финализацию данных, а filesystem — восстановление и публикацию файла; реализация конкретных recoverable writers ещё не прочитана. [Factory boundaries](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L148-L190), [row wiring](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L422-L492), [bulk wiring](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L537-L580).

`FileWriter` владеет map активных bucket; пользовательский `BucketAssigner` получает timestamp записи, watermark и processing time. Write получает/создаёт bucket, пишет элемент и увеличивает record counter. `flush(endOfInput)` только сохраняет флаг; реальное закрытие и подготовка файлов идут через `prepareCommit`. Перед ним удаляются уже неактивные bucket; остальные возвращают committables. Periodic timer проверяет rolling policy всех активных bucket и регистрирует следующую проверку. `close` вызывает dispose текущих part files, не commit. [Write/prepare/snapshot](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriter.java#L188-L238), [dispose и timer](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriter.java#L252-L279).

Bucket хранит один `inProgressPart`, список pending recoverables и последний persisted recoverable для cleanup. Event/time/checkpoint policy либо end-of-input закрывает part через `closeForCommit` и переводит handle в pending. `prepareCommit` выдаёт pending handles как committables и очищает локальный список; отдельно выдаётся cleanup предыдущего persisted handle. `snapshotState` вызывает `persist()` текущего part, запоминает handle для последующего cleanup и сохраняет bucket metadata/creation time/handle. Pending commit state современной версии поэтому отделено от writer-state и переносится через committable topology. Порядок runtime prepare→snapshot→commit ещё должен быть сверён с sink operator. [Bucket transition](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L180-L229), [closeForCommit](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L249-L289).

Restore выбирает `resumeInProgressFileFrom`, если underlying bucket writer поддерживает resume; иначе восстановленный in-progress handle добавляется в pending. Старые pending-per-checkpoint handles из миграционного состояния кешируются до первого prepareCommit. При нескольких состояниях одного bucket writer сохраняет первый bucket, закрывает in-progress part присоединяемого и объединяет pending handles. Имена новых файлов используют новый UUID и счётчик с нуля: общий конструктор вызывается и при restore. Это фактическая защита имён в прочитанном пути; JavaDoc `FileWriter.initializeState` про восстановление максимального part counter не соответствует этому bucket-коду и структуре writer-state, где counter отсутствует. [Restore и merge](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L84-L178), [генерация имени](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucket.java#L264-L275), [комментарий initializeState](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriter.java#L140-L175).

`FileCommitter` всегда выполняет `recoverPendingFile(...).commitAfterRecovery()`, в том числе без отдельной ветки normal/recovery; дополнительные checks делегируются underlying writer. Затем выполняется cleanup persisted in-progress handle. Удаление исходного compacted файла best effort: исключение подавляется с debug log. Ошибки публикации pending и cleanup recoverable здесь не подавляются. Серилизация writer-state v3 пишет magic, bucket id/path, creation time и optional in-progress; v1/v2 readers дополнительно читают legacy pending maps и адаптируют старые recoverable types. Committable serializer v2 содержит bucket id и три optional payload: pending, in-progress cleanup, compacted-file cleanup; v1 восстанавливает пустой bucket id. [Commit и cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/committer/FileCommitter.java#L55-L89), [writer-state versions](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/writer/FileWriterBucketStateSerializer.java#L72-L208), [committable versions](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSinkCommittableSerializer.java#L57-L155).

Compaction меняет precommit topology: committables rebalanced в coordinator parallelism 1, затем compactor с parallelism committer. Равенство нужно для совместного попадания summary и соответствующих committables. Writer скрывает временные файлы префиксом `.`. Если compaction не использовался, topology пропускается; explicit disable добавляет state-handler placeholder operators с прежними UID, чтобы обработать оставшееся состояние. Поэтому простое удаление topology при выключении не эквивалентно вызову `disableCompact`. Внутренние coordinator/compactor state machines пока не прочитаны. [Topology и disable handlers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L214-L288), [hidden writer files](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-connectors/flink-connector-files/src/main/java/org/apache/flink/connector/file/sink/FileSink.java#L422-L446).
