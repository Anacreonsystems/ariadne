# Ресурсные fixtures планировщика: планы, сериализация и границы доказательств

Срез закреплён на Flink `068f428b29f4d9ee587fa1006d2f1a69b43c0000`. После полного личного чтения назначенного owner=state (1280файлов/251161строка) отдельно передан оставшийся текстовый subtree `flink-table/flink-table-planner/src/test/resources/`: **756файлов/311943строки** по inventory минус union confirmed ledgers на момент handoff. Immutable owner остаётся table; подтверждения личного чтения дополнительных ресурсов записываются в `readers/state.confirmed.jsonl`. Binary fixtures не входят в этот текстовый срез. Ни tests, ни генерация golden files не запускаются. Чтение всего subtree пока не завершено.

Scoped planner AGENTS и README описывают XML golden plan tests и regeneration JSON через PLAN_TEST_FORCE_OVERWRITE. Это developer workflow, не свидетельство фактического запуска в этом исследовании. Resource содержит зафиксированный ожидаемый текст/JSON; семантика проверки требует отдельного test oracle и harness. Поэтому наличие operator/edge/option в fixture означает отражённый expected plan для соответствующего test case; оно само по себе не доказывает runtime execution, checkpoint restoration или внешнюю exactly-once запись. [Planner conventions](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/AGENTS.md), [README regeneration](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/README.md#L24-L27).

Первыми полностью прочитаны test SPI/configuration resources. Современный Factory service file регистрирует TestValues/TestFile, staging/update-delete/procedure/model/catalog factories и TimeoutAsyncLookup factory; legacy TableFactory отдельно регистрирует memory/temporal/partitionable/legacy-file providers. Эти services объясняют, почему compiled/explain fixtures могут содержать test-only connectors; они не означают наличие такого connector в production runtime. JUnit service file включает TestLoggerExtension и TestNameProviderExtension. ArchUnit допускает обновление уже замороженного store (allowStoreUpdate=true), но creation/refreeze лишь закомментированы, путь store=archunit-violations; assertions самого ArchUnit runner здесь отсутствуют. [Modern providers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/META-INF/services/org.apache.flink.table.factories.Factory#L16-L27), [legacy providers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/META-INF/services/org.apache.flink.table.legacy.factories.TableFactory#L16-L27), [ArchUnit config](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/archunit.properties#L19-L31).



В filesystem explain-fixtures AST→optimized plan ещё показывает один Sink, но Physical Execution Plan разворачивает streaming writer с parallelism=5 и end writer=1, с REBALANCE между ними; compaction-вариант добавляет coordinator=1 и compact operator=5 с BROADCAST coordinator→compact. Batch-вариант содержит Source=1→Filesystem Sink=5 через REBALANCE. Это важное различие уровней: реляционный Sink не задаёт число runtime operators. Пустые значения id в этих `.out` также показывают, что сохранённый normalized explain output не обязательно является самостоятельным валидным JSON. Explain files с cost/changelog detail задают ожидаемые planner estimates: rowcount=1e8 у source и 5e7 после a>10 не являются замерами. Batch/stream ExplainTest XML дают парные extended=false/true cases. Batch COUNT использует local partial→hash exchange→final aggregate; streaming COUNT использует GroupAggregate и в extended output меняет I→I,UA. GroupAggregationAnalyzer fixtures задают advice как функцию missing settings: при mini-batch=false/AUTO совет включить mini-batch; ONE_PHASE с latency=0,size=-1 перечисляет четыре настройки; mini-batch=true/ONE_PHASE советует только AUTO; true/AUTO даёт Local/GlobalGroupAggregate и «No available advice». Hint shuttle fixtures сохраняют промежуточные trees до propagation, после propagation/capitalization и после clearing. Вложенный view получает чужой inherited BROADCAST/LOOKUP/STATE_TTL с более длинным inheritPath; clearing удаляет этот экземпляр, сохраняя локальный hint и outer hint. Case-insensitive LOOKUP и STATE_TTL нормализуются uppercase. Это показывает scope metadata, а не момент TTL expiration: outer aggregate tmp=2d не должен заменить nested t4=1d; join outer t4=9d,t3=12d не должен проникнуть во внутренний t1=1d,t2=7d. Lookup hints с async/retry/capacity/timeout здесь остаются на UDTF/UNNEST Correlate в «NoNeedToClear» cases; отсутствие удаления на этом проходе не доказывает, что runtime UDTF реализует lookup retry protocol. [BROADCAST scope](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/hint/ClearJoinHintsWithInvalidPropagationShuttleTest.xml#L31-L50), [TTL scope](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/hint/ClearStateTtlHintsWithInvalidPropagationShuttleTest.xml#L19-L96), [UDTF/UNNEST boundary](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/hint/ClearLookupJoinHintsWithInvalidPropagationShuttleTest.xml#L101-L161).

CalcMerge fixtures показывают causal boundary для nondeterminism: если random result нужен и projection, и filter, остаются два Calc с именованным промежуточным a1; когда result нужен лишь filter, вызов переносится в condition; когда unused — удаляется. Два outer random_udf(a1) сохраняют shared inner random_udf(a) в отдельном Calc. Это ожидаемая форма, предотвращающая дублирование inner expression; конкретная count-of-invocations runtime здесь не проверяется. CalcTest отдельно фиксирует SEARCH/Sarg для IN/OR/NOT IN и `NULL AS TRUE` для OR IS NULL, typed constants, nested ROW/ARRAY/MAP и decimal coercion. [Shared nondeterministic value](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/batch/sql/CalcMergeTest.xml#L76-L94), [two outer calls](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/batch/sql/CalcMergeTest.xml#L155-L171), [NULL predicate](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/batch/sql/CalcTest.xml#L393-L424).

DagOptimization fixtures объединяют shared scan/filter/aggregate/window/UNION subplans с explicit reuse_id/reference_id. Один Calc(random_udf(a)) также переиспользуется между SUM и MIN sinks: это expected sharing конкретного общего view, а не общее обещание повторяемости random UDF. DeadlockBreakup fixtures добавляют BATCH shuffle на одном из расходящихся путей reuse→build/probe, в том числе distribution=any/single/hash и дополнительные exchange; изменения видны и когда reused node — blocking aggregate. Название теста с NestedLoopJoin либо SortMergeJoin не гарантирует такой выбранный узел: соответствующие сохранённые plans местами содержат HashJoin. «Barrier node» в имени batch case не является checkpoint barrier: fixture показывает execution dependency/materialization boundary. По golden plan нельзя заключить, что deadlock воспроизведён либо устранён в реально запущенном job. [Shared random view](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/batch/sql/DagOptimizationTest.xml#L307-L338), [reused barrier node](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/batch/sql/DeadlockBreakupTest.xml#L94-L126), [reuse exchange BATCH boundary](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/batch/sql/DeadlockBreakupTest.xml#L336-L402).



DynamicFilteringTest XML разворачивает filtered dimension→DataCollector→BATCH broadcast→OrderEnforcer/MultipleInput перед fact scan, а от того же dimension Calc идёт обычный join input. Пара ALL_EXCHANGES_PIPELINED всё равно содержит принудительные BATCH edges для collector broadcast и reused dimension join path: имя режима не обещает отсутствие blocking boundaries. Static pruning ограничивает fact partitions до p1=2/3 и сосуществует с dynamic filter. Duplicate fact table occurrence вне qualifying join остаётся обычным TableSourceScan; legacy source case также не получает dynamic filtering. Два facts могут делить collector и dimension exchange. В [CalcMerge](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkCalcMergeRuleTest.xml#L95-L112) результат `random_udf` остаётся в нижнем Calc, когда используется и условием, и выходом. Повторное использование двумя верхними выражениями также сохраняет два Calc (L154–171), тогда как одиночное вложенное применение допускает объединение; неиспользуемая случайная проекция удаляется. Поэтому это не общий запрет объединять недетерминированные функции: fixture различает кратность ссылок на вычисленный результат.

[Limit0](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkLimit0RemoveRuleTest.xml#L1-L204) заменяет `fetch=0`, в том числе с offset, пустым Values. EXISTS пустого подзапроса даёт пустой внешний результат, NOT EXISTS — исходный внешний scan. IN/NOT IN на этом этапе ещё представлены semi/anti join с пустым правым Values. В [PruneEmpty](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkPruneEmptyRulesTest.xml#L1-L246) соответствующий semi затем становится пустым отношением, anti — левым входом. UNION DISTINCT над оставшимися дубликатами сохраняет Aggregate для устранения повторений; EXCEPT с пустым правым входом также не разрешает потерять DISTINCT. Это наблюдения разных наборов правил, а не свидетельство общей неспособности удалить join.

[ConstantRange Rank](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkLogicalRankRuleForConstantRangeTest.xml#L123-L192) преобразует `RANK=2` в Rank с диапазоном 2..2 и последующую константную проекцию ранга; `rk<=2 AND rk>-2` печатает `rankStart=-1`, то есть fixture не показывает принудительное ограничение нижней границы единицей. Дополнительный `a>10` остаётся над Rank. Одинаковые RANK с одним окном объединяются, разные окна и RANK вместе с ROW_NUMBER остаются OverAggregate. В частности, [bounded ROW_NUMBER](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkLogicalRankRuleForConstantRangeTest.xml#L316-L338) здесь остаётся OverAggregate с фильтром: это граница данного ruleset, а не запрет ROW_NUMBER→Rank во всём planner.

### RangeEnd и границы переноса условий через join

В отличие от предыдущего ConstantRange ruleset, [RangeEnd](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkLogicalRankRuleForRangeEndTest.xml#L267-L288) преобразует ограниченный ROW_NUMBER в Rank. Переменное `rk<a` печатается как `rankEnd=a` (L171–192), а `rk=b` — как `rankEnd=b`, без остаточного фильтра (L243–264). Это точная запись golden, а не доказательство эквивалентности строгого неравенства и равенства: семантику переменного диапазона необходимо связывать с реализацией правила и исполнителя. Нижняя переменная граница `rk>a` здесь остаётся OverAggregate+Calc.

[FilterJoin](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkFilterJoinRuleTest.xml#L699-L880) различает левое условие внутри anti join и внешний фильтр: `NOT EXISTS(... WHERE b>2)` сохраняет условие в anti join, поскольку его ложность должна разрешить левую строку; semi-вариант переносит `b>2` в левый вход. Внешний `WHERE b>2` переносится в левый вход обоих типов. NOT IN содержит null-aware условие `IS NULL(left) OR IS NULL(right) OR left=right`, тогда как IN использует обычное равенство.

Для [outer join](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkFilterJoinRuleTest.xml#L884-L1165) правое `ON a2=2` LEFT JOIN фильтрует только правый вход; правое `WHERE a2<1` переводит join в inner и распространяется на оба равных ключа. `WHERE a2 IS NULL` остаётся над LEFT JOIN. FULL с условием только в ON сохраняется full; null-rejecting WHERE по одному входу даёт left/right, по обоим — inner (L253–367). [RightToLeft](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkRightJoinToLeftJoinRuleTest.xml#L94-L140) меняет входы и индексы условий, а отдельная Project восстанавливает исходный порядок столбцов, включая вычисленные ключи и цепочки join.

[SemiAntiJoinJoinTranspose](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkSemiAntiJoinJoinTransposeRuleTest.xml#L51-L354) опускает semi/anti в ту ветвь inner join, от которой целиком зависит условие. Ссылка одновременно на x и y оставляет его над join; в показанных full/left/right случаях он также остаётся сверху (L357–482,609–670). [ProjectTranspose](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkSemiAntiJoinProjectTransposeRuleTest.xml#L19-L94) переносит semi через прямую проекцию и дальше к y, но вычисляемый `d+1` на ключе оставляет semi над Project. [FilterTranspose](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/FlinkSemiAntiJoinFilterTransposeRuleTest.xml#L19-L76) показывает обратный относительно pushdown шаг: semi/anti оказывается под исходным левым фильтром. Поэтому направление одного правила нельзя выдавать за итоговое положение фильтров во всём optimizer.

[EqualityTransfer](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/JoinConditionEqualityTransferRuleTest.xml#L19-L145) преобразует цепочку `a=d AND a=e AND b=d` в локальные `a=b`, `d=e` и одно межвходовое равенство `a=d`. Неравенства остаются отдельными условиями; преобразование видно и для semi EXISTS/IN. Сам этот fixture оставляет новые локальные равенства внутри Join, не показывает физический source pushdown.

### Приведение типов, производные условия и MultiJoin

[TypeCoerce](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/JoinConditionTypeCoerceRuleTest.xml#L19-L196) материализует вычисленные ключи в Project, сохраняя типы исходных выходных полей. INTEGER→BIGINT/DECIMAL/FLOAT/DOUBLE показаны явно. Однако FLOAT IN DOUBLE печатает приведение правого DOUBLE к FLOAT (L87–92), тогда как FLOAT IN DECIMAL приводит оба ключа к DOUBLE (L62–66). Поэтому fixture не доказывает общего обещания только расширяющих, сохраняющих точность приведений. Коррелированный OR в последнем случае разворачивается через dedup ключей корреляции, внутренний join и null-safe обратные равенства (L227–263). [PushExpressions](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/JoinPushExpressionsRuleTest.xml#L19-L126) similarly выносит CAST/`b+1` в левый Project; NOT IN сохраняет null-aware часть отдельно от корреляционного равенства.

[DependentConditionDerivation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/JoinDependentConditionDerivationRuleTest.xml#L19-L81) оставляет исходную дизъюнкцию `(a=1 AND d=2) OR (a=2 AND d=1)` и добавляет необходимые, но недостаточные локальные `a IN(1,2)`, `d IN(1,2)`. Замена исходного условия их конъюнкцией потеряла бы связь пар; golden её не делает. Если OR содержит альтернативу без ограничения данного входа, производное ограничение этого входа не возникает (L142–160,186–204). [DeriveNullFilter](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/JoinDeriveNullFilterRuleTest.xml#L40-L208) добавляет IS NOT NULL в показанных inner equi-join по отдельным входам; no-null-count и below-threshold случаи остаются без фильтра. Порог задан setup теста и не восстанавливается из XML. Outer и non-equi случаи здесь не меняются.

[JoinRemove](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/JoinRemoveRulesTest.xml#L417-L486) удаляет неиспользуемый dept из LEFT JOIN, но сохраняет emp self-join, даже если берётся только левый deptno: неиспользуемые правые столбцы сами по себе не исключают размножение строк. DISTINCT/COUNT DISTINCT над сохраняемым входом допускает удаление ненужной ветви; обращение к правому name оставляет join (L19–145). Это различие кратности и metadata, а не синтаксический dead-column pruning.

[MultiJoin](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/JoinToMultiJoinForReorderRuleTest.xml#L179-L319) собирает плоские inner/некоторые left цепочки, сохраняя outerJoinConditions отдельно от joinFilter. Full остаётся вложенным MultiJoin с isFullOuterJoin=true. У RIGHT JOIN последующий ключ по дополняемому левому входу оставляет вложенную границу, по сохраняемому правому — допускает плоский список (L622–713). Это представление области перестановок, не готовый физический порядок или доказательство произвольной ассоциативности outer join.

[TemporalCorrelate](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/LogicalCorrelateToJoinFromTemporalTableRuleTest.xml#L73-L188) превращает Correlate в Join, но сохраняет Snapshot с коррелированным period. Для temporal T3 добавляет `__INITIAL_TEMPORAL_JOIN_CONDITION` с ключами и proctime либо обеими rowtime; lookup T2 остаётся без этого маркера. [UNNEST](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/LogicalUnnestRuleTest.xml#L19-L310) заменяет коррелированный Uncollect на внутреннюю TableFunctionScan `$UNNEST_ROWS$1`, с отдельной функцией WITH_ORDINALITY и INTEGER полем позиции. [SnapshotProject](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/ProjectSnapshotTransposeRuleTest.xml#L77-L135) проталкивает id/age в lookup source, но age-фильтр остаётся в Calc над Snapshot.

### Partition pruning, limit и watermark capabilities

[FilterScan](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/PushFilterIntoTableSourceScanRuleTest.xml#L211-L280) показывает принятие ITEM массива/map и CAST variant через source capabilities, но [field после ITEM](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/PushFilterIntoTableSourceScanRuleTest.xml#L340-L375) остаётся внешним Filter. Поэтому поддержку nested fields нельзя переносить на произвольную цепочку collection access. [LimitScan](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/PushLimitIntoTableSourceScanRuleTest.xml#L19-L148) задаёт scan limit=offset+fetch, сохраняя внешний Sort с исходным offset/fetch; ORDER BY и offset без fetch не получают source limit. Эталон не утверждает, что локальный лимит источника заменяет глобальное ограничение или сортировку.

Полностью прочитаны обе параметризованные матрицы [legacy partition](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/PushPartitionIntoLegacyTableSourceScanRuleTest.xml#L139-L1074) и [current partition](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/PushPartitionIntoTableSourceScanRuleTest.xml#L139-L1128), включая sourceFetchPartitions/useCatalogFilter и virtual-column варианты. Чистые partition predicates AND/OR превращаются в конкретные списки partitions, фильтр над строками исчезает. Mixed `id>2 OR part1=A` остаётся целиком residual; при дополнительном `AND part2>1` только этот конъюнкт сужает partitions. UDF над part2 в приведённом setup также оценивается для отбора partitions, оставляя id>2 сверху; current TRIM(part1) case отбирает A/2. Совпадение goldens разных способов получения partition lists доказывает ожидаемую форму, но не число catalog RPC, объём listing или производительность.

[INTERSECT DISTINCT](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/ReplaceIntersectWithSemiJoinRuleTest.xml#L19-L119) и [EXCEPT DISTINCT](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/ReplaceMinusWithAntiJoinRuleTest.xml#L19-L119) используют semi/anti join по IS NOT DISTINCT FROM и отдельный Aggregate для dedup. ### Scalar COUNT и anti-subquery matrix

[RewriteSubquery](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/subquery/FlinkRewriteSubQueryRuleTest.xml#L163-L591) использует целочисленную неотрицательность COUNT(*): `>0`, `>0.9`, `>=1`, `>=0.1` и перевёрнутые сравнения становятся semi EXISTS, с correlation equality либо uncorrelated MIN(true)/IS NOT NULL маркером. COUNT(e)>0 сохраняет scalar aggregate, а grouped COUNT в scalar позиции получает SINGLE_VALUE над сгруппированным результатом (L19–78), сохраняя ограничение scalar cardinality. TPC-DS Q41 проходит тот же rewrite с большим OR: все ветви predicates прочитаны, но fixture не доказывает ускорение запроса или корректность на dataset.

Полностью прочитаны **2445 строк** [AntiJoin matrix](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/subquery/SubQueryAntiJoinTest.xml#L19-L2442), включая комбинированные IN/NOT IN/EXISTS/NOT EXISTS, lateral, correlated/noncorrelated, CASE, computed/multi-column keys, nested negations. NOT EXISTS удаляет лишнюю SELECT-проекцию, поэтому `SELECT x.a IS NULL` внутри EXISTS не является условием отбора; lateral table function внутри правого входа остаётся Correlate (L382–613). Левое условие внутри NOT EXISTS/NOT IN остаётся частью anti condition (L487–508,1129–1151), внешний WHERE остаётся внешним фильтром.

Для NOT IN простая форма использует `left IS NULL OR right IS NULL OR left=right`; tuple форма AND-ит такие условия по всем компонентам (L2369–2442), что сохраняет ложную компоненту даже при NULL в другой. Non-NULL CASE output убирает ненужную левую IS NULL ветвь (L1924–1946). Когда IN/NOT IN нужен как CASE value, дополнительные global/per-correlation COUNT/COUNT(nonNull), dedup и LEFT join markers различают empty, match и unknown; их нельзя заменить анти-join, отбрасывающим строки (L71–133,1155–1357,2168–2219).

Граница интерпретации: [ComplexCondition6](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/test/resources/org/apache/flink/table/planner/plan/rules/logical/subquery/SubQueryAntiJoinTest.xml#L1473-L1499) печатает для коррелированного глобального SUM(e)*5 grouped-by-d правый вход anti join без видимого восстановления отсутствующей группы. SQL scalar/global aggregate и grouped aggregate имеют разную empty-input семантику; этот golden в отдельном ruleset сам по себе не подтверждает её сохранение во всём pipeline и не является результатом runtime проверки. Это зафиксированное различие представлений, требующее связи с production rewrite и другими стадиями, а не объявление runtime дефекта.

Текущий personally confirmed extra slice: **249 файлов / 110029 строк**, остаток **507 файлов / 201914 строк**. Чтение продолжается.
