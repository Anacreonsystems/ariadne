# 09. Текстовые ресурсы: миграционные образы и визуальное представление

Исследуется checkout Flink `068f428b29f4d9ee587fa1006d2f1a69b43c0000`. Эта глава отделяет сведения из сохранённых текстовых fixtures от поведения Java-кода [checkpoint/state storage](03-state-checkpoints-windows-timers.md) и [интеграционных проверок](07-build-boundaries-tests-web.md). Чтение переданного остатка началось после полного буквального закрытия исходных 388 013 строк control. Исходный inventory owner=root и знаменатель исследования сохраняются. В момент передачи оставались 776 текстовых файлов, 152 357 строк; этот переданный остаток теперь прочитан полностью, каждый файл отдельно, с точными подтверждёнными диапазонами. Бинарные snapshot/SST/metadata файлы этим чтением не декодируются.

## 1. Что показывает файл options

Первый полностью прочитанный options fixture из native savepoint Flink 1.16 явно сообщает RocksDB 6.20.3 и options_file_version1.1. Он сохраняет DBOptions, затем отдельные CFOptions/TableOptions для `default`, `_timer_state/processing_user-timers` и `_timer_state/event_user-timers`. Это свидетельство физического разделения timer namespaces в конкретном сохранённом DB image. Из самих имён и настроек нельзя получить доказательство восстановления timer callback или exactly-once после сбоя: для этого нужны вызывающий код и assertions, разобранные в главах 03/07. [Версия и DBOptions](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.16-rocksdb-savepoint-native/66d713b7-9829-4198-9050-1148e656474a#L7), [Processing timer family](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.16-rocksdb-savepoint-native/66d713b7-9829-4198-9050-1148e656474a#L182), [Event timer family](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.16-rocksdb-savepoint-native/66d713b7-9829-4198-9050-1148e656474a#L273).

В этом fixture `wal_dir` содержит абсолютный временный путь машины генерации, включая job/operator/attempt directory. Его следует читать как происхождение образа, не как переносимую конфигурацию deployment. `atomic_flush=false`, `use_fsync=false`, WAL recovery mode и compaction/cache settings описывают RocksDB-образ; они сами не отменяют и не устанавливают Flink checkpoint protocol. В частности, наличие options text не доказывает, какие из значений применяются при восстановлении текущим backend. [Путь генерации и flags](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.16-rocksdb-savepoint-native/66d713b7-9829-4198-9050-1148e656474a#L32).

Уже в полностью прочитанных checkpoint fixtures Flink 1.17 появляются десятичные значения с запятой: `memtable_prefix_bloom_size_ratio=0,000000`, `blob_garbage_collection_age_cutoff=0,250000`, `max_bytes_for_level_multiplier=10,000000` и `data_block_hash_table_util_ratio=0,750000`. В первом прочитанном Flink 1.16 fixture те же виды значений записаны с точкой. Это фактическое различие текстового представления; без чтения вызываемого parser/load-options пути нельзя объявлять его ни допустимой нормализацией, ни причиной отказа восстановления. [Запятая в fixture](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.17-rocksdb-checkpoint/0193581b-bd07-4b9d-b5d3-a6c986164fa4#L102).

Версия Flink в имени каталога не совпадает автоматически с версией RocksDB: первый полностью прочитанный checkpoint fixture Flink 1.19 всё ещё сообщает 6.20.3. От предыдущих прочитанных 1.18 образов его текст отличается `avoid_flush_during_shutdown=true` и явным `compression_per_level=kSnappyCompression` во всех трёх families. Это даёт конкретный пример эволюции сохранённой конфигурации при прежнем engine version; переносить эти значения в рекомендации текущему deployment без trace backend-options нельзя. [Версия и shutdown option](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.19-rocksdb-checkpoint/26f4ed93-f4f7-4fe8-9848-b17dd1d993da#L7), [Per-level compression](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.19-rocksdb-checkpoint/26f4ed93-f4f7-4fe8-9848-b17dd1d993da#L143).

## 2. Однострочный указатель и граница доказательства

Все переданные однострочные текстовые ресурсы прочитаны отдельно. Среди образцов broadcast migration строка содержит `MANIFEST-000004` в каталоге Flink 1.16 и `MANIFEST-000005` в каталоге Flink 2.0. Это имя физического manifest в соответствующем сохранённом образе. Сам указатель не содержит ни списка SST, ни checkpoint identifier, ни подтверждений операторов; содержимое бинарного manifest этим текстовым чтением не устанавливается. Поэтому существование указателя вместе с options позволяет описать состав fixture, но успешность совместимого восстановления определяется вызывающим тестом и его проверками из главы 07. [Указатель 1.16](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.16-rocksdb-savepoint-native/38d42b00-e95f-4ece-9181-aa6b2cf112c8#L1), [Указатель 2.0](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink2.0-rocksdb-checkpoint/0110d0b3-f6cb-476a-bb14-b11749aebdc0#L1).

В первых прочитанных options образца Flink 1.20 версия RocksDB также остаётся 6.20.3, а `wal_dir` сохраняет путь временного MiniCluster генератора. Число в имени manifest и версия в имени каталога имеют разные роли: первое адресует файл внутри DB image, второе обозначает исторический набор миграционных ресурсов. Ни одно не задаёт само по себе полную матрицу совместимости. [Образец 1.20](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink1.20-rocksdb-checkpoint/069887f0-ab63-4081-8614-87ddbb0ff56f#L7).

В первом полностью прочитанном checkpoint fixture Flink 2.0 меняется уже сам engine: `rocksdb_version=8.10.0`. При том же `options_file_version=1.1` текст содержит больше параметров, `fail_if_options_file_error=true`, checksum `kXXH3` для трёх block tables и структурную запись merge operator с delimiter. Это показывает, почему одного номера options format недостаточно для описания физической совместимости: значимы engine, семейства колонок и их параметры. Отдельная настройка `fail_if_options_file_error` относится к options RocksDB и сама не определяет политику ошибок всего Flink restore. [Engine и DBOptions 2.0](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink2.0-rocksdb-checkpoint/2eec98b5-adc5-401b-ab70-25523db73d43#L7), [Merge и table format](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink2.0-rocksdb-checkpoint/2eec98b5-adc5-401b-ab70-25523db73d43#L164).

Следующий прочитанный checkpoint fixture Flink 2.1 сохраняет engine 8.10.0, но задаёт `periodic_compaction_seconds=2592000` для default и обоих timer families; в прочитанных образцах 2.0 это значение равно нулю. Рядом присутствует RocksDB `ttl=2592000`. Эти физические параметры нельзя отождествить с пользовательским Flink state TTL или с моментом срабатывания таймера: такую семантику задают state descriptors, backend и timer service, рассмотренные в главе 03. [Compaction в образце 2.1](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-tests/src/test/resources/new-stateful-broadcast-udf-migration-itcase-flink2.1-rocksdb-checkpoint/006b7cb5-7a76-4164-ae94-76c5aca3da5e#L141).

В полностью прочитанном checkpoint-наборе `new-stateful-udf` Flink 1.16 встречаются три состава DB image: `default` с `state-name` у StreamFlatMap, `default` с двумя timer families у первого subtask timely-оператора и все четыре families у других его subtasks. Для совместимости нужно связать конкретный ресурс с путём загрузки backend и assertions миграционного теста; номер каталога и текст options по отдельности этого не заменяют. ## 4. Визуальные ресурсы: открытая область чтения

После закрытия ресурсов тестов переданы оставшиеся текстовые файлы `docs/static/fig/` и `docs/static/font-awesome/`. Их буквальное чтение XML, path и CSS продолжается отдельно, при неизменном inventory owner=root. Непрочитанные файлы и части длинных строк не считаются подтверждёнными. Код визуального представления сам по себе не устанавливает runtime-инварианты, порядок событий или гарантии восстановления; такие связи требуют причинного пути реализации.


Первый полностью прочитанный SVG `ClientJmTm` содержит самостоятельные текстовые подписи Client/Compiler/Optimizer, Submit Job, JobManager/Scheduling/Resource Management, TaskManager/Task Execution/Data Exchange и Exchange Intermediate Results (shuffle/broadcast), а также координаты paths и стили Inkscape. Это обзорная группировка обязанностей: широкая подпись Resource Management внутри JobManager не задаёт границу Java-класса JobMaster и не заменяет разделение Dispatcher/ResourceManager/Scheduler, установленное кодом в главе 01. Стрелки изображения не кодируют fencing token, acknowledgment, повторные попытки или устойчивое подтверждение выполнения. [Подписи control plane](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/ClientJmTm.svg#L167), [Обмен результатов](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/ClientJmTm.svg#L298).


`FlinkOnK8s` явно разводит Deployment Flink Master с Dispatcher, JobMaster и K8sResMngr, Service с selector, worker pods, ConfigMap и registry. Схема YARN группирует Flink JobManager с YARN AppMaster, показывает выделение worker containers и сохранение Uberjar/config в HDFS. Последняя подпись «Always Bootstrap containers with Uberjar and config» принадлежит этому рисунку; она не доказывает универсальное обязательное использование HDFS или единственную политику запуска всех режимов. Реальные ветвления запуска, владение процессами и HA attempts разобраны по реализации в главе 01. [Kubernetes](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/FlinkOnK8s.svg#L118), [YARN](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/FlinkOnYarn.svg#L126).

Полностью прочитанные `async_io` и `checkpoint_tuning` изображают разные виды ожидания. Первый сопоставляет sendRequest/receiveResponse и перекрытие нескольких запросов к database; в нём нет retry, timeout, checkpoint state или транзакции внешнего сервиса. Второй различает базовый interval, длительность checkpoint и минимальное время между checkpoint: при позднем завершении следующий checkpoint может занимать почти всё время, а pause оставляет промежуток обработки. Подпись «Guaranteeing Progress» описывает эту временную иллюстрацию, без доказательства общей живости при backpressure, остановке источника или отказах storage. Такие условия проверяются отдельно в runtime и тестах глав 03/07. [Async I/O](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/async_io.svg#L291), [Minimum pause](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/checkpoint_tuning.svg#L421).


Полный XML `checkpointing` показывает четыре последовательных состояния рисунка: starting, два in progress и completed. В таблице Master появляются source positions 6791/7252/5589/6843, затем `State 1: ptr1`, `State 2: ptr2`, а pending у двух sink сменяется ack. Это различает сохранённые позиции чтения и ссылки на данные state; оно согласуется с разделением coordinator metadata и backend handles, исследованным в главе 03. Однако таблица изображения не является форматом `CompletedCheckpoint`, а подпись sink acknowledgment после всех barriers не доказывает commit внешней транзакции: в XML отсутствуют вызовы sink API, external commit и обработка неоднозначного результата. Схема также не задаёт альтернативный unaligned путь или recovery при незавершённом snapshot. [Barrier и acknowledgment](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/checkpointing.svg#L347), [State pointers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/checkpointing.svg#L1015), [Sink ack](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/checkpointing.svg#L1431).


Схемы `concepts/stream_barriers` и `concepts/stream_aligning` буквально различают barrier n/n−1, newer/older records, input/output buffers и шаги begin alignment → end alignment → checkpoint. Геометрия задерживает один вход до появления второго barrier, затем показывает state backend; это иллюстрация согласованного среза двух каналов. Она не задаёт общий порядок между разными inputs, scheduler fairness или завершение storage future. В `connected-streams` отдельная стрелка control stream входит в тот же оператор, что data in: такая визуальная стрелка не отождествляет пользовательский connected stream с control-plane RPC или OperatorEvent gateway из глав 01/02. [Alignment](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/concepts/stream_aligning.svg#L145), [Control stream](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/connected-streams.svg#L57).

Визуальное кодирование неоднородно: `click-event-count-example` содержит HTML foreignObject с входными JSON и оконными результатами, плюс fallback `[Not supported by viewer]`; `datastream-example-job-graph` хранит весь рисунок в одной строке SVG с glyph paths вместо обычных text nodes. Полная строка последнего прочитана отдельными диапазонами символов, без rendering. Поэтому plain-text извлечение подписи по text nodes не является полным чтением этих ресурсов. Пример click count задаёт представление topic input/output и 15-секундного окна на рисунке; перечисленные counts 1000 не служат результатом запуска теста или доказательством exactly-once. [Click example](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/click-event-count-example.svg#L21), [Glyph paths](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/datastream-example-job-graph.svg#L21).


`delegation_token_framework` содержит последовательность start cluster → load providers → obtain tokens → authenticate/check credentials → store → update worker tokens → connector get token/connect. Важна прямая оговорка самого рисунка: некоторые системы объединяют authentication service и token service, тогда шаги 4–6 выполняются одним шагом. Следовательно, число нарисованных внешних RPC не является обязательным протоколом для каждого provider. Название TokenStore на схеме не устанавливает персистентность, атомарность распространения по workers или лидерское fencing; это подтверждается конкретными manager/provider/receiver путями, а не прямоугольником store. [Полный SVG и текст оговорки](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/docs/static/fig/delegation_token_framework.svg#L23).
