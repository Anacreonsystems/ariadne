Фиксация: Apache Flink `068f428b29f4d9ee587fa1006d2f1a69b43c0000`. Эта глава описывает только фактически прочитанный код. Точные подтверждённые диапазоны находятся в `readers/table.confirmed.jsonl`; экспозиции инструмента сами по себе чтение не подтверждают. ## 1. Синхронная оконная агрегация TVF: фактическая граница ответственности

`WindowAggOperator<K,W>` — оболочка жизненного цикла, timer service и checkpoint вокруг `SyncStateWindowProcessor<W>`. В ней нет SQL-парсера и нет собственного алгоритма `SUM`: `processElement` передаёт текущий ключ и `RowData` процессору, а возвращённый `boolean` означает отбрасывание записи и увеличивает late metric через meter. Таймер выбирает ключ, вызывает `fireWindow`, затем `clearWindow`. Оператор считает, что у окна один текущий таймер, и отдельно его не удаляет. Коллектор создаётся с очищенным timestamp: timestamp входного StreamRecord не переносится автоматически на результат. [WindowAggOperator:132–265](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/window/tvf/common/WindowAggOperator.java#L132).

Слои образуют цепочку:

```text
WindowAggOperator.processElement
  → AbstractSliceSyncStateWindowAggProcessor.processElement
    → SliceAssigner.assignSliceEnd
    → RecordsWindowBuffer.addElement(key, namespace, row)
      → binary WindowBytesMultiMap
progress / checkpoint / нехватка памяти
  → RecordsWindowBuffer.flush
    → AggCombiner.combine
      → setCurrentKey
      → windowState.value / createAccumulators
      → setAccumulators → accumulate | retract
      → windowState.update → registerEventTimeWindowTimer
watermark → processor.advanceProgress → super.processWatermark → timer callback
  → setCurrentKey → fireWindow → clearWindow
```

Буфер — временная managed-memory оптимизация, accumulator — keyed state с namespace окна. Descriptor состояния называется `window-aggs`; namespace serializer задаёт процессор. `PerWindowStateDataViewStore` привязывает дополнительные data views агрегатной функции к тому же backend/namespace. Сгенерированный `NamespaceAggsHandleFunction` создаётся через user-code classloader, а не через загрузчик вызывающего API. [AbstractSyncStateWindowAggProcessor:64–85](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/AbstractSyncStateWindowAggProcessor.java#L64).

## 2. Watermark, восстановление и порядок действий

Watermark — checkpointed operator state, не просто transient метрика. `initializeState` получает union list state `watermark`, а после восстановления берёт минимум присланных значений. `snapshotState` пишет единственное текущее значение. В `open` сначала восстанавливается watermark timer service, затем открывается процессор, затем ему передаётся initial watermark. Комментарий прямо связывает этот порядок с недопущением повторного принятия истёкших данных при flush буфера. [WindowAggOperator:138–205](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/window/tvf/common/WindowAggOperator.java#L138).

Новый event-time watermark сначала продвигает процессор (в частности, сбрасывает буфер в state), затем передаётся базовому оператору. Это необходимо до исполнения timer callbacks, читающих аккумуляторы. Watermark не должен продвигать processing-time window: соответствующая ветка намеренно пропускает `advanceProgress`. Меньший или равный watermark заменяется текущим перед передачей дальше. При processing-time callback новый timestamp сначала продвигает процессор, затем исполняет окно; повторные callbacks одного timestamp не повторяют advance. `prepareSnapshotPreBarrier` вызывает `prepareCheckpoint`, а slicing processor безусловно flush-ит буфер. [WindowAggOperator:226–270](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/window/tvf/common/WindowAggOperator.java#L226).

## 3. Late data, slices и changelog

Докстринг оператора о сбросе late elements нельзя переносить на все slices буквально. `AbstractSliceSyncStateWindowAggProcessor` проверяет сначала конец slice, затем конец последнего затрагиваемого окна. Если slice уже fired, но последнее окно ещё нет, запись **принимается** в `sliceStateMergeTarget(sliceEnd)`, а таймер ставится на первое ещё не fired окно. Только когда последнее окно тоже fired, метод возвращает dropped=true. Это особенно существенно для hopping/cumulative: промежуточный slice может быть поздним относительно одного результата и полезным для следующего. [AbstractSliceSyncStateWindowAggProcessor:95–125](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/AbstractSliceSyncStateWindowAggProcessor.java#L95).

`AggCombiner` различает accumulate/retract по `RowDataUtil.isAccumulateMsg`: изменяемый вход не равен исключительно append-only. Однако выход текущего `WindowAggProcessorBase.collect` документирован как `RowKind.INSERT`; early/late firing и changelog-result оставлены TODO. Нельзя обещать пользователю произвольный changelog-output лишь потому, что внутренний combiner умеет retract. Результат составляется переиспользуемым `JoinedRowData` из текущего ключа и значения агрегата. [AggCombiner:75–115](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/combines/AggCombiner.java#L75), [WindowAggProcessorBase:108–119](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/WindowAggProcessorBase.java#L108).

Shared processor вызывает assigner.mergeSlices с callback: null merge target означает временный accumulator вне state; непустой target означает загрузку/создание base accumulator и сохранение результата обратно в namespace. Затем он подавляет empty output и назначает следующий timer даже без новых records. Hopping требует позиции COUNT(*) в accumulator: иначе нельзя определить пустоту и необходимость продолжения timers. Unshared processor читает один namespace, создаёт accumulator при отсутствии, подавляет пустоту и выдаёт результат. При cleanup удаляются `expiredSlices(windowEnd)` и вызывается `aggregator.cleanup(slice)`, чтобы очистить также data views. [SliceSharedSyncStateWindowAggProcessor:64–130](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/SliceSharedSyncStateWindowAggProcessor.java#L64), [AbstractSliceSyncStateWindowAggProcessor:159–178](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/AbstractSliceSyncStateWindowAggProcessor.java#L159).

## 4. Память, мутабельность и ошибки

`RecordsWindowBuffer` хранит records в `WindowBytesMultiMap` по `(sliceEnd,key)`. При EOF append он flush-ит существующие ключи и повторяет запись; если буфер уже пуст, запись слишком велика и исходное исключение выходит наружу. Это не бесконечный retry. После flush проверяется пустота. `minSliceEnd` позволяет не flush-ить на каждый watermark, пока ни один buffered window не готов к firing. На flush combiner вызывается для каждой записи map, затем память логически reset-ится и min возвращается к MAX_VALUE. Factory выбирает копирование по `!stateBackend.isSafeToReuseKVState()`: это защита heap state от переиспользуемых ключей/строк. Закрытие сначала освобождает binary buffer, затем закрывает combiner. Исключения `combine` не проглатываются, reset не находится в finally. [RecordsWindowBuffer:80–131](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/buffers/RecordsWindowBuffer.java#L80).

Функции и буферы имеют раздельный close: процессор закрывает свой aggregator, затем window buffer, который закрывает aggregator combiner-а. Оператор сначала вызывает `super.close`, обнуляет collector, затем закрывает процессор. В этих методах последовательный cleanup не защищён общим finally: это наблюдение о локальном коде, а не доказательство утечки всего runtime, поскольку внешний lifecycle ещё не прочитан. [AbstractSliceSyncStateWindowAggProcessor:173–178](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/AbstractSliceSyncStateWindowAggProcessor.java#L173).

## 5. Session windows: state namespace и фактическое окно

Unslicing processor использует `MergingWindowProcessFunction` и trigger `afterEndOfWindow`; allowed lateness жёстко 0. `assignStateNamespace` определяет accumulator namespace, тогда как `assignActualWindow` определяет реальное окно и timer. Проверяется согласованность Optional: либо оба присутствуют, либо оба отсутствуют. В присутствующий namespace сразу применяется accumulate/retract и state update. Timer регистрируется в epoch milliseconds с timezone преобразованием от `actualWindow.maxTimestamp()`. Fire сначала подготавливает aggregate accumulator к emit через merging function, затем спрашивает trigger, затем подавляет пустой результат. Clear делегирован `cleanWindowIfNeeded`. Здесь `advanceProgress` и `prepareCheckpoint` пусты: slicing-buffer у этого пути нет. [UnsliceSyncStateWindowAggProcessor:93–199](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/UnsliceSyncStateWindowAggProcessor.java#L93).

Window context очищает accumulator и aggregate data views вместе, удаляет timers старых окон и передаёт merge событие trigger-у. Merging trigger state допускает лишь `InternalMergingState`: иной descriptor даёт `IllegalArgumentException`, обёрнутый в `RuntimeException("Error while merging state.")`. Partitioned trigger state в показанном context получается с `VoidNamespace`. Это разные пространства: accumulator окна, bookkeeping merging function и trigger state нельзя без анализа объединять в одну TTL map. Продолжение чтения самой merging function и её mapping приведено ниже в §8. [UnsliceSyncStateWindowAggProcessor:219–395](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/processors/UnsliceSyncStateWindowAggProcessor.java#L219).

## 6. Builder как проверка допустимости runtime-плана

Builder выбирает sync slicing/shared/unshared или sync unslicing. Для slicing создаёт RecordsWindowBuffer с обычным либо global combiner. Async путь отдельно запрещает global aggregation и неслайсовые assigners и требует generated key equaliser. Следовательно пример Javadoc с session + async не доказывает поддержку: исполняемые guards принимают только SliceAssigner. Эти ограничения нужно проверять в планировщике и тестах далее. [WindowAggOperatorBuilder:181–307](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/aggregate/window/WindowAggOperatorBuilder.java#L181).

## 7. Инварианты для проверки собственного движка Ariadne

Это исследовательские выводы для будущей архитектуры; они не изменяют утверждённые ADR.

1. До timer firing все buffered records соответствующего progress должны быть отражены в checkpointable state; до checkpoint barrier незаснятый буфер должен быть flush-нут либо сам сниматься.
2. После restore progress и timer-service progress должны согласоваться до первого flush. При перераспределении partitions нельзя случайно принять максимальный watermark как общий безопасный frontier.
3. Оконный state имеет ключ и namespace; текущий ключ меняется явно перед вызовами state и регистрацией таймеров.
4. Поздность записи определяется всеми ещё изменяемыми результатами, а не исключительно первым slice. Final output policy, allowed lateness и retract-input capability — независимые контракты.
5. Cleanup accumulator должен включать data views; merging session state требует удаления superseded timers и согласованного отображения actual window в state namespace.
6. Reused rows и keys требуют явного ownership/copy contract. Memory overflow должен различать flush-able capacity pressure и record-too-large failure.
7. Выбор sync/async и one-stage/global — часть проверяемой допустимости плана; название API и пример в комментарии недостаточны.

`MergingWindowSet` хранит checkpointed `MapState<actualWindow,stateWindow>` и transient LRU из sorted windows по ключу (10000 ключей). `initializeCache(key)` обязателен до add/retire; на cache miss sorted set восстанавливается из map. ## 9. TableEnvironment → Parser → Planner: полный прочитанный верхний путь

Полностью прочитан `TableEnvironmentImpl` (1635 строк). Создание окружения строит mutable user classloader, обнаруживает ExecutorFactory, создаёт catalog/secret stores, TableConfig с root configuration executor-а, ResourceManager, ModuleManager, CatalogManager с default in-memory catalog, FunctionCatalog и Planner через PlannerFactoryUtil. `OperationTreeBuilder` получает function lookup, schema data type factory, parser функций/выражений и streaming mode; CatalogManager инициализирует schema resolver. Окружение владеет контекстом имен, конфигурацией и dispatcher-ом операций, а не выполняет RowData операторы само. [TableEnvironmentImpl:197–352](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-api-java/src/main/java/org/apache/flink/table/api/internal/TableEnvironmentImpl.java#L197).

```text
TableEnvironmentImpl.executeSql(sql)
  → getParser().parse(sql) → ровно одна Operation
  → executeInternal(operation)
    → ExecutableOperation.execute(context) для локальных operation-контрактов
    → ModifyOperation / StatementSet → translate(modifies)
    → QueryOperation → CollectModifyOperation → translate
translate → PlannerBase.translate
  → beforeTranslation
  → translateToRel (queryOperation builder + sink schema/casts/abilities)
  → Optimizer.optimize
  → только FlinkPhysicalRel допустим
  → ExecNodeGraphGenerator.generate
  → ExecNodeGraphProcessor.process (последовательно)
  → translateToPlan → List<Transformation<?>>
  → afterTranslation
TableEnvironmentImpl → Executor.createPipeline → Executor.executeAsync → JobClient/TableResult
```

`sqlQuery` возвращает Table над QueryOperation, не запуская job; modify operation отвергается. `executeSql` разбирает ровно одну операцию и dispatch-ит. Query оборачивается collect sink и возвращает schema исходного QueryOperation; result provider перед повторным job reset-ится, затем получает JobClient, а cached DQL plan сохраняет operation/sink/transformations. DML result schema содержит названия sinks и BIGINT значения `-1` для affected rows. `TABLE_DML_SYNC` заставляет await; при interrupted/execution error вызывается cancel и ошибка оборачивается TableException. `createPipeline` получает только локальную конфигурацию, чтобы не повторять root configuration. State layout зависит от доказанной уникальности входа:

| Факт о входе | Inner-side state внутри join key | Outer-side state |
|---|---|---|
| Unique key содержится в join key | ValueState(record) | ValueState(record, associations) |
| Unique key есть, но join key его не содержит | MapState(uniqueKey → record) | MapState(uniqueKey → record, associations) |
| Unique key нет | MapState(record → multiplicity) | MapState(record → multiplicity, associations) |

Без unique key одинаковая строка — дополнительный экземпляр multiset, не upsert; getRecord намеренно возвращает null. Итератор разворачивает multiplicity в повторяющиеся строки. Для outer state associations — число matches на другой стороне, не число одинаковых строк своей стороны. Именно transitions 0→1 и 1→0 управляют DELETE/INSERT null-padding. [JoinRecordStateViews:45–244](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/join/stream/state/JoinRecordStateViews.java#L45), [OuterJoinRecordStateViews:47–343](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/operators/join/stream/state/OuterJoinRecordStateViews.java#L47).

На входе StreamingJoinOperator запоминает RowKind, затем нормализует row к INSERT для state identity. ## 14. Retention — ограничение семантики, а не только памяти

Положительный retention включает StateTtlConfig OnCreateAndWrite + NeverReturnExpired; неположительный выключает TTL. Read не продлевает TTL. Join state factories включают его на соответствующем ValueState/MapState. Это processing-time retention в прочитанных harness: `setStateTtlProcessingTime`. Он отличается от event-time window finality. Тест с left TTL=4000/right TTL=1000 сначала выдаёт join, после expiry правой записи left update не выдаёт ничего, после expiry левой новая правая запись тоже ничего. При disabled TTL те же события дают matches. Для outer joins expiry меняет null-padding поведение; expired retract state может игнорироваться. Поэтому «сократить TTL без изменения результатов» для произвольного unbounded join неверно без domain bound или принятой политики потери истории. [StateConfigUtil:32–39](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/main/java/org/apache/flink/table/runtime/util/StateConfigUtil.java#L32), [StreamingJoinOperatorTest:129–194](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-runtime/src/test/java/org/apache/flink/table/runtime/operators/join/stream/StreamingJoinOperatorTest.java#L129).

## 16. Schema — планировочный контракт и переносимый row type

Полностью прочитаны Column (385 строк), ResolvedSchema (348), DefaultSchemaResolver (560). ResolvedSchema хранит разрешённые columns, watermark specs, primary key, indexes и immutable columns; этот объект намеренно не Serializable и не предназначен для передачи connector-у. Переносимый row type имеет три разных projection-контракта:

| Метод | Состав полей |
|---|---|
| toSourceRowDataType | physical + computed + metadata |
| toPhysicalRowDataType | только physical |
| toSinkRowDataType | physical + persisted metadata; без computed и virtual metadata |

Во всех трёх row type становится NOT NULL как целое, а time attribute снимается с каждого поля: ROWTIME/PROCTIME принадлежит столбцу конкретной схемы, и его нельзя неявно переносить через произвольный composite field в другой контекст. Primary key и immutable indices вычисляются относительно **physical projection**, не общей последовательности столбцов. Metadata column не physical, но может быть persisted; computed column не physical и не persisted. [ResolvedSchema:208–287](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-common/src/main/java/org/apache/flink/table/catalog/ResolvedSchema.java#L208), [там же:331–346](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-common/src/main/java/org/apache/flink/table/catalog/ResolvedSchema.java#L331).

Resolver сначала отвергает duplicate column names и duplicate metadata keys, разрешает physical/metadata типы, затем computed expressions на source columns. Далее разрешает watermark, помечает rowtime, проверяет PK, indexes и immutable constraint. Computed columns получают resolved expression output type; ошибки сохраняют context имени столбца. Для watermark допускается не больше одного определения, time column должна существовать и иметь TIMESTAMP/TIMESTAMP_LTZ precision 0..3, не PROCTIME. Watermark expression разрешается с ожидаемым типом столбца и должна иметь тот же type root; выход также проверяется на timestamp/precision. ROWTIME tag добавляется лишь в streaming mode. Здесь валидируется декларация; соблюдение уникальности и immutable values на реальном входе этим классом не обеспечивается. Он измеряет длину исходного кода, а не окончательный размер bytecode, поэтому threshold — эвристика; окончательная проверка остаётся за компилятором. POM закрепляет ANTLR 4.7, генерацию visitors и relocation runtime в table-shaded namespace. JavaCodeSplitter сначала возвращает короткий input без преобразований; иначе cache key содержит **весь source + оба limits**. Cache ограничен 300 soft values и 5 минутами после доступа. Перед uncached rewrite сбрасывается thread-local счётчик имён, обеспечивающий одинаковое именование для одинакового input без зависимости от истории потока. Порядок зависимостей строгий: ReturnValueRewriter → DeclarationRewriter → BlockStatementRewriter → FunctionSplitter → MemberFieldRewriter → удаление пустых строк. Если DeclarationRewriter возвращает null, итогом становится исходный source. Cache execution failures разворачиваются в RuntimeException с cause. Blank-line cleanup использует настоящий newline; присутствие triple quotes отключает cleanup, чтобы не менять будущие Java text blocks, хотя текущая grammar остаётся Java8 и сама такая защита не доказывает поддержку text blocks parser-ом. [JavaCodeSplitter:43–95](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-code-splitter/src/main/java/org/apache/flink/table/codesplit/JavaCodeSplitter.java#L43), [CodeSplitUtil:33](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-code-splitter/src/main/java/org/apache/flink/table/codesplit/CodeSplitUtil.java#L33).

Промежуточное представление — parse tree и token intervals, а не typed IR. Длинный non-void method сначала получает field для return value и void implementation; затем локальные переменные выносятся в class fields, чтобы extracted methods видели прежние значения. DeclarationRewriter переименовывает коллизии с members/другими hoisted locals; enhanced-for оставляет iteration variable локальной и копирует её в поле на входе body. Block splitting сохраняет IF/WHILE control structure и порядок statements, извлекая вложенные тела; grouping объединяет подходящие соседние statements. FunctionSplitter переносит `return` через class boolean marker, сбрасывает его в начале invocation и проверяет после helper calls. Return/jump counters ограничивают преобразования; anonymous classes/lambda имеют отдельные границы обхода. Это создаёт mutable execution fields у generated instance, поэтому instance ownership/reentrancy — часть контракта generated operator, а не деталь форматирования. Здесь не доказана пригодность splitter для произвольного пользовательского Java. [ReturnValueRewriter:105](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-code-splitter/src/main/java/org/apache/flink/table/codesplit/ReturnValueRewriter.java#L105), [DeclarationRewriter:140](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-code-splitter/src/main/java/org/apache/flink/table/codesplit/DeclarationRewriter.java#L140), [FunctionSplitter:112](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-code-splitter/src/main/java/org/apache/flink/table/codesplit/FunctionSplitter.java#L112).

MemberFieldRewriter уменьшает количество members, группируя поля одинакового текстового типа в arrays; отдельно переносит initialization, учитывает вложенные class scopes и избегает parameter/local shadowing. Он требует поддерживаемой формы declarations и уникальных names. Grammar явно добавляет this/super constructorCall как expression, что проверено JavaParserTest; это важная граница для constructors при последующих transformations. Собственный FlinkTokenStreamRewriter сохраняет конфликтные interval-edit правила ANTLR, но getText не должен разрушать накопленные edits; перекрывающиеся incompatible replacements приводят к exception, а covered inserts/deletions сливаются либо отбрасываются по заданному порядку. [MemberFieldRewriter:254](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-code-splitter/src/main/java/org/apache/flink/table/codesplit/MemberFieldRewriter.java#L254), [JavaParser:483–500](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-code-splitter/src/main/antlr4/JavaParser.g4#L483).
