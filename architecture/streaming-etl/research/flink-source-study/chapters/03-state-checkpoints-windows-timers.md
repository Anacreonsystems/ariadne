## Окно — namespace состояния, а не отдельный исполняемый процесс

`WindowOperator` связывает четыре независимых решения: `WindowAssigner` выбирает ноль или несколько окон для входа; backend хранит содержимое; `Trigger` решает, когда вызвать пользовательскую функцию и очищать ли содержимое; cleanup timer определяет окончательное освобождение окна. Ключ уже установлен в keyed backend до `processElement`; оператор берёт его через `getCurrentKey`, а окно устанавливает как namespace перед `add/get/clear`. Поэтому элемент sliding window может попасть в несколько panes, каждый с одной парой `(key, window)`. Поля transient содержат рабочие ссылки, а само состояние принадлежит backend: в `open` оператор получает или восстанавливает state по descriptor и window serializer. [Создание и обработка](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/WindowOperator.java#L229-L435).

Фраза Javadoc об «экземпляре trigger на pane» не разрешает хранить mutable per-pane state в объекте `Trigger`: интерфейс прямо запрещает это, поскольку экземпляр может переиспользоваться между ключами и пересоздаваться. Состояние trigger должно запрашиваться через `TriggerContext.getPartitionedState`, который направляет запрос к backend с текущими key и window namespace. Сам `Context` — переиспользуемый носитель текущих полей. [Контракт Trigger](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/triggers/Trigger.java#L31-L118), [реализация context](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/WindowOperator.java#L831-L934).

Обычный путь записи имеет строгую последовательность: assign → отклонение закрытого окна → выбор namespace → добавление → `trigger.onElement` → при FIRE чтение аккумулятора и вызов user function → при PURGE очистка содержимого → регистрация cleanup. FIRE и PURGE — независимые биты. FIRE оставляет данные, PURGE не вызывает user function, FIRE_AND_PURGE сначала выдаёт результат. Пустое содержимое не вызывает функцию даже при FIRE. Выход получает timestamp `window.maxTimestamp()`, а не timestamp последнего входа. [Флаги](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/triggers/TriggerResult.java#L21-L65), [emit/cleanup](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/WindowOperator.java#L556-L583).

`CountTrigger` увеличивает `ReducingState<Long>` с именем `count`; при пороге очищает именно счётчик и возвращает FIRE. Следовательно, `CountTrigger.of(N)` сам по себе не означает непересекающиеся пачки по N: накопленное содержимое pane остаётся. `PurgingTrigger` превращает любое nested FIRE в FIRE_AND_PURGE. `CountEvictor`, напротив, ограничивает набор элементов, удаляя первые `size−maxCount` итератором, и выбирает before либо after evaluation. Это разные измерения политики: частота вычисления, сохранение содержимого и выбор элементов. [CountTrigger](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/triggers/CountTrigger.java#L37-L82), [PurgingTrigger](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/triggers/PurgingTrigger.java#L43-L75), [CountEvictor](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/evictors/CountEvictor.java#L49-L80).

`EvictingWindowOperator` хранит целые `StreamRecord`, включая timestamps, в `InternalListState`. После FIRE он строит iterable timestamped values, вызывает `evictBefore`, проецирует значения в user function, вызывает `evictAfter`, затем записывает весь оставшийся список через `state.update`: AppendingState не предоставляет точечного удаления. Эта политика требует хранения элементов и повторной записи списка, поэтому её нельзя считать эквивалентом предварительной агрегации. Отдельные обработчики input/event-time/processing-time сохраняют ту же последовательность trigger → emit → purge → terminal cleanup. [Полная цепочка eviction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/EvictingWindowOperator.java#L373-L428).

## Время, lateness и освобождение

Event-time trigger ставит timer на `maxTimestamp`. Если watermark уже достиг этого timestamp, новый принятый элемент немедленно вызывает FIRE. `onEventTime` выдаёт FIRE только для точного timestamp конца. Важно следовать реализации: Javadoc `EventTimeTrigger.create` говорит об отбрасывании элементов после fire, но возвращаемый FIRE сам очистки не делает. При allowed lateness данные могут оставаться и давать повторные результаты; окончательное удаление делает оператор. Processing-time trigger регистрирует timer на конец окна и возвращает FIRE из processing callback; watermark для него не определяет закрытие. [EventTimeTrigger](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/triggers/EventTimeTrigger.java#L36-L94), [ProcessingTimeTrigger](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/triggers/ProcessingTimeTrigger.java#L34-L70).

Окно event-time считается late при `cleanupTime(window) <= currentWatermark`, где cleanup равен `maxTimestamp + allowedLateness` с насыщением до `Long.MAX_VALUE` при переполнении. Для processing-time cleanup равен `maxTimestamp`, lateness не добавляется. Timer на `Long.MAX_VALUE` не регистрируется. Terminal cleanup очищает содержимое, вызывает `Trigger.clear`, затем `userFunction.clear` и удаляет merging mapping. Обычный PURGE очищает только содержимое. Если элемент не попал ни в одно допустимое окно и `element.timestamp + allowedLateness <= watermark`, он идёт в late side output либо увеличивает `numLateRecordsDropped`. Отказ отдельного окна ещё не делает весь элемент late: он мог попасть в другое окно. [Проверки lateness и timers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/WindowOperator.java#L608-L685).

`InternalTimerServiceImpl` владеет двумя key-group priority queues: event-time и processing-time. Идентичность регистрации включает key, namespace и timestamp. Для processing-time сервис держит одну внешнюю scheduled future на ближайший timestamp и переносит её раньше, когда добавлен новый минимум. В callback он устанавливает ключ каждого timer перед вызовом target, извлекает все due timers и проверяет cancellation. Для event-time watermark задаёт верхнюю границу обхода. Есть два фронтира: `currentWatermark` сразу получает запрошенную цель; `reachedWatermark` отражает выполненные callback. При прерывании обхода достигнутый фронтир равен timestamp последнего timer минус один: другие timers с таким же timestamp могут ещё не отработать. Только завершённый обход устанавливает достигнутый фронтир в цель. [Регистрация и выполнение](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/operators/InternalTimerServiceImpl.java#L244-L368).

Snapshot timers создаётся отдельно для key-group и включает key/namespace serializers и обе очереди. Restore проверяет локальное владение key-group, согласованность восстановленных serializers между группами и добавляет timers обратно в очереди. При start восстановленная schema compatibility может быть compatible-as-is либо с reconfigured serializer; incompatible и compatible-after-migration отклоняются. Затем регистрируется ближайший восстановленный processing timer. Это конкретное ограничение timer restore, которое нельзя автоматически переносить на все виды state serializer. [Start](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/operators/InternalTimerServiceImpl.java#L144-L223), [snapshot/restore](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/operators/InternalTimerServiceImpl.java#L370-L431).

## Слияние окон: логическая граница отделена от state namespace

`MergingWindowSet` восстанавливает из keyed ListState mapping «актуальное логическое окно → окно, служащее namespace данных». При расширении session-подобного окна сохраняется один старый namespace, чтобы не переносить state при каждом расширении. Ассайнер получает все текущие окна вместе с новым и сообщает merge groups. Новый window ещё не имеет состояния и исключается из списка переносимых namespaces; целевой namespace также исключается. Callback оператора сначала проверяет, что merge не породил уже закрытую границу, вызывает trigger.onMerge для нового логического окна, очищает trigger state и cleanup timers старых окон, затем `mergeNamespaces` объединяет содержимое. Только после этого вход добавляется к target state namespace, но trigger и выдача используют актуальное логическое окно. Mapping явно persist-ится после изменений. [Mapping algorithm](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/MergingWindowSet.java#L76-L223), [callback](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/WindowOperator.java#L306-L406).

Оставшийся timer несуществующего merged окна безопасно игнорируется, когда logical→state mapping уже отсутствует; комментарий связывает этот случай с trigger, не удалившим timer. Пользовательский per-window state через `ProcessWindowFunction.windowState()` для merging windows запрещён всеми getState/getListState/getReducingState/getAggregatingState/getMapState: оператор не обещает сам объединять произвольную пользовательскую структуру. Global keyed state остаётся доступным отдельно. [Timer callback](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/WindowOperator.java#L452-L543), [ограничение per-window state](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/operators/windowing/WindowOperator.java#L713-L829).

## Checkpoint — распределённый протокол фиксации snapshot

`CheckpointCoordinator` не принимает отдельный ACK каждой записи. Он создаёт checkpoint plan с задачами trigger/wait/commit, получает монотонный checkpoint ID, создаёт `PendingCheckpoint` и timeout, инициализирует storage location, снимает operator coordinator state, затем master hooks, и только после их завершения отправляет task trigger. ID и storage операции выполняются вне общего lock на IO executor; дальнейшие переходы проходят timer executor и lock. Такое упорядочение coordinator → master → task явно необходимо для externally induced source. Политика trigger отдельно ограничивает concurrent checkpoints, min pause и queued requests; backlog источников может менять период. [Начало протокола](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/CheckpointCoordinator.java#L620-L955).

`PendingCheckpoint` собирает три множества подтверждений: execution attempts задач, operator coordinators и master hook identifiers. ACK задачи классифицируется SUCCESS/DUPLICATE/UNKNOWN/DISCARDED. TaskStateSnapshot распределяется по operator IDs и parallel subtask index, а finished-on-restore и finished-operator markers обрабатываются через checkpoint plan. Полнота означает пустые все три множества при ещё не disposed объекте. Хранятся state handles, а не материализованные пользовательские значения. [Pending state machine](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/PendingCheckpoint.java#L65-L185), [ACK](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/PendingCheckpoint.java#L385-L545).

При полноте coordinator сообщает shared-state registry о завершении, а pending checkpoint пишет `CheckpointMetadata` в metadata stream и `closeAndFinalizeCheckpoint`. Затем создаётся CompletedCheckpoint и pending объект dispose-ится с `releaseState=false`: владение handles переходит завершённому checkpoint. Для обычного checkpoint его добавляют в CompletedCheckpointStore и применяют retention/subsumption. Только после этого completion future успешно завершается; затем удаляются более старые subsumable pending checkpoints и отправляется `notifyCheckpointOnComplete` задачам commit и coordinators. Обычный несинхронный savepoint не проходит обычную commit-notification ветку. [Finalize](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/PendingCheckpoint.java#L317-L365), [store и notification](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/CheckpointCoordinator.java#L1363-L1443).

Здесь существуют разные границы: task snapshot ACK, запись metadata, регистрация checkpoint в completed store и уведомление участникам о completion. Они не являются одной транзакцией внешнего sink. При сбое записи store с `PossibleInconsistentStateException` coordinator не знает, сохранилась ли metadata, и намеренно не удаляет соответствующее состояние: иначе мог бы уничтожить единственный доступный recovery checkpoint. При определённом провале storing cleaner освобождает checkpoint; участникам отправляется abort. Late/unknown ACK также требует cleanup handles, однако shared handles регистрируются независимо от актуальности ACK, чтобы не удалить файлы, ещё используемые другим checkpoint или задачей. Savepoints имеют отдельное владение жизненным циклом. [Late ACK/shared state](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/CheckpointCoordinator.java#L1233-L1350), [неопределённый store outcome](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/CheckpointCoordinator.java#L1508-L1546).

Abort завершает checkpoint promise и master-trigger promise ошибкой и dispose-ит pending с releaseState=true; cleaner освобождает private handles, незарегистрированное shared state ещё считается private. Cleanup best-effort очищает operator map и storage target; timeout future отменяется при любом dispose. Savepoint не может быть subsumed новым checkpoint. Timeout, decline, trigger failure, suspend и shutdown проходят явные abort paths, а не masquerade как successful snapshot. [Abort/dispose](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/PendingCheckpoint.java#L548-L699), [coordinator abort](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/CheckpointCoordinator.java#L2282-L2376).

## Restore имеет область и политику владения

Regional/subtask restore выбирает последний completed checkpoint, допускает немаппируемое состояние, поскольку восстанавливается лишь часть JobVertices, и пропускает reset coordinators. Global restore восстанавливает coordinators, а при отсутствии checkpoint сбрасывает их в пустое состояние. Оба пути восстанавливают master hooks. StateAssignmentOperation получает operator states и устанавливает initial task restore; её подробный разбор приведён ниже. При заданном checkpoint ID возможно явное отбрасывание in-flight channel data через копию OperatorState. Если checkpoint unclaimed, следующий обычный checkpoint принудительно full; флаг снимается после успешного добавления full snapshot в store. [Области restore](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/CheckpointCoordinator.java#L1645-L1865).

Savepoint restore сначала разрешает внешний pointer и выбирает claim policy: CLAIM принимает обычное checkpoint ownership, LEGACY сохраняет savepoint properties, NO_CLAIM использует unclaimed snapshot. Shared handles регистрируются до добавления в completed store, поскольку добавление может запустить subsumption. ID counter ставится в restored ID + 1. Затем выполняется общий restore с проверкой partial-finished operators и настройкой allowNonRestoredState. [Savepoint restore](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/CheckpointCoordinator.java#L1878-L1952).

## Дополнение: конкретные assigners и проверенные сценарии trigger

`TimeWindow` — полуинтервал `[start,end)`, а maxTimestamp равен `end−1`. Tumbling assigner вычисляет один start по размеру и offset; sliding сначала выравнивает lastStart по slide, затем перебирает start назад, пока `start > timestamp−size`. Event-time варианты отклоняют `Long.MIN_VALUE` как маркер отсутствующего timestamp. Processing-time варианты берут `context.getCurrentProcessingTime`, игнорируя timestamp входа. Нормализация start специально обрабатывает отрицательный остаток, чтобы до epoch границы совпадали с математическим floor. У tumbling assigners есть лениво выбранная фаза stagger: ALIGNED=0, RANDOM выбирает смещение в пределах size, NATURAL использует фазу первого processing-time получения. [TimeWindow](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/windows/TimeWindow.java#L40-L118), [sliding enumeration](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/assigners/SlidingEventTimeWindows.java#L58-L91), [stagger](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/api/windowing/assigners/WindowStagger.java#L26-L62).

Для merge геометрия допускает также соприкасающиеся окна: `intersects` использует `start <= other.end` и `end >= other.start`. `TimeWindow.mergeWindows` сортирует по start, транзитивно расширяет cover и сообщает callback только группы из нескольких различных окон. `GlobalWindows` направляет всё в singleton с maxTimestamp=`Long.MAX_VALUE`; обычный default NeverTrigger никогда не выдаёт FIRE, а специальный end-of-stream trigger регистрирует event-time timer на MAX_VALUE. ## Дополнение: repartition и key-group layout

`StateAssignmentOperation` сначала проверяет, что каждому сохранённому operator ID соответствует оператор, либо разрешён explicit `allowNonRestoredState`. При сопоставлении предпочитается user-defined operator ID, если он присутствует в snapshot, иначе generated ID. Далее три прохода создают TaskStateAssignment, перераспределяют handles и устанавливают `JobManagerTaskRestore` текущим execution attempts. Finished vertex получает `FINISHED_ON_RESTORE`. При изменении parallelism managed/raw operator state идут через operator repartitioner, managed/raw keyed state — через пересечение старых handles с новым KeyGroupRange. При неизменном parallelism keyed handles просто назначаются тому же subtask index. [Порядок и mapping](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/StateAssignmentOperation.java#L105-L303), [keyed reassignment](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/StateAssignmentOperation.java#L379-L434).

Ключ переводится в key-group формулой `murmurHash(key.hashCode()) % maxParallelism`; key-group переводится в subtask формулой `keyGroupId * parallelism / maxParallelism`. Поэтому масштабирование parallelism меняет владельца диапазонов, но сохраняет устойчивый key-group layout. Изменение maxParallelism изменило бы сам layout. В этой версии отдельно запрещено восстанавливать вновь объединённую chain, если её операторы записали разные maxParallelism и vertex содержит keyed state: даже stateless оператор с другим сохранённым значением мог бы перезаписать shared vertex maxParallelism и направить чужое keyed state неправильно. Также snapshot maxParallelism должен быть не ниже нового parallelism; runtime может принять сохранённый maxParallelism только когда vertex это разрешает. [Формулы](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/state/KeyGroupRangeAssignment.java#L42-L126), [chain agreement](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/StateAssignmentOperation.java#L306-L377).

In-flight channel state — самостоятельный вид восстановления. Input/output mappings могут назначить старые buffers нескольким новым subtasks с фильтрацией при recovery. Даже stateless task должен получить restore assignment, если его upstream output или downstream input имеет сохранённые buffers. Output redistribution на downstream выполняется после вычисления всех input mappings. Изменение topology, которое превращает exchange с persisted buffers во внутреннюю цепочку, явно отклоняется. Эти правила показывают, почему rescale unaligned checkpoint нельзя свести к переносу keyed KV диапазонов. [Channel repartition](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/checkpoint/StateAssignmentOperation.java#L458-L617).

## Дополнение: RocksDB snapshot не равен external transaction

RocksDB backend использует один DB instance с column family на state name. Ключи кодируются составно с key-group prefix, key, namespace и для MapState user map key; backend обновляет общий composite-key builder при смене текущего ключа. Для checkpoint сначала flush-ится batch wrapper в DB, затем SnapshotStrategyRunner готовит native checkpoint: RocksDB создаёт hard links живых файлов в отдельной snapshot directory под ResourceGuard lease. После этой локальной фиксации async часть может загружать стабильный набор файлов. Local recovery directory и remote checkpoint storage имеют разное владение. [DB и guard](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/RocksDBKeyedStateBackend.java#L193-L269), [flush/snapshot](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/RocksDBKeyedStateBackend.java#L704-L761), [native preparation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/snapshot/RocksDBSnapshotStrategyBase.java#L150-L184).

Incremental strategy переиспользует SST только из подтверждённого JM checkpoint. Сам факт успешного upload ещё не даёт права reuse: task мог бы удалить эти handles при провале старого checkpoint. FORWARD_BACKWARD допускает использование прежней базы; FORWARD начинает без старой базы, но публикует новые SST для последующих checkpoints; NO_SHARING загружает private EXCLUSIVE files и не сохраняет их как будущую базу. Metadata и misc files входят в новый result, SST могут быть placeholder handles, разрешаемыми shared registry. После успешного async snapshot stream factory получает reuse notification, требуемое file merging. После checkpointComplete стратегия продвигает подтверждённую базу только если этот ID действительно есть в SST history; savepoint notification сама по себе базу не меняет. Abort удаляет history этого checkpoint. [Sharing и notifications](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/snapshot/RocksIncrementalSnapshotStrategy.java#L124-L221), [upload/handles](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/snapshot/RocksIncrementalSnapshotStrategy.java#L251-L432).

Особый race: CP1 загрузил `file.sst→A`, CP2 начался до подтверждения CP1 и повторно загрузил тот же локальный SST как B, затем приходит позднее подтверждение CP1. Если CP2 завершится и subsume-ит CP1, A может быть удалён. Поэтому PreviousSnapshot вычёркивает из базы CP1 имена SST, повторно загруженные более поздними checkpoints. CP3 может стать фактически full, хотя CP1 уже подтверждён. Прочитанный тест воспроизводит именно этот порядок и требует равенства full size и checkpointed size у CP3; второй сценарий требует сохранить incremental после savepoint notification. [Race и pruning](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/snapshot/RocksDBSnapshotStrategyBase.java#L400-L503), [сценарии теста](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/test/java/org/apache/flink/state/rocksdb/snapshot/RocksIncrementalSnapshotStrategyTest.java#L68-L131).

Restore metadata сначала возвращает DB и зарегистрированные column families; actual state object создаётся при первом запросе descriptor с проверкой compatibility. RocksDB умеет мигрировать serialized values, но не composite key. Namespace migration запрещена; MapState migration разрешает эволюцию value только при compatible-as-is user map-key serializer. [Full strategy](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/snapshot/RocksNativeFullSnapshotStrategy.java#L159-L248), [value migration](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-state-backends/flink-statebackend-rocksdb/src/main/java/org/apache/flink/state/rocksdb/RocksDBKeyedStateBackend.java#L862-L1046).

Compatibility проверяется, когда известны обе стороны. Предыдущий serializer создаётся лениво, текущий становится недоступен при incompatible результате; reconfigured результат заменяет зарегистрированный instance. Поэтому migration logic должна сохранять фактически записанную metadata и учитывать такой wrapper, а не выводить старую схему заново из восстановленного serializer. ## Дополнение: operator state snapshot отличается от keyed heap snapshot

DefaultOperatorStateBackend хранит list state с assignment mode SPLIT_DISTRIBUTE/UNION и broadcast map state. Отдельны восстановленные registries и cache уже accessed instances; при первом доступе к восстановленному state сверяются name, mode и serializer compatibility. Async writer затем пишет metadata и compressed state, а handle сохраняет offsets каждого list item как partition и один offset всей broadcast map. При file merging даже пустой operator state может возвращать специальный handle, удерживающий directories. [Backend modes](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/state/DefaultOperatorStateBackend.java#L137-L219), [deep-copy и запись](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/state/DefaultOperatorStateBackendSnapshotStrategy.java#L65-L235).

Operator restore сначала восстанавливает прежние serializers и metadata. Unloadable old serializer немедленно останавливает restore: пока не зарегистрирован новый serializer, нечем прочитать bytes. Затем list partitions загружаются по offsets через add, а broadcast map — count и pairs. Используется порядок operator list state перед broadcast, соответствующий write. Context classloader и cancel registry всегда восстанавливаются/закрываются в finally. ## Дополнение: async windows сохраняют causal order через StateFuture
