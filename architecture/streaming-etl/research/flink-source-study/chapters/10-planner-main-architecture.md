## Dynamic filtering: control dependency становится graph structure

Batch physical collector проецирует выбранные dimension fields, а ExecNode создаёт collector с **configured parallelism1**. Default threshold8MB ограничивает payload: при превышении coordinator получает empty event с flag, позволяющим отказаться от filtering. Поэтому описанное table reader поведение runtime coordinator «первое событие побеждает» относится к singleton collector, не к distributed union partial sets. [Physical lowering](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/scala/org/apache/flink/table/planner/plan/nodes/physical/batch/BatchPhysicalDynamicFilteringDataCollector.scala#L60-L67), [threshold and singleton](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/plan/nodes/exec/batch/BatchExecDynamicFilteringDataCollector.java#L55-L106). Runtime body/assertions атрибутируются [05](05-table-sql-planner-runtime.md).

Fact source первоначально имеет collector input как planning dependency. DynamicFilteringDependencyProcessor копирует source без inputs, чтобы убрать cycle в ExecNode DAG, затем вставляет broadcast/BATCH exchange collector→enforcer и source→enforcer вторым input. Все прежние consumers переключаются на enforcer. При mode отличном от ALL_EXCHANGES_BLOCKING processor также требует blocking boundaries на выходах dimension-side upstream closure. Это явная зависимость исполнения, выраженная topology и exchange mode; она не переносит filter rows в обычный fact record stream. [Rewrite](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/plan/nodes/exec/processor/DynamicFilteringDependencyProcessor.java#L91-L139), [blocking boundaries](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/plan/nodes/exec/processor/DynamicFilteringDependencyProcessor.java#L145-L246).

## Compiled source spec: восстановление конфигурации не равно восстановлению данных

При первом запросе он выбирает module factory, затем catalog factory fallback, создаёт connector с classloader/context и применяет abilities в сохранённом порядке. Catalog options перечитываются отдельно только для permanent table при restore mode ALL; ALL_ENFORCED не запрашивает catalog, IDENTIFIER уже приходит с catalog table. ## Логическое сокращение агрегатов и подзапросов

RelNode на этом этапе описывает вычисление, а не работающую task. Скопированный Calcite Join заранее строит JoinInfo в конструкторе; MultiJoin хранит N inputs, общий predicate, отдельные outer-join conditions, projection/reference metadata и hints. Flink-копия MultiJoin переносит hints через copy и RexShuttle. Это представление для преобразований и выбора порядка join, отличное от managed state runtime multi-way join из главы05. [Join construction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/rel/core/Join.java#L83-L109), [MultiJoin metadata](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/rel/rules/MultiJoin.java#L96-L120), [copy/hints](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/rel/rules/MultiJoin.java#L151-L171).

AggregateReduceFunctionsRule расширяет входную projection для дополнительных выражений, собирает переиспользуемые AggregateCall и восстанавливает исходный output schema завершающей projection. AVG превращается в SUM/COUNT с приведением типа результата; nullable SUM — в SUM0 плюс CASE по COUNT, чтобы пустая группа дала NULL. ## Валидация как владелец изменяемого SQL-дерева

Полностью прочитанная Flink-копия SqlValidatorImpl хранит scopes, namespaces и node types в отдельных identity maps: одинаково напечатанные NULL nodes могут иметь разные выведенные типы. Validation сначала выполняет unconditional rewrites, регистрирует query/scopes, затем вызывает validation узла. FROM, WHERE, GROUP, WINDOW и QUALIFY проверяются перед SELECT; SELECT выводит row type, после чего становятся доступны HAVING и ORDER BY aliases. LEFT/RIGHT/FULL join делает nullable соответствующие namespaces, а nested-field derivation отдельно переносит nullable parent record на field. Эти объекты принадлежат компиляции запроса; они не являются runtime checkpoint state. [Mutable ownership](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql/validate/SqlValidatorImpl.java#L250-L327), [validation entry](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql/validate/SqlValidatorImpl.java#L1091-L1106), [SELECT sequence](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql/validate/SqlValidatorImpl.java#L4116-L4143), [nested nullability](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql/validate/SqlValidatorImpl.java#L7258-L7282).

Scope определяет допустимую корреляцию: LATERAL получает видимость предыдущих join inputs, обычный FROM регистрируется через inherited parent scope. Проверка temporal SNAPSHOT требует timestamp period и temporal table; для CTE конкретная table-проверка явно отложена до planner rules. Это admission SQL формы, не согласованный snapshot внешнего источника. OVER validator временно включает nested-aggregate context, устанавливает window call, делегирует проверку SqlWindow и затем сбрасывает context. Сам SqlWindow относится к внешней Calcite dependency, его тело здесь не прочитано; поэтому прежний вопрос о достижимости нулевых bounded OVER offsets остаётся открытым. [LATERAL scope](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql/validate/SqlValidatorImpl.java#L2495-L2511), [temporal admission](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql/validate/SqlValidatorImpl.java#L5901-L5927), [OVER delegation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql/validate/SqlValidatorImpl.java#L6135-L6166).

RexUtil обеспечивает последующую работу с typed expressions: детерминированность call выводится из operator flag, constant finder допускает dynamic parameters как постоянные в пределах execution, а correlation не считает constant. CNF expansion имеет threshold с возвратом исходного expression при превышении; дополнительное disjunction expansion по input/table возвращает пустой набор derived predicates при превышении собственного бюджета. Поэтому отказ от optimization не обязан менять исходный predicate. SEARCH expansion сохраняет достаточно сложные Sarg вместо полного разворачивания. Это ограничения compiler work, не размер runtime keyed state. [Constant visitor](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/rex/RexUtil.java#L768-L787), [expansion fallback](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/rex/RexUtil.java#L2931-L2942), [derived-expression budget](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/rex/RexUtil.java#L3066-L3075), [SEARCH complexity](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/rex/RexUtil.java#L3484-L3533).


## SQL→Rel и decorrelation: сохранение семантики перед physical planning

SqlToRelConverter создаёт отдельный Blackboard для SELECT/subquery и хранит текущий Rel root, correlation mappings, subquery expressions и временные aggregate/window modes. convertQuery при необходимости вызывает validator, строит Rel tree, проверяет сохранение validated row types и затем распространяет/очищает hints по query-block boundaries. Это переход между представлениями программы; logical JOIN либо aggregate ещё не выбирает конкретный runtime algorithm. Для set-semantic table parameters Flink всегда преобразует input query, но намеренно не создаёт logical exchange: partition/order indices сохраняются custom RexCall, физические exchanges добавляются позднее по traits. [Query path/type guard](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/SqlToRelConverter.java#L666-L732), [per-query workspace](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/SqlToRelConverter.java#L5473-L5516), [delayed exchanges](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/SqlToRelConverter.java#L1515-L1584).

AggConverter сначала собирает group/input expressions и AggregateCalls; SQL FILTER становится отдельным input boolean, nullable filter оборачивается IS_TRUE. Named arguments переставляются через FlinkSqlCallBinding до expression conversion. Временное отключение bb.agg для вычисления arguments/sort expressions защищено finally; общие converted expressions и aggregate calls получают повторные references. COUNTIF понижается в COUNT(*) FILTER, APPROX_COUNT_DISTINCT — в COUNT с distinct+approximate flags. Это compiler representation, не обещание одного общего mutable accumulator на runtime tasks. [Aggregate wrappers/COUNTIF](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/AggConverter.java#L347-L392), [argument/filter mode](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/AggConverter.java#L459-L505), [call construction/sharing](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/AggConverter.java#L507-L569).

Subquery lowering зависит от контекста UNKNOWN. Filter может свести UNKNOWN к непрохождению, projection должен сохранить третье значение: IN full logic добавляет общий COUNT(*)/COUNT(keys), matched indicator и CASE для empty/null cases. Default config оставляет subqueries как RexSubQuery, поэтому последующие rules остаются частью успешного пути; альтернативное eager expansion — другой configured path. OVER conversion нормализует отсутствующие bounds, сохраняет ROWS/RANGE, order/null directions, distinct/null-treatment и создаёт Rex windows; bb.window сбрасывается finally. [IN logic](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/SqlToRelConverter.java#L1674-L1756), [default expansion policy](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/SqlToRelConverter.java#L6894-L6913), [OVER frame normalization](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/SqlToRelConverter.java#L2397-L2506).

RelDecorrelator создаёт собственные mutable maps и stack видимых correlation frames, сначала применяет специальные rules, затем при необходимости общий rewrite. Он переносит correlation columns в grouping и переписывает references через immutable Frame mappings. При scalar aggregate нельзя просто добавить key в GROUP BY: пустой input перестал бы давать COUNT=0. Поэтому отдельный path строит distinct domain внешних keys, LEFT JOIN агрегированных результатов и CASE NULL→0 для COUNT. Соединение correlation keys использует IS NOT DISTINCT FROM; обычное равенство выбирается только при установленной non-nullability. [Decorrelation phases](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/RelDecorrelator.java#L231-L269), [empty aggregate preservation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/RelDecorrelator.java#L847-L992), [null-safe correlation join](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/RelDecorrelator.java#L1692-L1717).

Коррелированный Sort с offset/fetch обычно оставляется без общего rewrite, чтобы local limit не превратился в global limit. Исключение fetch=1 без offset использует partitioned FIRST_VALUE+DISTINCT; узкий single-column NULLS LAST path допускает MIN/MAX с correlation grouping. Поэтому промежуточный golden с Sort(fetch=1) надо оценивать с фазой optimization и выбранным decorrelation path, а не объявлять самостоятельным runtime verdict. Flink-копия также явно отключает повторное hint propagation и два upstream extraction шага по отмеченному workaround. Тестовые орacles и expected plans остаются отдельными свидетельствами глав08/11, ничего здесь не запускалось. [Limit guard](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/RelDecorrelator.java#L574-L607), [partitioned fetch-one](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/RelDecorrelator.java#L1042-L1186), [disabled preprocessing](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/sql2rel/RelDecorrelator.java#L319-L363).


## Runtime helpers: семантика caller и локальный lifetime

Полностью прочитанный `SqlFunctions` — набор исполняемых строительных блоков, а не самостоятельный SQL executor. Его [входной контракт](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L155-L165) возлагает проверку NULL на generated caller; для ленивых AND/OR helper вообще не предназначен. Поэтому наличие Java-метода и аннотации не доказывает ни выбор данного метода Flink codegen, ни обработку NULL на всём SQL-пути. Это следующий участок зависимости, а не основание переносить реализацию helper на каждый одноимённый встроенный SQL operator.

Состояние вычисления имеет разные владельцы. [Regex/LIKE helper](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L2001-L2062) хранит ограниченный кеш скомпилированных шаблонов. [DateFormatFunction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L5184-L5280) дополнительно переиспользует изменяемый StringBuilder, а [DateParseFunction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L5354-L5465) кеширует изменяемые DateFormat по паре format/timeZone. Следовательно, потокобезопасность кеша сама по себе не задаёт потокобезопасность всего экземпляра функции; caller должен определить lifetime экземпляра и сериализацию вызовов. [CURRENT_TIMESTAMP и LOCAL_TIMESTAMP](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L6135-L6196) читают разные поля DataContext, а [sequence](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L6475-L6490) принадлежит thread-local map с AtomicLong. Последнее не является checkpointed sequence или общекластерным durable счётчиком.

Коллекции также требуют точной границы владения: [transform](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L6773-L6809) возвращает ленивый view поверх исходного списка; [sortArray](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L6811-L6819) и [reverse](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L7094-L7098) меняют переданный список; [arraySlice](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L7100-L7107) возвращает subList. Результат такого вызова нельзя автоматически считать независимой immutable записью. В противоположность этому [MULTISET INTERSECT ALL/EXCEPT ALL](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/calcite/runtime/SqlFunctions.java#L7013-L7034) создают копии и удаляют по одному совпадению, сохраняя multiplicity, тогда как DISTINCT-варианты используют Set. Семантика Java equals/hashCode здесь требует сопоставления с выбранной SQL representation; отдельно прочитанные table runtime функции описаны в [главе05](05-table-sql-planner-runtime.md), и их реализация не подменяется этим copied Calcite helper.

Личный literal scope copied Calcite main теперь закрыт целиком, включая все7434 строки этого файла. Это узкое завершение поддерева; весь переданный planner main остаётся открытым. Тесты и runtime не запускались.


## Связь capability, generated callback и результата чтения

На входе SQL sink [DynamicSinkUtils](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/DynamicSinkUtils.java#L291-L394) сначала готовит mutable sink, собирает и применяет ability specs, затем проверяет positional schema и добавляет cast/metadata projection, и лишь потом создаёт LogicalSink. [NOT NULL здесь ослабляется](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/DynamicSinkUtils.java#L1132-L1142) намеренно: runtime constraint operator остаётся владельцем проверки. Writable metadata идут [в порядке provider metadata map](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/DynamicSinkUtils.java#L1076-L1103), физические колонки — перед persisted metadata. Это контракт representation, который не задаёт commit внешнего sink; runtime sink protocol разобран отдельно в [06](06-connectors-formats-storage-metrics.md).

Row-level операции меняют сам relational input: [ALL_ROWS UPDATE](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/DynamicSinkUtils.java#L776-L840) убирает filter и переносит условие в IF(updated, original), а REMAINING_ROWS DELETE использует [обычный NOT исходного predicate](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/DynamicSinkUtils.java#L631-L652). Для nullable predicate последнее оставляет отдельное обязательство проверки SQL UNKNOWN: plain NOT не равен IS NOT TRUE. Это source observation конкретного rewrite; тесты этого пути здесь не прочитаны и wrong-result воспроизведение не заявляется.

[CollectDynamicSink](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/CollectDynamicSink.java#L109-L157) связывает client result с созданием runtime transformation: iterator получает operator UID, serializer и checkpoint configuration, converter открывается здесь же. [Internal/external wrappers](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/CollectDynamicSink.java#L177-L235) используют один underlying iterator. `isFirstRowReady` становится true и после завершения пустой job: готовность результата означает возможность закончить ожидание, а не наличие хотя бы одной строки. DataStream bridges отдельно выбирают [выдачу rowtime metadata и propagation watermark](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/connectors/ExternalDynamicSource.java#L106-L155); эти две capability не взаимозаменяемы.

Generated async scalar [сначала заполняет metadata/results slots](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/codegen/AsyncCodeGenerator.java#L129-L191), и только затем вызывает async expressions: callback может сработать немедленно. Throwable при invocation завершает внешний collector exceptionally. Async correlate [отдельно генерирует operands и timeout body](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/codegen/AsyncCorrelateCodeGenerator.java#L81-L120), поскольку обычный bridging вызов не возвращает нужный timeout override. Это связывает compiler contract с callback lifetime; retry и checkpoint accounting принадлежат runtime operator, а не генератору строки Java.

JSON/XML parser reuse сохраняет ленивость: первый реально выполненный call читает document, поэтому skipped CASE branch не должен заранее бросить parse error. [PARSE_JSON и TRY_PARSE_JSON](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/codegen/JsonCodeGenUtils.java#L88-L246) делят parsed value/error, но только strict call site превращает ошибку в исключение. [XML shared reader](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/codegen/XmlCodeGenUtils.java#L110-L157) использует identity input object; гарантия нового либо корректно reset input на следующей записи остаётся контрактом enclosing generated pipeline. Наличие этих полей не является global cache и не добавляет checkpoint state.

## Materialized table: catalog и refresh job имеют разные commits

Полностью прочитаны default executor1363, controller381 и factory54. [Executor](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/delegation/materializedtable/DefaultMaterializedTableExecutor.java#L130-L218) выполняет operation синхронно на вызывающем пути и всегда освобождает retrieved job clients в finally. Continuous CREATE сначала пишет table в catalog, потом запускает streaming refresh; ошибка запуска вызывает компенсирующий drop. Conversion regular→materialized [сохраняет изменённый catalog entry в SUSPENDED](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/delegation/materializedtable/DefaultMaterializedTableExecutor.java#L271-L327) вместо возврата regular table. FULL mode отдельно создаёт workflow и сохраняет сериализованный handler: workflow scheduler и catalog не объединены транзакцией.

Успешный submit ещё не означает записанный refresh handler. [Submit→register→record](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/delegation/materializedtable/DefaultMaterializedTableExecutor.java#L608-L680) создаёт job, затем обновляет catalog. При ошибке record [cancel компенсация](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/delegation/materializedtable/DefaultMaterializedTableExecutor.java#L682-L731) явно допускает двусмысленный исход catalog write и неуспешную отмену; exception сообщает идентичность потенциально живой job. SUSPEND, в свою очередь, [сначала получает savepoint от остановленной job, затем пишет путь/status](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/delegation/materializedtable/DefaultMaterializedTableExecutor.java#L400-L455). Ошибка второй фазы не возвращает job в RUNNING; оператору сообщается путь для ручного восстановления. Это полезный пример архитектуры компенсаций и recovery hints, а не durable inbox/atomic workflow engine.

[RefreshJobController](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/delegation/materializedtable/RefreshJobController.java#L82-L207) держит submitted client дольше одной operation, retrieved clients закрывает после operation. Из catalog восстанавливаются execution target/cluster/job identity, остальные cluster coordinates берутся из текущей program configuration. [Ожидание ответа](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/delegation/materializedtable/RefreshJobController.java#L251-L307) ограничено client.timeout, но timeout не отменяет исходный future/request. Retrieval самого client использует отдельный `.get()` без такого timeout. Поэтому повтор после timeout обязан учитывать, что stop/cancel ещё может завершиться на cluster. Runtime/tests не запускались; отдельные fixture границы этой области атрибутированы [11](11-planner-tests-evidence.md).


## Table API expression → Rex: identity, inference и момент появления фактов

Весь Java `expressions` и весь `functions/bridging`/`functions/inference` лично прочитаны полностью, включая29 customized converters. [ExpressionConverter](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/expressions/converter/ExpressionConverter.java#L100-L119) обходит ordered chain: legacy scalar, FunctionDefinition, OVER, direct mapping, customized conversion. Поэтому mapping function name не равен выбору runtime helper из предыдущего раздела. Literal conversion отдельно сохраняет тип через RexBuilder, но [TIME ограничивается миллисекундной точностью, LTZ нормализуется в UTC](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/expressions/converter/ExpressionConverter.java#L177-L228); [field reference использует имя](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/expressions/converter/ExpressionConverter.java#L231-L249), поскольку grouping может переставить field indexes. Для declarative aggregates [merge input и accumulate input разрешаются раздельно](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/expressions/DeclarativeExpressionResolver.java#L56-L97), а aggregate decimal arithmetic имеет собственные definitions, отличные от обычного PLUS/MINUS.

Важен момент появления информации. [CallBindingCallContext](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/inference/CallBindingCallContext.java#L74-L179) работает на SQL AST и умеет переставлять named arguments; [его TableSemantics](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/inference/CallBindingCallContext.java#L287-L320) ещё не содержит timeColumn/changelog/upsert keys. [OperatorBindingCallContext](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/inference/OperatorBindingCallContext.java#L180-L215) получает эти факты позднее из Rex table inputs, если caller их передал. Отсутствие данных на validation stage поэтому не является доказательством insert-only input или отсутствия keys. DEFAULT в обоих контекстах представлен как NULL; descriptor и строковый MAP имеют специальные literal adapters, поскольку Calcite представляет их calls.

[Operand inference](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/inference/TypeInferenceOperandInference.java#L67-L125) может проглотить ValidationException и оставить ошибку окончательному checker. [Checker](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/inference/TypeInferenceOperandChecker.java#L211-L279) сначала вычисляет castArguments, потом меняет SqlCall operands, вставляя CAST и обновляя validator namespace/type cache. Такой checker участвует в построении изменяемого дерева, а не только возвращает boolean. [CAST converter](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/expressions/converter/converters/CastConverter.java#L33-L44) берёт top-level nullability из разрешённого output call; [TRY_CAST](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/expressions/converter/converters/TryCastConverter.java#L44-L64) принудительно допускает NULL. Эти различия нужны для корректного переноса SQL constraints в runtime representation.

[BridgingSqlFunction](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/bridging/BridgingSqlFunction.java#L235-L330) разрешает conditional PTF traits по конкретным partition keys и scalar literal arguments, затем создаёт новый operator с effective static signature. Это повторяется при fresh planning и compiled-plan restore, поскольку они входят в downstream chain разными путями. Broadcast table для Calcite [объявляется SET semantics](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/bridging/BridgingSqlFunction.java#L452-L483), а собственная broadcast validation принадлежит system inference. Следовательно, Calcite facade не заменяет runtime broadcast protocol из03/05. Полная runtime specialization PTF и changelog assumptions атрибутированы [05](05-table-sql-planner-runtime.md).

Промежуточный личный объём переданного planner main:182 whole files72731 строк; весь остальной reserved scope остаётся открыт. Чтение тестов11 выполняется отдельным reader, запусков здесь нет.


## Declarative aggregate: state формируется из выражений, а capability выбирает planner

Все19 Java `aggfunctions` прочитаны полностью. Объект declarative aggregate описывает buffer schema, initial/accumulate/retract/merge и getValue expressions; runtime generator должен правильно связать references и порядок обновлений. [AVG](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/aggfunctions/AvgAggFunction.java#L59-L105) хранит sum+count, пропускает NULL input и возвращает NULL при count=0. [COUNT и COUNT1](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/aggfunctions/Count1AggFunction.java#L32-L84) отличаются именно включением NULL occurrences, а [SUM WITH RETRACT](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/aggfunctions/SumWithRetractAggFunction.java#L62-L107) должен сохранять count даже при числовом sum0, чтобы различать пустой input и ненулевую cardinality с нулевой суммой. Accumulator representation и output schema здесь разные объекты; это объясняет local/global aggregate fields в goldens08.

Наличие пустого retract hook нельзя читать как универсальную retract capability. [MAX](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/aggfunctions/MaxAggFunction.java#L75-L84) явно оставляет retract без действия ради случая monotonicity, когда предыдущий maximum уже не нужен даже при changelog соседних aggregations. Выбор такого aggregate требует доказанных planner metadata; обычный retractable MAX с произвольными удалениями должен использовать иной state contract. [LEAD/LAG](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/aggfunctions/LeadLagAggFunction.java#L85-L107) использует retract как reset на default для OffsetOverFrame, а не удаление occurrence. Поэтому интерфейс hook не заменяет семантику owner frame. [Rank](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/aggfunctions/RankAggFunction.java#L87-L100) и [NTILE](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/aggfunctions/NTILEAggFunction.java#L78-L97) также зависят от связывания новых counter значений между выражениями. State/checkpoint frame ownership атрибутирован05; данные классы сами не выполняют snapshot.

## Cast rule как отдельно компилируемый объект

Прочитанные11 базовых casting classes задают второй путь исполнения помимо enclosing operator codegen; конкретные cast rules ещё читаются. [CastRuleProvider](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/CastRuleProvider.java#L275-L328) сначала ищет exact target/root/family map, затем custom predicates, предварительно снимая DISTINCT wrappers. Validation допустимого cast, наличие runtime rule и runtime canFail — три разных вопроса. Identity cast [возвращает исходный object](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/CastRuleProvider.java#L186-L206), не создавая копию.

[Full executor generation](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/AbstractCodeGeneratorCastRule.java#L60-L175) передаёт serializers/reusable objects в constructor, компилирует Java через classloader и оборачивает runtime exception только когда rule сообщает canFail. [Expression-only fast path](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/AbstractExpressionCodeGeneratorCastRule.java#L63-L103) строит null guard и boxing самостоятельно. Полученный [CodeGeneratedExpressionCastExecutor](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/CodeGeneratedExpressionCastExecutor.java#L38-L61) переиспользует mutable Object[1] на каждый вызов; thread-safety этого экземпляра требует caller ownership, а не следует из чистоты арифметической expression. Конкретные conversion semantics и проверенные runtime assertions нельзя выводить только из этой инфраструктуры.


## Cast ownership, точность и единицы длины

Identity и часть binary casts сохраняют alias исходного значения, тогда как [ARRAY cast](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/ArrayToArrayCastRule.java#L79) выделяет новый массив и проверяет фактический NULL element даже при NOT NULL target. [ROW cast](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/RowToRowCastRule.java#L174) создаёт reusable binary writer и возвращает copy; RowKind намеренно не переносится для nested value. Следовательно, ownership результата определяется конкретной rule, а SQL CAST сам по себе не обещает deep copy. Для MAP/MULTISET [каждая преобразованная пара помещается через HashMap.put](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/MapToMapAndMultisetToMultisetCastRule.java#L179). Если преобразование ключей неинъективно, локальный код не складывает multiplicities при collision; admissibility такого преобразования и точный test oracle остаются отдельным обязательством, без заявления о воспроизведённой ошибке.

String/binary преобразование имеет несколько единиц длины. Основной CHAR/VARCHAR путь [использует numChars/substring BinaryStringData](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/CharVarCharTrimPadCastRule.java#L104), а общий formatter constructed values [обрезает Java String через length/substring](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/CharVarCharTrimPadCastRule.java#L190), то есть UTF-16 units. Binary target [обрезается по числу UTF-8 bytes](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/StringToBinaryCastRule.java#L67). Эти пути нельзя описывать одним правилом «длина строки»: representation и target family входят в контракт. [Binary→String](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/BinaryToStringCastRule.java#L73) дополнительно выбирает strict UTF-8, legacy replacement и printing hex; bounded target проходит другой materialization путь, чем unbounded. Это source evidence, Unicode boundary tests здесь ещё не прочитаны.

Temporal casts несут query context. [TIMESTAMP↔LTZ](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/TimestampToTimestampCastRule.java#L58) сначала применяет session zone, затем при необходимости truncates precision; переход между time indicators для without-zone принудительно использует precision3. [TIMESTAMP→DATE](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/TimestampToDateCastRule.java#L56) для without-zone использует floorDiv, а LTZ требует session-zone helper. Числовые timestamp rules существуют в registry, но [generateExpression намеренно бросает ValidationException](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/NumericToTimestampCastRule.java#L47): найденный cast-rule object ещё не означает разрешённую executable conversion. String parsing rules явно canFail; coercion, TRY_CAST и enclosing null handling должны сохранять это различие. Runtime/tests не запускались; весь reserved planner main остаётся незавершённым.


Printing и conversion также разделены: [FromVariantCastRule](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/FromVariantCastRule.java#L67-L118) переводит variant-null в SQL NULL для nullable target, но printing идёт через отдельный toPrintString. [ToVariantCastRule.canFail](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/ToVariantCastRule.java#L72-L151) вычисляет fallibility по типу и declared length, прямо предупреждая: source может выдать более длинное значение и нарушить предпосылку TRY_CAST. Reusable converters и builders принадлежат generated instance; они не являются checkpoint state. [RowDataToStringConverterImpl](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-table/flink-table-planner/src/main/java/org/apache/flink/table/planner/functions/casting/RowDataToStringConverterImpl.java#L57-L96) лениво строит column converters в printing context и проверяет фактический row NULL перед cast. Поэтому отображаемый результат CLI нельзя автоматически использовать как oracle обычного SQL CAST.
