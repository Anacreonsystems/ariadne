# Исполнение задачи, mailbox и сетевое давление

Исследуемая ревизия: `068f428b29f4d9ee587fa1006d2f1a69b43c0000`. Глава пополняется по мере полного чтения исходников. Текущие утверждения относятся к перечисленным реализациям; полное покрытие выделенного корпуса ещё не достигнуто. Прочитанные тесты служат свидетельством заложенных проверок; тесты и сборки не запускались. Реестр реально прочитанных диапазонов — [execution.confirmed.jsonl](../readers/execution.confirmed.jsonl); inventory задаёт обязательство, а exposure подтверждает только выдачу текста.

## Два уровня жизненного цикла

`Task` — оболочка одной попытки параллельной подзадачи. Она получает собственные конфигурации, идентификаторы и дескрипторы входных/выходных промежуточных результатов; политика повторных попыток и связи графа остаются у JobManager. Конструктор создаёт writers/gates через `ShuffleEnvironment` и отдельный Java `Thread`, но не запускает работу. Это отделяет подготовку объекта от приобретения ресурсов, которые потребуется освобождать при провале deployment ([Task:129–145](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskmanager/Task.java#L129-L145), [Task:413–452](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskmanager/Task.java#L413-L452)).

`startTaskThread()` запускает этот поток; `run()` завершает `terminationFuture` только после выхода из `doRun()`. Переходы состояния используют CAS. Успешный путь: `CREATED → DEPLOYING`, загрузка пользовательского classloader, регистрация сетевых ресурсов, создание `RuntimeEnvironment` и invokable, затем `INITIALIZING → restore() → RUNNING → invoke() → cleanUp(null)`. После этого оболочка вызывает `finish()` каждого output partition и только затем пытается перейти `RUNNING → FINISHED`. Даже успешный возврат пользовательского кода не означает успешное завершение: конкурентная отмена либо ошибка завершения partition переводит путь в обработку отказа ([Task:577–683](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskmanager/Task.java#L577-L683), [Task:778–849](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskmanager/Task.java#L778-L849), [Task:952–984](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskmanager/Task.java#L952-L984)).

`StreamTask` реализует внутренний streaming lifecycle invokable. Одна задача содержит цепочку операторов. `ChainingOutput.collect()` синхронно вызывает `recordProcessor.accept()` следующего оператора; промежуточный сетевой обмен для этого перехода не нужен. Исключение следующего оператора становится `ExceptionInChainedOperatorException` в вызывающем стеке. Сам `ChainingOutput` не владеет закрываемыми ресурсами ([StreamTask:174–210](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L174-L210), [ChainingOutput:72–141](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/ChainingOutput.java#L72-L141)).

## Mailbox — граница владения операторным потоком

`StreamTask` создаёт `MailboxProcessor(this::processInput, ...)`, привязанный к текущему потоку конструктора invokable. Основная работа по чтению данных является default action. Таймеры, checkpoint requests и operator events направляются в тот же mailbox. Потоки таймеров и сетевые потоки существуют отдельно, однако пользовательский timer callback переносится в mailbox через `deferCallbackToMailbox()`. Асинхронный snapshot pool и однопоточный channel IO executor выполняют вспомогательную работу, не превращая операторную цепочку в набор независимых потоков ([StreamTask:427–499](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L427-L499), [StreamTask:2188–2205](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L2188-L2205)).

`MailboxProcessor.runMailboxLoop()` сначала исполняет доступную порцию писем и затем одну default action. Когда default action приостановлена, поток блокируется на получении mail и продолжает обрабатывать управление. Возобновление извне публикует urgent control mail; из mailbox thread оно может изменить suspension непосредственно. Suspension имеет идентичность: поздний resume старого объекта не снимает новую приостановку ([MailboxProcessor:214–234](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/MailboxProcessor.java#L214-L234), [MailboxProcessor:355–410](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/MailboxProcessor.java#L355-L410), [MailboxProcessor:510–534](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/MailboxProcessor.java#L510-L534)).

Mailbox допускает несколько отправителей и одного читателя. Общая queue защищена `ReentrantLock`, текущий batch принадлежит mailbox thread. Обычные письма, добавленные во время обработки batch, не расширяют текущую порцию: самопубликующееся письмо не должно навсегда вытеснить обработку input. Urgent письма могут попадать перед оставшимися обычными письмами, при этом перенос обеспечивает FIFO среди urgent писем. Числовой priority служит фильтром при `yield()` конкретного executor: извлекается первое письмо с `mailPriority >= priority`; это не глобальная сортировка обычной очереди по числу ([TaskMailbox:29–67](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/TaskMailbox.java#L29-L67), [TaskMailboxImpl:236–288](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/TaskMailboxImpl.java#L236-L288), [TaskMailboxImpl:344–360](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/TaskMailboxImpl.java#L344-L360)).

Есть три разных состояния остановки: suspend всей петли допускает последующий запуск; `allActionsCompleted()` завершает её навсегда; `prepareClose()` переводит mailbox в QUIESCED и запрещает новые письма, сохраняя чтение накопленного. `close()` отбрасывает остаток и отменяет содержащиеся futures. При нормальном завершении StreamTask сначала quiesce-ит оба timer service, закрывает приём писем, drain-ит остаток и только затем снимает `isRunning` ([MailboxProcessor:168–207](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/mailbox/MailboxProcessor.java#L168-L207), [StreamTask:1282–1322](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L1282-L1322)).

## Availability: данные и управление при backpressure

`StreamOneInputProcessor.processInput()` вызывает `input.emitNext(output)`. После `END_OF_DATA` он уведомляет `endInput()` и заменяет output на `FinishedDataOutput`; конец восстановления переключает recoverable input в обычный режим. `StreamTask.processInput()` интерпретирует статусы и выбирает future, которое разбудит default action. Недоступный downstream writer даёт soft-backpressured time; отсутствие input даёт idle time; ожидание changelog writer учитывается как отдельный busy interval. Если availability успела измениться между проверками, цикл просто повторяет шаг ([StreamOneInputProcessor:58–88](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/StreamOneInputProcessor.java#L58-L88), [StreamTask:681–759](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L681-L759)).

Наличие chain availability provider меняет условие прогресса: заполненная внутренняя очередь при доступном downstream считается внутренней обработкой, а при недоступном downstream — backpressure. Проверка для batch emission требует одновременно доступности задачи и отсутствия писем. Поэтому batch processing сотрудничает с управляющей очередью, но mailbox не может вытеснить произвольный долгий вызов оператора посередине его Java-стека ([StreamTask:731–743](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L731-L743), [StreamTask:1416–1429](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L1416-L1429)).

Soft backpressure не устраняет все блокирующие пути. `BufferWritingResultPartition` сначала пробует получить `BufferBuilder` без ожидания, а при неудаче выполняет `requestBufferBuilderBlocking()` и измеряет hard-backpressured time. Это возможно внутри записи, в частности при продолжении record через границу buffer. В этот момент операторный поток действительно блокируется; управление mailbox возобновится после выхода из вызова. Buffer debloat может менять желаемый размер, но append при нехватке pool способен расширить текущий buffer, чтобы уменьшить вероятность такой блокировки ([BufferWritingResultPartition:318–338](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/BufferWritingResultPartition.java#L318-L338), [BufferWritingResultPartition:449–463](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/BufferWritingResultPartition.java#L449-L463)).

## Из record в partition и обратно

`RecordWriter` выбирает subpartition и сериализует record с четырёхбайтовым префиксом длины. Его target — `ResultPartitionWriter`; availability делегируется partition. Buffer timeout выбирает flush после каждого record, отсутствие periodic flush либо отдельный daemon `OutputFlusher`. Ошибка flusher сохраняется и позднее превращается в `IOException` на producer path; volatile-проверка намеренно выполняется не на каждом record ([RecordWriter:83–157](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/api/writer/RecordWriter.java#L83-L157), [RecordWriter:184–244](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/api/writer/RecordWriter.java#L184-L244)).

В `BufferWritingResultPartition` unicast использует отдельный builder для subpartition, broadcast — один builder и копии consumers с общим удерживаемым buffer. Смена режима завершает builders предыдущего режима. Event broadcast сначала завершает builders, затем добавляет отдельную копию event consumer каждой subpartition. Для continuation запись partial bytes обязана предшествовать созданию consumer: иначе читатель спутает начало buffer с началом полного record ([BufferWritingResultPartition:164–220](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/BufferWritingResultPartition.java#L164-L220), [BufferWritingResultPartition:370–427](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/BufferWritingResultPartition.java#L370-L427)).

`PipelinedResultPartition` держит отдельные счётчики двух обязательств: lifetime ownership и подтверждение обработки пользовательских данных downstream. `numberOfUsers = subpartitions + 1` включает producer; release читателя идемпотентен по bitset, producer снимает собственную ссылку в `close()`. Только нулевое число пользователей разрешает partition manager освободить partition. `allRecordsProcessedFuture` завершается отдельно, по подтверждениям всех subpartitions. Pipelined partition нельзя повторно потребить или переподключить ([PipelinedResultPartition:92–184](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/PipelinedResultPartition.java#L92-L184), [PipelinedResultPartition:203–229](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/PipelinedResultPartition.java#L203-L229)).

`SingleInputGate` объединяет channels одного intermediate result. Готовые channels стоят в `PrioritizedDeque`, bitset предотвращает дублирование. После получения одного buffer канал с продолжением добавляется в конец, чтобы другие channels получили шанс. Priority notification содержит sequence number; gate отбрасывает запоздавшее уведомление, если соответствующий buffer уже был прочитан, включая специальную обработку переполнения sequence number ([SingleInputGate:958–972](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/SingleInputGate.java#L958-L972), [SingleInputGate:1210–1336](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/SingleInputGate.java#L1210-L1336)).

## Remote channel: credit, ownership и checkpoint cut

Сетевой IO thread передаёт полученный buffer в `RemoteInputChannel.onBuffer()`. Этот метод принимает полное обязательство recycle: либо buffer становится собственностью queue, либо `finally` освобождает его. Последовательность проверяется до помещения в queue; несовпадение создаёт channel error. Task thread забирает buffer через `getNextBuffer()`, а очередь и её bookkeeping защищены `receivedBuffers`. Флаг release выставляется до закрытия connection; поздно прибывший buffer поэтому будет recycled ([RemoteInputChannel:455–492](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L455-L492), [RemoteInputChannel:518–546](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L518-L546), [RemoteInputChannel:778–877](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L778-L877)).

Initial credit соответствует exclusive buffers канала. Backlog producer увеличивает требуемый объём до `backlog + initialCredit`, и channel запрашивает floating buffers. При появлении доступных buffers `unannouncedCredit` атомарно накапливается; уведомление отправляется только при переходе от нуля. Для конфигурации без exclusive buffers блокировка upstream освобождает floating buffers, чтобы другие channels могли продвигаться; resume сбрасывает накопленный credit согласованно с producer. На gate setup сначала резервируется хотя бы один floating buffer для предотвращения тупика при нулевом exclusive allocation ([RemoteInputChannel:635–680](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L635-L680), [RemoteInputChannel:767–775](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L767-L775), [SingleInputGate:598–613](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/SingleInputGate.java#L598-L613)).

Priority barrier может обойти обычные buffers. Channel помнит sequence number последнего barrier, а `checkpointStarted()` удерживает ссылки на overtaken inflight data и передаёт их persister. Events не становятся data snapshot; при неизвестном barrier sequence сохраняется весь соответствующий inflight. Более новый barrier может subsume старый checkpoint. Отдельное announcement позволяет объявить barrier до физического продвижения его buffer в priority region ([RemoteInputChannel:845–860](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L845-L860), [RemoteInputChannel:927–956](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L927-L956), [RemoteInputChannel:1113–1191](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L1113-L1191)).

В исследуемой ревизии recovery может сразу использовать физический remote channel. Пока `inRecovery`, credit notifications подавлены, восстановленные buffers поступают в обычную received queue, обычные живые события временно складываются в stash, а живые data buffers запрещены precondition. После доставки последнего recovered buffer добавляется `EndOfFetchedChannelStateEvent`; только его потребление снимает recovery, выпускает stash и открывает credits. Release размыкает latch ожидания upstream и завершает state-consumed future исключением, чтобы ожидание не зависло. Checkpoint во время recovery использует собственный `RecoveryCheckpointBarrier` sentinel и удерживает только data до него ([RemoteInputChannel:273–377](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L273-L377), [RemoteInputChannel:830–843](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L830-L843), [RemoteInputChannel:959–1050](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/RemoteInputChannel.java#L959-L1050)).

## Успех, отмена и отказ не имеют общего shortcut

`EndOfData` означает завершение пользовательских данных; `EndOfPartitionEvent` завершает транспорт конкретного канала. Gate отслеживает эти условия разными bitsets. `StreamTask.endData()` при DRAIN сначала продвигает event time, завершает цепочку операторов и уведомляет writers. `END_OF_INPUT` приостанавливает default action и mailbox loop. Затем `afterInvoke()` вновь запускает mailbox, чтобы принять checkpoint/ack управление до выполнения условий завершения: downstream all-data-processed и final checkpoint, если checkpoints после finished tasks включены, либо stop-with-savepoint. Только потом следуют quiesce, drain, output flush и закрытие операторов ([SingleInputGate:1093–1123](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/SingleInputGate.java#L1093-L1123), [StreamTask:761–775](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L761-L775), [StreamTask:1253–1322](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamTask.java#L1253-L1322)).

External fail/cancel меняет состояние CAS и запускает cancellation вне task thread, поскольку пользовательский `cancel()` может блокировать. Отдельный interrupter периодически прерывает execution, отдельный watchdog сообщает fatal error, если поток не выходит за timeout. Atomic `invokableHasBeenCanceled` обеспечивает единственный вызов отмены. Canceler вызывает `fail()` partitions, чтобы освободить buffer pools, но не закрывает producer builders конкурентно с task thread; окончательный close остаётся у task cleanup. Checkpoint RPC boundary также не вызывает операторный snapshot прямо в чужом потоке: Task вызывает `triggerCheckpointAsync()`, StreamTask публикует mail, причём unaligned trigger urgent. ## TaskExecutor: принятие RPC и исполнение пользовательского кода

`TaskExecutor` наследует `RpcEndpoint` и управляет несколькими Task. Перед submit он требует соединение с JobManager именно данного job, совпадение `JobMasterId` и активную allocation. Затем восстанавливает offloaded deployment data, создаёт task-scoped state manager и получает memory manager allocation. Только после `taskSlotTable.addTask(task)` запускается `task.startTaskThread()`. Возвращаемый `Acknowledge` означает принятие deployment и запуск потока; успешное restore, обработка данных и FINISHED наступают позже ([TaskExecutor:662–743](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskexecutor/TaskExecutor.java#L662-L743), [TaskExecutor:826–905](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskexecutor/TaskExecutor.java#L826-L905)).

То же различие действует для checkpoint trigger RPC: он находит Task, вызывает `triggerCheckpointBarrier()` и возвращает Ack; устойчивость checkpoint этот ответ не подтверждает. Операторная часть запроса затем выполняется в mailbox, а checkpoint responder сообщает отдельный результат. Terminal state от task thread возвращается через `runAsync()` в TaskExecutor, где task удаляется из slot table и отправляется итог со snapshot accumulators и IO metrics. Ошибка подтверждения state update от JobMaster вызывает external failure соответствующей Task ([TaskExecutor:1091–1120](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskexecutor/TaskExecutor.java#L1091-L1120), [TaskExecutor:2151–2203](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskexecutor/TaskExecutor.java#L2151-L2203), [TaskExecutor:2689–2710](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskexecutor/TaskExecutor.java#L2689-L2710)).

Slot offer имеет собственный UUID поколения и проверку текущего leader: запоздалый ответ предыдущего offer либо старого JobMaster игнорируется. Разрыв JobManager connection сначала externally fail-ит задачи job и переводит active slots обратно в allocated; release partitions может откладываться до termination всех задач. В batch recovery с Netty допускается временное сохранение partitions после потери master. Следовательно, task lifetime, slot allocation lifetime и partition lifetime действительно различаются ([TaskExecutor:1775–1863](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskexecutor/TaskExecutor.java#L1775-L1863), [TaskExecutor:1915–1996](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/taskexecutor/TaskExecutor.java#L1915-L1996)).

`LocalBufferPool` считает availability строже, чем возможность выполнить одиночный request: должен иметься свободный segment и ни одна subpartition не должна достигнуть `maxBuffersPerChannel`. ## Порядок lifecycle цепочки и object reuse

`OperatorChain` строит outputs рекурсивно от tail к head, затем связывает wrappers в прямом топологическом порядке. Сетевые outputs регистрируются в close registry; частично неудавшийся конструктор закрывает уже созданные outputs. Main operator может иметь chained sources, поэтому первый lifecycle wrapper не обязательно совпадает с main. `RegularOperatorChain.initializeStateAndOpenOperators()` идёт tail→heads, `finishOperators()` запускает heads→tail, а `closeAllOperators()` снова идёт tail→heads и агрегирует исключения, пытаясь закрыть каждый оператор. Это три различных порядка, несмотря на устаревающую формулировку отдельных комментариев про close ([OperatorChain:120–140](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/OperatorChain.java#L120-L140), [OperatorChain:282–295](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/OperatorChain.java#L282-L295), [RegularOperatorChain:101–132](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/RegularOperatorChain.java#L101-L132)).

Finish каждого wrapper quiesce-ит его processing-time service, откладывает `wrapped.finish()` в mailbox и ставит завершающее письмо после него. Ожидая finished future, wrapper выполняет `tryYieldIgnoringDeferrable()`: отложенное продолжение watermark обязано закончить пересылку до EndOfData. При NO_DRAIN пользовательский finish пропускается, при этом quiesce и mailbox ordering сохраняются. После этого finish передаётся следующему wrapper ([StreamOperatorWrapper:150–207](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamOperatorWrapper.java#L150-L207), [StreamOperatorWrapper:210–247](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/tasks/StreamOperatorWrapper.java#L210-L247)).

## Локальный путь, Netty и возврат к mailbox

`LocalInputChannel` запрашивает `ResultSubpartitionView` непосредственно у локального partition manager и читает producer buffers через этот view. Для обычного локального пути не нужен consumer-side remote credit protocol. В recovery выделен отдельный deque восстановленных buffers; normal upstream data не читаются до sentinel, а priority event может быть взят из producer view раньше recovered data. Уже извлечённый recovered buffer всегда возвращается первым даже при конкурентном priority notification, иначе он потеряется. Исходник прямо ограничивает безопасность lock-free сброса pending-priority flag отсутствием concurrent unaligned checkpoints; перенос такого механизма на другой concurrency contract требует нового доказательства ([LocalInputChannel:428–485](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/LocalInputChannel.java#L428-L485), [LocalInputChannel:538–566](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/LocalInputChannel.java#L538-L566), [LocalInputChannel:633–664](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/LocalInputChannel.java#L633-L664)).

На producer стороне `PipelinedSubpartition` выдаёт законченные buffers, а explicit flush может сделать доступным ещё незаконченный buffer. Уведомление возникает при первом доступном finished buffer, после чего reader обязан продолжать до признака отсутствия данных. У subpartition есть собственная blocking state для checkpoint/recovery; priority buffers всё ещё выдаются в этой state. При priority unaligned barrier сохраняются копии overtaken output data, при timeout aligned barrier исходная barrier переводится в priority и channel-state future получает overtaken buffers. Завершение subpartition добавляет `EndOfPartitionEvent`, release закрывает всех оставшихся consumers и завершает pending channel-state future исключением ([PipelinedSubpartition:53–68](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/PipelinedSubpartition.java#L53-L68), [PipelinedSubpartition:217–269](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/PipelinedSubpartition.java#L217-L269), [PipelinedSubpartition:328–355](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/PipelinedSubpartition.java#L328-L355), [PipelinedSubpartition:433–465](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/PipelinedSubpartition.java#L433-L465), [PipelinedSubpartition:622–635](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/PipelinedSubpartition.java#L622-L635)).

Netty `PartitionRequestQueue` переносит producer availability notification в event loop через `ctx.executor().execute()`. На этом потоке queue выбирает готового reader, проверяет transport writability, отправляет один BufferResponse и продолжает из write-completion listener. Reader с продолжением ставится в хвост; регистрации дублирующего reader мешает его registered flag. Поэтому consumer credits, готовность producer view и writability TCP channel являются разными условиями прогресса. Ошибка транспорта освобождает все readers данной connection и уведомляет downstream ErrorResponse ([PartitionRequestQueue:84–126](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/netty/PartitionRequestQueue.java#L84-L126), [PartitionRequestQueue:297–364](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/netty/PartitionRequestQueue.java#L297-L364), [PartitionRequestQueue:393–420](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/netty/PartitionRequestQueue.java#L393-L420)).

Client handler различает fatal connection error и error конкретного receiver. PartitionNotFound инициирует проверку producer state; остальные receiver errors становятся channel error. Fatal connection failure выставляется один раз и распространяется на все remote input channels этой connection. `InputChannel.setError()` сохраняет первую причину CAS и уведомляет gate о nonempty даже без данных, чтобы task thread проснулся и выбросил её при чтении ([CreditBasedPartitionRequestClientHandler:246–265](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/netty/CreditBasedPartitionRequestClientHandler.java#L246-L265), [CreditBasedPartitionRequestClientHandler:307–358](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/netty/CreditBasedPartitionRequestClientHandler.java#L307-L358), [InputChannel:267–296](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/runtime/io/network/partition/consumer/InputChannel.java#L267-L296)).

`CheckpointedInputGate` подписывается отдельно на priority-event availability и публикует urgent mail, который вычитывает priority events в task thread. Это поддерживает checkpoint progress, когда default data action остановлена из-за downstream pressure. Обычный `pollNext()` обрабатывает barriers/announcements через barrier handler, EndOfData подтверждает upstream, а fetched-state sentinel переводит recoverable channel в live mode. `AbstractStreamTaskNetworkInput` держит spanning-record deserializer на каждый channel; пока есть недочитанный buffer, input available без нового gate poll. После каждого полного stream element batch может продолжаться только при `canEmitBatchOfRecords`; record attributes принудительно завершают batch. Snapshot должен включить также непрочитанный остаток deserializer, а не только queued network buffers ([CheckpointedInputGate:102–143](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/checkpointing/CheckpointedInputGate.java#L102-L143), [CheckpointedInputGate:180–217](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/checkpointing/CheckpointedInputGate.java#L180-L217), [AbstractStreamTaskNetworkInput:151–201](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/AbstractStreamTaskNetworkInput.java#L151-L201), [StreamTaskNetworkInput:118–137](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/StreamTaskNetworkInput.java#L118-L137)).

Для multi-input `StreamMultipleInputProcessor` ждёт availability только выбранных незавершённых inputs. Первое обращение к operator input selection выполняется после open. Выбор вращается относительно последнего прочитанного input и перепроверяет другие inputs для предотвращения starvation. Если все inputs finished, повторный вызов возвращает END_OF_INPUT, а не NOTHING_AVAILABLE: иначе already-completed availability future вызвал бы busy spin при выходе из recovery ([StreamMultipleInputProcessor:54–108](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/StreamMultipleInputProcessor.java#L54-L108), [StreamMultipleInputProcessor:138–168](https://github.com/apache/flink/blob/068f428b29f4d9ee587fa1006d2f1a69b43c0000/flink-runtime/src/main/java/org/apache/flink/streaming/runtime/io/StreamMultipleInputProcessor.java#L138-L168)).

Полное покрытие owner=execution не достигнуто. В частности, остаются hybrid/blocking shuffle, memory manager, deployment/services/slots, многие операторы и все ещё не подтверждённые тесты/ресурсы. Единственный источник количественного покрытия — объединённые подтверждённые диапазоны реестра; список разобранных механизмов не заменяет чтение оставшихся файлов.
