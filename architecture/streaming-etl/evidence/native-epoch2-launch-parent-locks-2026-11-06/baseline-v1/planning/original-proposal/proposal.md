## Parent fencing and lock-order analysis

The candidate request prefix would be Flow SHARE → Authority SHARE → Graph SHARE → (prepare: all assigned Workers SHARE, sorted) → own Worker SHARE → own Capability SHARE → own Subtask UPDATE → own Attempt(s) UPDATE → (replacement prepare: Replacement UPDATE → TaskRun UPDATE → output Partition UPDATE). No existing lower lock or ordering is removed. No parent lock is upgraded later by either endpoint's call tree.

Shared parent locks retain a stable lifecycle/generation/admission view until request commit. Real exclusive parent transitions must wait. Relevant source anchors:

- START/admission: `stream_dag_executions.py:1115` requests update=True; it enters admission at1141–1153. `stream_dags.py:1062–1069` obtains Flow/Authority UPDATE through `_flow(... update=True)` (`stream_dags.py:59–103`) and Graph UPDATE before all-or-none allocation; graph admission writes are1457–1460.
- Activation: `stream_dag_executions.py:2099` requests update=True, checks admission/control2108–2115, validates current child/Grant/launch generation at2225–2259, and writes Graph activation/startup fields at2269–2272. Shared launch prefix cannot bypass this barrier or create a Grant/ready acknowledgement.
- Freeze/control: `begin_dag_control`1166–1167 explicitly requires exclusive scope. It freezes all admitted targets including grant-less candidates, records bounded targets and the control operation, then writes Graph.current_control_operation_id at1419. Cancel/fail callers request update=True at1533/1567; generic Flow cancellation also does so at3241. A prepare already holding parent SHARE commits first and is visible to the later control; a control committed first makes fresh prepare reject, while replay/record returns STOP_REQUIRED according to the existing contract.
- Flow final/recovery: `stream_executions.py:646–692` locks Flow UPDATE then Authority/Graph before lifecycle mutation. Claim/takeover examples lock Flow/Authority at197–218/318–349 before generation/holder writes444–450. Native deployment takeover is separately rejected in the shown generic path330–334; this is not a claim that every recovery profile is supported. Completed/stopped graph finalizers explicitly require exclusive scope at `stream_dag_executions.py:2652`/2872. Signed Task events enter `lock_dag_child(graph_update=True)` (`services/task_run_recorder.py:99–109`) before control/finalization.
- Replacement/grant lifecycle stays outside the proposed change: `stream_dag_launches.py:1186–1216` authorize and1219–1273 confirm still use the helper's default exclusive parent prefix. Confirm requires exactly one recorded candidate and a CLOSED old birth. Claim767–849 and register852–917 retain their existing default prefix, grant creation/registration and links. Stop951 onward, close472 onward, retire1276 onward, startup abort and poll are unchanged. Prepare's required all_workers lock order is retained.
- Ordinary tag/global slots and physical slots are not touched by the two endpoints. Allocation/release helpers are imports only, not transitive calls from prepare/record. Capacity/tag admission, grant creation, actual Task events, physical stop and parent control continue to own those side effects. Tests must compare these tables, because this is a source finding rather than new runtime proof.

Limits: shared-prefix compatibility with a reader of a DIFFERENT subtask removes one unnecessary graph-wide exclusive conflict; own Subtask/Attempt locks still intentionally serialize same-target work. Genuine exclusive parent holders, earlier queued parent writers, Worker/capability writers, replacement TaskRun/output locks, FK checks, pool exhaustion and DB/network delays can still delay the request. Lock queueing may block a later SHARE request behind a pending writer. No deadlock-freedom or throughput claim follows from static inspection. Checks preserve existing state validations; this proposal does not repair or broaden any pre-existing generation/status check.
