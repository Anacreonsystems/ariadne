## What this isolates

Hypothesis: baseline prepare/record require parent FOR UPDATE despite writing only the own Attempt; a held data-reader FOR SHARE prefix therefore blocks them. A caller-only shared prefix should permit commit while that reader transaction remains open. This deliberately creates a known synthetic reader holder. It does NOT identify the unknown b4 holder or prove these two timeouts caused the full native deadline failure.

Use actual authenticated FastAPI HTTP routes against actual PG17. The existing `execution_api` fixture (`tests/server/api/test_stream_dag_executions.py:33–41`) uses httpx ASGITransport with real route/auth/transaction/DB behavior, not a mocked response. Explicitly label this HTTP-via-ASGI evidence; it is not TCP/native process evidence. If Principal requires TCP500 parity, run the same request payloads against a separately owned actual HTTP server in the isolated DB and label that additional surface separately. Keep `raise_app_exceptions=False` for ASGI so a genuine server exception is observed as HTTP500. Do not inject a fake500, override the model, bypass auth, patch DB results or change timeout settings.

## Required fence and concurrency controls

- For EACH endpoint and EACH parent kind (Flow, Authority, Graph), hold an actual exclusive parent lock in correct prefix order, observe Q blocking with a real blocker witness, and show no Attempt delta until release. Then release and let the valid request finish. This confirms SHARE did not bypass exclusive lifecycle transitions.
- Control-first: durably start FAIL/CANCEL/startup stop by the normal lifecycle APIs. A new prepare must reject without inserting a birth. Exact accepted prepare replay retains receipt and returns STOP_REQUIRED. A delayed record on an existing PREPARED birth must journal its exact PID and return STOP_REQUIRED; conflicting record body must fail without mutation. Existing delayed-record test587–694 is relevant regression coverage and must be retained.
- Launch-first: if a launch holds parent SHARE and has committed its birth before freeze can acquire parent UPDATE, later control must include the target/birth in closure obligations. No last-stop finalization until every prepared/recorded birth closes. Existing all-attempts-close test697 onward is a regression anchor.
- Same-target concurrent identical prepare: real Subtask UPDATE serializes two calls; they must return one receipt/launch ID, one attempt_index/epoch and one inserted row. Changed digest/identity conflicts must leave no additional row. Concurrent identical record returns one stable record receipt; differing PID/ticks/journal digest is rejected. Do not depend on timing alone; observe lower-lock blocker if deliberately held.
- Cross-target healthy reader: hold another target's data-reader transaction including its own Subtask SHARE while issuing prepare/record for a different target; only shared parent prefix overlaps, so valid launch can commit without reader release. This narrows the intended benefit; a SAME-target Subtask SHARE is expected to block its UPDATE and is not a failure of the proposal.
- Keep stale Worker/principal, assigned-worker mismatch, missing/exact slot mismatch, current graph/admission mismatch, expected Grant/epoch/Replacement auth mismatch, prior unclosed birth, terminal TaskRun/output, retry64/budget and authority generation/holder/run_count validation regressions. Use normal public lifecycle setup where possible. If a specific negative case requires data corruption injection, identify it separately as guard coverage, never as a supported user flow.
- Run the relevant existing launch module and focused lifecycle/API regressions only after authorization. The held coordinator model and native fixture sources remain byte-held. Do not broaden change scope on a failure; report precise failing invariant and return to Root/Principal.
